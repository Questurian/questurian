Auditing a Kill Switch: the Photo Import Flag

~20 minutes · builds on the codebase overview · companion: Photo Import Gate Map · all claims code-verified 2026-06-10 unless tagged otherwise

The question you asked: "Have we set a robust feature flag?"

PARTLY A flag exists (uncommitted in your working tree): ENABLE_GOOGLE_PHOTO_IMPORT, default off. It gates 4 of the 5 money-spending paths and 2 of the 3 UI surfaces.

GAP 1 retry() can still spend Google money with the flag off.

GAP 2 The "Pull photos from Google" button still renders on every existing location's media tab.

GAP 3 It's an env var — toggling it means editing .env and restarting the server. The UI on/off button you want doesn't exist yet.

1Why this feature costs money

Every "Pull from Google" interaction fans out to Google's Places API (New) photo endpoints, and each call is billable (pricing table):

  • Opening the picker (preview) = 1 Place Details call + up to N photo-media calls, one per thumbnail. The code admits this fan-out: "Fan out and grab thumbnail URLs… latency is acceptable" — photo-import.service.ts:117
  • Importing = 1 photo-media bytes download per selected photo.
  • Cropping in the add-flow = 1 more bytes download via the proxy endpoint.

So a single browse-and-import session on a location with 10 photos can be ~12–15 billable calls. That's the bill you're switching off.

2The skill: how to audit any kill switch

This is the repeatable method — it works for any "expensive integration" flag, in any codebase:

  1. Find the waist. What is the narrowest piece of code that talks to the paid service? Here: GooglePlacesPhotosClient — the only class that holds the API key and calls places.googleapis.com.
  2. Enumerate every path to the waist. Grep for the client's methods (getPhotosForPlace, getPhotoUri, fetchPhotoBytes) and walk callers upward. You get 5 paths: preview, previewByPlaceId, start, proxyPhotoBytes, retry.
  3. Check the gate on each path. 4 of 5 call isConfigured() first. One doesn't.
  4. Check the UI's source of truth. Does the UI derive its disabled state from the server, or does it guess? Here the add-flow phases read preview.configured from the server response — good. The media-tab panel reads nothing — gap.

Full path-by-path table with file:line evidence: Photo Import Gate Map.

3The gaps, and the principle behind them

Gap 1 — retry() bypasses the flag. PhotoImportService.retry() (photo-import.service.ts:219) goes straight to processDownload() → fetchPhotoBytes(). The only check on that route is the key check inside the Google client — not the flag. With the flag off and your key still set, clicking "Retry" on a failed staged photo spends real money.
Gap 2 — PhotoImportPanel ignores the flag. The panel renders its "Pull photos from Google" button whenever the location has a placeId (PhotoImportPanel.tsx:270). It's mounted on every location's media gallery (LocationMediaGallery.tsx:44) and the accommodations edit form. Clicking it with the flag off doesn't spend money (the preview short-circuits server-side), but the button you wanted gone is still everywhere.
Principle: gate at the narrowest waist.
The current design checks the flag per-method at the service layer — five doors, four locks. That is exactly how retry() got missed, and how the next method someone adds will get missed too. If instead the flag check lives inside GooglePlacesPhotosClient.requireConfigured() — the one chokepoint every Google call already passes through — every present and future caller is covered automatically. Defense in depth means keeping the service-layer checks too (they give friendly early errors), but the waist is the lock that can't be forgotten. This maps directly to your mission's "blast radius" idea: a gate's blast radius should equal the cost surface, and the waist is the only place where it provably does.

4What you actually asked for: a runtime toggle

An env flag answers "is this deployment allowed to spend money?" — it changes on restart. You asked for an ops toggle: a button in the UI that flips the feature live. In Hodgson's taxonomy that's a longer-lived, runtime-dynamic toggle, and it needs three pieces the codebase doesn't have yet:

PieceDesignEntry point
Persisted setting A one-row settings store in the LM SQLite DB (e.g. app_settings key/value), read at request time — not cached at boot packages/server/src/shared/db/ (follow the migration pattern in migrations/add-photo-import-fields.ts)
Status + toggle API GET /api/settings/photo-import and PUT /api/settings/photo-import, behind the same operator auth as the other routes. The effective state = env flag AND runtime setting AND key present — env stays as the master kill switch features/locations/routes/location.routes.ts
UI toggle + consumers One shared React Query hook (usePhotoImportEnabled) consumed by all three surfaces; the toggle button lives in the existing admin area packages/client/src/features/admin/pages/ (alongside PayloadSync.tsx)

The key architectural move: once a status endpoint exists, all three UI surfaces stop guessing and derive from one source of truth — which also fixes Gap 2 properly instead of patching the panel.

5Exercise — close Gap 1 yourself (the tangible win)

One edit, then verify with a tight feedback loop. Move the flag check into the waist:

  1. In google-places-photos.client.ts, make isConfigured() also require EnvConfig.getInstance().ENABLE_GOOGLE_PHOTO_IMPORT. Because requireConfigured() runs before every Google call, this closes retry() and any future caller in one move. (The service's own isConfigured() can then go back to just delegating — one source of truth.)
  2. Set ENABLE_GOOGLE_PHOTO_IMPORT=false in apps/location-manager/.env, start the app (pnpm dev from apps/location-manager — server is on port 4317), then run:
# 1. Preview must short-circuit: expect "configured": false, empty photos
curl -s "http://localhost:4317/api/photo-import/preview-by-place?placeId=ChIJtest" | head -c 300

# 2. The proxy (a direct waist path) must refuse BEFORE any network call:
#    expect a 400 error, and no outbound Google request in server logs
curl -s "http://localhost:4317/api/photo-import/proxy?name=places/x/photos/y"

# 3. Flip the flag to true, restart, re-run #2: expect a Google error instead
#    (bad photo name) — proving the gate, not the name, was the blocker

The loop: each curl gives you immediate pass/fail. If step 2 returns image bytes or a Google-shaped error while the flag is off, your gate isn't at the waist yet.

6Check yourself

Q1. Flag off, API key still set in .env. Which action spends Google money today (before your fix)?

Retrying a failed staged photo. retry() never consults isConfigured(); it goes straight to processDownload → fetchPhotoBytes, and the client's own check only verifies the key exists.

Q2. Why is GooglePlacesPhotosClient the right place for the flag check, rather than adding the missing check to retry()?

It's the chokepoint: every Google call, from every current and future caller, already passes through it. Patching retry() fixes one door; locking the waist fixes the building. Per-call-site gating is what produced the gap in the first place.

Q3. How does the add-flow UI know the feature is disabled?

It doesn't have its own config — it reads the configured: boolean field that the server returns in the preview response. Server is the source of truth; the client just renders it. PhotoImportPanel is the surface that lacks this wiring.

Q4. After the env flag ships, what still stands between you and "click a button to turn it off"?

Env vars are read at process start — flipping one means editing .env and restarting the server. A live UI toggle needs a persisted runtime setting, an authed status/toggle endpoint, and the UI surfaces reading that endpoint. The env flag should remain as the outer kill switch.

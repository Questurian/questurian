2. Fixed product decisions

These decisions are settled. Do not restart the design discussion or substitute a different flow.

  1. Title seed is a finished or near-finished SEO title. User supplies it once. Preserve it; do not generate or discover it.
  2. No initial Grill. Trip details and layouts are entered with forms and controls.
  3. Number of days creates that many tabs. Three days means three independently editable day layouts.
  4. User selects day type and organizes stops. Selecting a type fills a visible, editable agenda.
  5. User approves every layout before entering the day workspace. Layout approval is not approval of AI-generated content.
  6. Each day has its own future Grill. Shared trip details are inherited; day data and notes remain separate.
  7. AI stays disconnected in this build. Workspace must be useful and honest about its current availability.
  8. Every displayed element needs a purpose. No fake statistics, filler panels, duplicated title inputs or technical metadata in the product UI.

Implementation defaults: four stages on the existing route, Full Day Balanced on new days, optional shared preferences collapsed, browser-local saving, per-day approval buttons, no approve-all shortcut. These specify how to implement the agreed flow; they are not claims that each detail was separately requested by the user. Use them unless repository constraints require a documented equivalent.

Reference A — Scope

Build a usable frontend workflow, with no AI integration: Trip details → Shape days → Approve layouts → Day workspace. The initial section is a structured form. Every day gets its own future Grill after all layouts are approved.

  • One title seed: a finished or near-finished SEO-ready title, supplied by the user. Preserve its wording and promise. No title generation, discovery interview or duplicate seed field.
  • Structure belongs to the user: number of days, day types, slot order and options. Show the resulting layout immediately.
  • No initial Grill: collect known shared information through controls. Optional information stays optional.
  • One future Grill per day: daily purpose, experiences, geography, distances, timings and tradeoffs. Each receives the same shared trip context and its own day snapshot.
  • This build stops at an honest workspace: editable preparation notes and readable context work; sending messages, AI recommendations, research, route verification and day-content approval do not.

This document is the implementation handoff. When assigned this plan, implement the application UI through Tasks 1–7 above. The seven revised day rhythms and their complete slot rules remain specified in the appendix.

Acceptance principle: every visible element must help enter a decision, inspect its result, fix a problem or move to the next step. Remove decorative metrics, duplicate summaries and implementation metadata from the product UI.

Day options

Available time does not silently prune the template. Show out-of-window stops with a linked message to adjust daypart, remove the stop or change the window. Dayparts are coarse labels. Custom windows must receive an explicit layout review; do not claim exact schedule fit from dayparts.

State, persistence and ownership

UI-only build: save one local draft per signed-in user and browser using a feature-specific, versioned storage key. If no reliable user identity is available, keep in memory and explain the limitation; do not use an anonymous shared draft for authenticated operators. No new backend run or AI calls. “Saved on this browser” is the accurate persistence label.

Create the draft on first substantive edit. Autosave form changes with a short debounce and flush on blur/stage navigation; preparation notes have explicit Save and a leave-with-unsaved-notes prompt. Catch storage failures and show “Changes aren’t saved on this browser” with Retry. Do not display Saved until write succeeds. Route navigation and tab switching preserve state; reload restores the same draft where storage works.

Derive readiness and approval validity; do not store contradictory status flags. Production limit: local storage is browser-local, not durable cross-device storage. Introduce server persistence later behind a repository interface; do not claim the frontend-only build creates production runs. Keep the UX and state boundaries ready for that replacement.

2A / Day and stop rules

Carry the rules with the day

A template is more than a list of stop names. Selecting one must carry its ordered slots and their selection instructions into the outline. The library below revises seven built-in templates by stop purpose, while retaining two saved custom templates and the 13 existing stop presets as reference.

Data pointRule for the new pipeline
Template identity and originKeep the source template ID and whether it came from the built-in or custom library. Full Day Balanced is the existing default; selecting a different template is an explicit editor choice.
Ordered slotsCopy the complete slot sequence into the day. Give each occurrence its own stable identity; two days can use the same template without sharing editable stops.
Time of dayPreserve each slot’s daypart. Morning, late morning, lunch, afternoon, dinner, evening, and nightlife are labels, not verified hours or durations. Flag slots outside the editor’s available time for an agreed adjustment.
Allowed place categoriesUse these as the category boundary for candidate selection. A dining-only slot cannot silently become an attraction. A multi-category slot allows any listed category.
Preferred categoriesPrefer these within the allowed categories. Preference is not an additional mandatory category, and does not authorize a category outside the allowed list.

Give every stop a job

A slot tells Claude why a stop exists, not just its category or time of day. Signature anchors, neighborhood exploration, hands-on experiences, scenic resets, cultural deep dives, transition stops and evening anchors shape genuinely different days.

Keep the three underlying types: Restaurant (dining), Activity (attractions), and Nightlife (nightlife). Slot roles sit above those types. Cultural anchors and scenic recovery map to Activity; dinner maps to Restaurant; a cocktail opener can use Restaurant or Nightlife; the main nightlife destination maps to Nightlife.

Carry each role’s purpose into the outline and research prompt. Light means low intensity with a memorable experience. Food needs a non-food break. Adventure needs recovery. Nightlife needs progression. Premium needs indulgent experiences beyond expensive meals. Culture gets its anchor before lunch.

Optional finishes remain explicitly optional; none should be added merely to fill a template. Dayparts and routing still need feasibility checks. Future Food Explorer, Foodie Splurge and Street Food Day variants can share a theme while using different skeletons; these are future options, not extra templates in this revision.

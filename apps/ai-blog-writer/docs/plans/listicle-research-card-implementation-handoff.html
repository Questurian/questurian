The implementation contract

An operator prepares one item card, clicks Research this place, and receives a saved, editable evidence profile. That profile can later support multiple listicles.

Implementation handoff · September 11, 2026. This document supersedes the earlier seven-call proposal for the research phase. It specifies work for the implementing agent; it does not claim the trigger or viewer already exists.

Ship the full vertical slice: durable preparation → server-enforced readiness → explicit one-place research trigger → one grounded AI call → persisted findings → card summary and research viewer → manual additions/edits → reload and reuse.

Out of scope: blurb generation, intro generation, AI angle selection, AI fact-check/repair calls, automatic follow-ups, research-all, publication and Location Manager jobs. No standalone worker service or live deployment. Use Mac localhost.

The user wants to inspect one to three places individually before expanding. A whole-list approval step is unnecessary for this slice. Every place is independently eligible; completing preparation never starts a paid call.

Research viewer

Open a drawer or modal from the card; preserve card scroll position on close. Header identifies venue and branch. Default filter is this list’s topic; an All topics filter reveals reusable material. Table columns: finding, topic/category, source, dates, review state. Expand a row for supporting passage, scope and provenance.

Provide Add finding, Edit, Keep, Discard, Restore, Add possible angle and Research a specific gap. Keep/discard changes curation, never erases raw research history. Mark AI rows Unreviewed initially. Viewing a source opens its link; no automatic fetching or paid work on GET.

Research history shows requested search directions, actual provider metadata when available, timestamps, result state and usage. Do not expose secrets or raw transport headers. Make large/raw provider output staff-only and collapsed; normal reading stays concise.

Click-to-output sequence

  1. Operator checks prep items. Save them with optimistic version checking; show Saving / Saved / Could not save. URL fields save on blur; checkboxes save immediately. Disable research until the latest save succeeds.
  2. Operator clicks Research this place. Client creates an idempotency key for this logical action and sends candidate/context versions.
  3. Server loads current candidate, board decisions, Google identity and prep. Recompute readiness; reject stale/blocked input without a provider call.
  4. Resolve/create profile by internal ID and verified external identity. Existing unresolved identities are not merged by name. Attach a per-run candidate link and discovery sightings.
  5. In a short SQLite transaction, reserve the one-active-attempt slot, store an immutable input snapshot and mark the attempt running. Commit before outbound network work.
  6. Invoke existing grounded transport exactly once. Use a deterministic prompt assembled from topic, article standard, branch identity, shared categories, relevant existing findings and optional source links.
  7. Parse and validate response locally. Save attributed findings, unresolved attribution and coverage. No second AI parser, research retry or gate call.
  8. Commit findings and terminal attempt state transactionally. Release slot only for the owning attempt. Return saved attempt/profile summary.
  9. Card updates and viewer reads saved rows. Refreshing page restores running/completed state from GET. All later edits use the same profile store.

Use a synchronous POST for this first one-place action with an in-process executor; SQLite is the durable record. UI may poll status while the POST is pending. Reuse the existing transport timeout pattern; align client timeout so it does not report failure before the backend deadline. Do not hold a DB transaction open during the AI request.

If the browser loses its response, GET status before offering retry. Repeating the same idempotency key returns the existing attempt, never buys another call. If the process dies, an expired ownership lease marks the attempt interrupted; late writes must fail ownership checks. No startup replay of interrupted paid work. Reuse tested lease patterns from the existing search runner rather than inventing a queue service.

One call: what it searches and returns

Shared categories: signature offering, preparation, customer observations, value/portions, setting, occasion, drinks, people, history, recognition, practical details, caveats. Fixed category IDs; any number of specific finding rows. The first version does not need a category editor or AI-generated taxonomy. An “other” category covers exceptional material.

Topics remain separate: wings, ceviche, cocktails, restaurant-wide. Persist a topic key derived from the approved order kind using deterministic normalization, plus human-readable label. Do not treat every restaurant article as one interchangeable topic. Operator can assign existing topic labels to manual findings; unknown new labels are allowed without an AI call.

For the wings run, request official offering evidence, specific reviews/food writing about wings, preparation/value and useful setting details. Search Spanish first. History/awards are optional incidental material, never required fields. Other topics found incidentally can be stored without launching separate research.

Response budget: start at the existing roughly 3,000-token scale and existing research timeout; inspect truncation in the pilot. No dollar estimates borrowed from discovery. Record actual gateway usage, duration, model and grounding metadata.

Storage and precise contracts

Keep research in the same ABW SQLite database. Preserve existing profiles and claim IDs where feasible. Internal profile ID owns identity; Google Place ID is a verified external reference, not a reason to merge distinct branches. Existing data must survive migration.

Freshness and attribution rules

Keep three dates separate: source publication/observation date, retrieval date and event date. A fourth field, explicit validity end, is useful for promotions. Unknown stays null. Re-reading a 2024 review today does not renew it.

MaterialStored interpretation / future use
Award won in 2023; founding in 1980Historical. Retain year. Corrections possible; do not convert into current award-holder or present-day reputation.
Dish/menu/chef/current operating practiceChangeable. Show source date and “may need reconfirmation before current use.” No automatic fixed 30/90-day expiry policy in this release.

Conflicting sourcesKeep both assertions and flag conflict. Operator resolves/annotates; no newest-wins rule.

Manual form guidance: one concrete assertion; name the dish/person/detail; select topic/category; identify source or personal observation; supply known dates and branch scope. “Excellent hidden gem” is an editorial opinion, better entered as a possible angle with supporting findings.

Deduplication in this slice: exact normalized text + profile + scope + topics can reuse the existing assertion and attach new provenance. Preserve separate evidence dates. Similar paraphrases may remain; do not pay for semantic deduplication or drop distinct claims using coarse word hashes. Manual edits and accepted findings are never silently replaced.

Reuse, refresh and failure rules

  • Opening any saved profile costs zero AI calls. Show prior topics across lists; filter to the current topic by default.
  • Initial request with an existing successful identical input snapshot returns saved output. Refresh is a separately labeled explicit action.
  • Input snapshot includes identity, article topic/standard, source links, prompt version and relevant existing finding versions. Idempotency key protects transport retries even when later profile state changes.
  • A new article topic is a new scope. Research only that topic; append findings to the same profile. Do not replace its wings evidence when researching cocktails.
  • Gap action requires a human question and makes exactly one scoped call, showing prior findings to avoid repeating work. No automatic chain.
  • If a new warning appears after a request starts, save the valid completed research under its original snapshot, but mark current readiness stale. Never erase paid findings or auto-approve the changed card.
  • If candidate is removed during research, finish saving to its profile but do not restore it to the board. Preserve a path through run history to its research.
  • Provider response with no findings is completed_empty; inaccessible sources are recorded, not converted into a negative verdict on the venue.
  • Provider failure, malformed output and process interruption have different reason codes. All preserve existing findings. Retry never occurs on reload or page mount.

Definition of done

An operator can reopen the existing wings run, prepare one retained card, explicitly start one research call, navigate away and back, see the saved findings, edit/add them manually and reuse the profile in another list. Failed calls remain visible and never erase prior work. No blurb is generated.

The implementing agent should report files changed, migration verification, tests run, UI walkthrough evidence, and any remaining provider-access limitations. Do not claim research quality is proven until real source-backed pilot output has been read. Do not run paid pilot calls solely because this document describes them; obtain the user’s scope for those calls.

Recommended decisions fixed for this implementation

  • Per-card trigger, no whole-list prerequisite.
  • All required prep resolved; optional sources remain optional.
  • Explicit button, never automatic research on checklist completion.
  • One grounded call per action; review sources included by default.
  • Shared categories + specific finding rows + optional manual angle ideas.
  • Historical versus changeable data, with honest dates; no arbitrary automatic expiry windows yet.
  • Results viewer and manual editing ship with the trigger, not later.

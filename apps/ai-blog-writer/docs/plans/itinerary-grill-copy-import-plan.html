1. Outcome and scope

One day moves from an approved layout to an agreed direction, then to a portable prompt, then to a reviewed day returned as JSON. The operator conducts the Grill inside AI Blog Writer, copies the research/writing prompt to an external high-tier AI tool, pastes its response, checks a preview, and explicitly saves the result to that day.

Planning assumption awaiting confirmation: Grill and structured direction extraction use in-app model calls. Research and final day writing use the external copy/paste workflow only. No internal research, routing, venue search, or automated evidence verification is included. If Grill must also happen externally, replace only the interview adapter; keep the remaining contracts and import flow.

Settled from this conversation

  • The dry run demonstrated the intended overall flow. Improve its safeguards without replacing that flow.
  • Work day by day, with the full trip’s context available.
  • Grill may propose changes to the skeleton; the operator agrees before those changes take effect.
  • The external model returns organized data and reader copy together. The app renders the returned day.
  • “Easy” describes effort and rhythm. It does not automatically mean fewer stops. This phase preserves the selected slot count; a lower-count day requires an explicit layout decision.

Boundary

This plan covers setup handoff, day interviews, prompt export, pasted JSON, validation, review, saved day results, and context for later days. Publishing to Questura, Payload identity matching, bookings, media selection, automatic source fetching, and rewriting the existing template catalogue are separate work. The delivered result lives in this itinerary workspace; it is not automatically a Payload article.

3. Operator journey, end to end

  1. Choose a day. Show inherited trip facts, current layout, preparation notes, and other-day summaries. Save any pending notes before starting. If layout approval is stale, return to its existing review screen.
  2. Start Grill. Capture the exact context. On first use, save the setup into a backend itinerary workspace. Show the first question and prefilled recommendation. Start and Answer are the actions that can spend model tokens.
  3. Discuss consequential gaps. Each answer advances one decision. Existing selections count as context. The operator can correct recommendations or introduce information freely.
  4. Review day direction. Model agreement is a candidate. Extract structured direction and show that exact object in readable form: purpose, geography, slot roles, rhythm, constraints, research checks and later-day implications. “Agree and prepare prompt” accepts the displayed revision.
  5. Copy research prompt. Show its purpose, the agreed day and export revision. Copy the complete packet; also offer select-all/download when clipboard access fails. Copy is free and does not initiate research.
  6. Use external AI. Operator chooses the high-tier research-capable tool, submits the prompt, and returns complete JSON. The app cannot know when that external work started or finished.
  7. Paste and preview. Paste JSON or upload a JSON text file. Validate deterministically on the server. Show the proposed day, missing/unresolved stops, blocking errors, warnings and changes versus the currently saved day.
  8. Save day result. Operator explicitly applies a structurally valid, current preview. A valid but incomplete result can be saved as “Needs work.” It does not count as a complete day. Saving an updated result preserves earlier import history.
  9. Continue or refine. Read the saved day, inspect evidence, return to Grill for changed intent, or copy a repair prompt for factual/format issues. Move to Day 2 with approved intent and accepted Day 1 content available.

End state: a saved, renderable day with source references and visible review status. Saving it does not verify claims, book tables, publish an article, or spend research tokens.

4. Grill behavior and completion

Input supplied on every turn

  • Trip title, city, dates/weekday/evergreen mode, base, preferences and getaway context.
  • Active day id, position, label, time window, layout, slot ids/kinds/categories/purposes/cues/exclusions, setup notes and preparation notes.
  • Other days’ tentative labels/layouts and accepted results, clearly distinguished.
  • Complete transcript: question, recommendation, pushback, actual answer and whether it matched the recommendation.
  • Decisions already settled, unsupported factual premises, and outstanding decisions.

Eight completion areas

AreaWhat “settled” means
PurposeDay’s promise and contribution to this trip.
GeographyAcceptable area/progression, start/end assumptions and transfer tolerance.
AnchorsWhich experience drives selection; “no single anchor” is valid.
Slot intentEvery slot has its role, required criteria, preferences and exclusions. Free time and travel have planning requirements rather than venue searches.
RhythmEffort, meal balance, rest and optionality. Count and intensity remain separate.
ContinuityWhat other days cover or tentatively reserve; meaningful overlaps are explained.
Change policyWhat must remain and what may be proposed if research cannot fill a slot.
Failure and unknownsWhat makes this day wrong; which factual questions research must answer.

Completion is coverage, not a fixed turn count. Six turns in the experiment are an example, not a quota. Explicit setup facts and accepted planning choices can cover decisions; accepted model suggestions never become independent factual evidence or firsthand experience. Blank dietary/access fields remain unspecified.

Question policy

Ask one decision at a time, choosing the one that most changes the rest of the day. Offer a concrete recommendation and its tradeoff. Do not repeatedly ask for information already entered. Do not invent a venue fact to make a recommendation sound researched. With no lookup capability, factual unknowns go into the research checklist; the Grill can still decide preferences.

Agreement extraction

Use a dedicated structured extraction job over the snapshot and full conversation. A proposed itinerary.day_direction job creates a candidate that passes schema and slot-reference checks. Show the candidate before acceptance. The accepted artifact is immutable and versioned. Extraction failure leaves the conversation intact and offers retry; approval never silently accepts a different unseen extraction.

Layout changes during Grill

Grill emits an explicit proposal, not a reducer action. Operator reviews the before/after layout using existing validation. New stops receive new ids; retained stops keep theirs. Apply the layout change and reapprove it, then continue the transcript against the new context. Retain the explanation and supersede any previous direction/export. No hidden stop removal or count reduction.

5. State model and invalidation

Store durable artifacts and attempts; derive visible state from them. Keep layout approval, interview agreement, import validity and editorial completeness distinct.

What makes work stale?

  • Changes to trip planning values, active-day layout, time, meaningful notes or accepted direction invalidate dependent exports and current import eligibility.
  • Changing a tab, opening a stop, saving unchanged text or updating a timestamp does not invalidate anything.
  • Reordering days retains identity but changes trip role/date/continuity context; affected work needs review.
  • Changing another day’s accepted result changes continuity context. Flag dependent directions and results; never rewrite them automatically.
  • Day removal preserves its work in history, excluded from the active trip. A newly added day does not inherit an old day’s id.
  • Voice/prompt/schema releases do not retroactively corrupt a valid outstanding export. Keep the versions it was made with; new exports use new versions. Revoke an old contract only explicitly.

No silent “rebase”: a result from an old export cannot be made current by editing its id. Re-export the new context, optionally attaching the old result as revision material. For unchanged intent affected only by another day, an explicit context review can create a new direction revision without starting the interview over.

6. Persistence and ownership

Recommended architecture: local setup remains available until the first Start Grill. Then create a backend itinerary workspace containing the complete setup snapshot. After successful creation, the backend becomes canonical for that workspace, including subsequent trip/layout edits. The browser stores its workspace pointer and temporary editing state, not a second authoritative result.

  1. Flush pending local edits. Send draftId, staff identity from auth, setup and an idempotency key.
  2. Server validates setup and creates the workspace once. Verify frontend approval signatures using the same documented canonical rules or shared fixtures; do not trust an arbitrary approval boolean.
  3. Return workspace id, full persisted setup and revision. Only then mark the local draft as linked. Preserve a recovery copy until the handoff is known to have succeeded.
  4. On reload, resolve the linked workspace. Network failure shows a retry/read-only state, never “empty draft” and never starts another paid call.
  5. All subsequent edits use expected workspace revision. Stale updates return a conflict with current revision; do not overwrite another tab’s changes.

Use the existing backend SQLite database/transaction conventions, with feature-owned tables and explicit schema initialization/migration consistent with the repository. No Payload schema change is needed. New endpoints use existing staff authentication and enforce owner access on every read/write; client-supplied workspace ids are not authorization.

Keep the current setup schema readable. Introduce workspace linkage without deleting browser drafts or silently resetting a version mismatch. This preservation concerns the current itinerary setup and does not restore deprecated Prompt2Blog v2/v3 behavior.

7. Production contracts: evolve the dry run

The dry-run schema proved rendering, but its fixed ids, exactly six rows and place-only assumptions cannot be production contracts. Define strict backend Pydantic models as the authoritative schema; export JSON Schema from them and maintain TypeScript mirrors with contract fixtures.

Three separate artifacts

  • DayDirection: agreed intent and executable selection criteria. Not the old free-text Generation Brief, not a Writer Brief, not an Article Brief. Preserve these distinctions in CONTEXT.md during implementation.
  • DayPromptExport: immutable transport envelope plus input snapshot and exact prompt.
  • DayResult: externally returned research, proposed schedule, reader copy, evidence references and review concerns.

  "workspaceId": "...",
  "dayId": "...",
  "exportId": "...",

Shape above is explanatory, not a valid response example. Implementation must export the full generated schema, typed alternatives and exact current ids into each prompt.

Typed stop outcomes

KindSelected/planned resultIncomplete result
placeReal name, branch/location, category, what to do, reader copy, evidence links.Unresolved reason; no invented venue.
experienceConcrete route, activity or meeting point; provider only if applicable; category and evidence.Missing duration, operating conditions or location remains explicit.

Use a discriminated union for result status: selected/planned, unresolved, or omitted_optional. Optional omission is legal only for an exported optional slot. Every exported slot appears once, in the agreed order; extra slots arrive as proposals. Slot categories must stay within allowed categories; preferred categories remain preferences.

Schedule designed for deterministic checking

Use integer minutes from the day’s reference midnight plus explicit day offset for overnight work; avoid parsing free-text “around eight.” Store durations and transfer ranges separately from proposed start times. Identify each schedule segment and its endpoints. Rest has an explicit location policy: remain nearby, named location, base, or unknown. A hotel return creates two legs. Rest added around existing slots must not duplicate an existing free-time slot. Unknown timing is nullable and yields an incomplete feasibility result, not zero minutes.

Evidence semantics

Sources have ids, real HTTP(S) URLs, titles and supplied retrieval/publication dates. Claims reference source ids and specific stop ids/fields where possible. Structured linkage proves only that references connect; it does not prove the page supports the assertion. Store external browsingUsed and “ready” judgments as reported metadata, never app verification.

8. Prompt assembly and external boundary

Build the prompt deterministically from accepted direction and saved context. No model call is needed to write or copy it. Save exactly what the operator received.

  1. Task and boundaries: research and compose one day; no bookings, purchases or publication.
  2. Exact identity envelope: workspace/day/export ids, input hash and contract version to echo unchanged.
  3. Trip and day snapshot: full slot semantics, approved constraints, preparation notes and usable time.
  4. Accepted direction: the accepted structured artifact, not a lossy paraphrase.
  5. Continuity context: used venues/experiences, tentative later-day allocation and legitimate overlap notes.
  6. Research/writing instructions: real branch identity; compatible opening days; route/effort reasoning; factual claims separated from estimates; unresolved outcomes allowed.
  7. Canonical voice: load the existing Questurian voice and writing conventions at export time. Store their version/hash in the export. Do not maintain a new voice copy as source code.
  8. Full generated response schema: dynamic slot ids and kind constraints plus JSON-only instructions.

Improvements exposed by the sample

  • Ask the model to consider the combined day, not six individually attractive places.
  • Do not equate short walking with taxi on every leg. Evaluate feasible walking before proposing taxis; report unknown routing honestly.
  • No availability claim from opening hours. “Open at 18:30” does not imply an available table.
  • Delivery menu evidence cannot silently support dine-in recommendations at a specific branch.
  • Rest needs location/transfer accounting. A 165-minute hole is allowed as a preference, not automatically proof of a relaxed or coherent day.
  • Separate effort, number of stops and available time. A full time window need not be filled with more venues.
  • Repetition warnings explain the overlap. They do not ban neighborhoods or foods across the rest of the trip.

Repair prompt: generate a free, deterministic follow-up containing the original export envelope, unchanged requirements, returned packet and validation/review issues. Request a complete replacement JSON object. Invalid content remains quoted as data, never new instructions. If intent changed, create a fresh export rather than repairing against obsolete requirements.

Show app usage only for the Grill/extraction calls. External research cost, model identity and browsing claims are unknown unless supplied; never display them as measured usage or “free research.”

Valid is not complete; complete is not verified

Allow structurally valid incomplete packets to be saved. Derive three separate indicators: Import validity (deterministic), Planning completeness (required outcomes and outstanding decisions), and Evidence review (unchecked/reviewed by operator). Do not copy the model’s top-level status into the app badge.

Atomic apply

Preview returns the normalized packet hash, validation report, current workspace/result revision and a preview token or equivalent signed reference. Apply sends that identity plus an idempotency key. Server reparses and rechecks current state inside the transaction. A changed paste invalidates the preview; a changed workspace returns 409 and asks for a new preview. Duplicate identical apply returns the existing result; a reused key with different content is a conflict. Cancel changes nothing.

Safe rendering

Render through React text nodes or the app’s supported safe Markdown renderer; never raw HTML from JSON. External links permit HTTP(S) only, with safe new-tab attributes. No automatic fetching of pasted URLs. Keep large raw JSON collapsed. Evidence and review language remain separate from reader prose.

10. Day-to-day continuity

Build continuity input from saved trip state, not solely from the external model’s suggested memory. Identify each day’s source revision. Clearly label tentative direction, accepted direction, accepted incomplete result and complete result.

  • Derive used venues from accepted selected stops. Identity uses known ids where available, otherwise normalized name/address for a warning only; name similarity is not proof of the same branch.
  • Carry experience descriptions and day purpose as editorial context. Suggested memory is advisory and cannot create mandatory bans without agreement.
  • Carry late finishes, demanding travel and known next-day constraints. Do not assume Day 2 has full energy after an unspecified late night.
  • Include future skeletons in Day 1. They reserve intent, not nonexistent bookings or guaranteed venues.
  • A partial day can inform the next Grill, labeled partial; no requirement to finish the entire prior day before discussing the next.

Change example: Day 1 originally has coastal scenery; Day 3 is assigned art. Revising Day 1 to a substantial art visit marks Day 3’s accepted direction as needing continuity review. Its old transcript/result remain intact. Operator either confirms the contrast still works or reopens its Grill. No silent re-generation or cascade of paid calls.

12. Model calls, retries and failures

  • Register proposed itinerary.grill and itinerary.day_direction jobs through existing model gateway configuration. Default to the operator’s intended high-tier stack; record requested and actual model. Do not change shared jobs’ defaults.
  • Keep the repository’s shared output-token floor. A small turn-size hint is not a hard generation cap.
  • Shared-engine change adds explicit seed_research_enabled and mid_turn_lookup_enabled capability controls, with current defaults preserved for existing pipelines. Itinerary sets both false. A lookup request cannot invoke research even if the model ignores its prompt.
  • Retain the shared engine’s one retry for unusable/repeated turns, recording both attempts. Do not stack another outer retry that doubles calls unnoticed.
  • Reserve a day attempt before dispatch. Duplicate Start/Answer requests with the same key return its status/result. A different pending mutation for that day returns a conflict.
  • Persist the submitted answer and its question identity before model execution; store whether advancement completed. If a call fails, resume from the recorded answer rather than appending it twice.
  • Do not hold a database transaction open during a provider call. Finalize against the original revision. If setup changed while the call ran, preserve its result as obsolete attempt output; do not promote it into the current day.
  • A timeout or process crash can leave provider completion unknown. Mark interrupted and expose retry as a new attempt. Never claim exactly-once provider billing across uncertain failures.
  • Switching days does not cancel or relabel an already dispatched call. UI only applies its response to the originating workspace/day/revision. Reload reads persisted work and never replays Start automatically.
  • Clipboard error shows selectable text. Paste failure preserves text. Apply conflict preserves both the saved result and the incoming preview for comparison.

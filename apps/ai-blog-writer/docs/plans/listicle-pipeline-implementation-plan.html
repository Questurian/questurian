01 / What the second check established

Failures verified. Scope corrected.

Reproductions import actual listicle contracts, service, runner, pooling, review and storage modules. Storage uses the real SQLite connection helper against a disposable database. Research calls return controlled fixture text. The external interview engine is stubbed at its boundary; its decision-making remains out of scope.

No existing test suite was used as evidence. No web searches were purchased. The probes establish what code does for concrete inputs; they do not establish which hotels, bars or restaurants are good.

Confirmed mechanisms

  • Old order retained after new agreement.
  • Failed refresh overwrites successful attempt.
  • Both simultaneous batch claims succeed.
  • Name containment silently merges distinct venues.
  • One branch’s cut flag applies to both branches.
  • Changed evidence retains old checked status.
  • Candidate 121 is omitted from a “checked” pool.
  • Accented and compound kinds get wrong catalogue.
  • Different Place IDs resolve to one profile.
  • One search copied across revisions becomes three in history.

Corrections to the first brief

  • Re-agreement is a backend/API defect. Current frontend hook has no interview-reopen action. Direct count/requirement edits use a different path and do create revisions.
  • Some identity protection already works. Explicit lobby/rooftop qualifiers stay separate. Preserve it. The reproduced defect is containment of distinct names.
  • “No middle coverage” is a design concern. We did not establish a real missing venue or recall loss.
  • Catalogue word counts are words, not billed tokens. Actual savings need usage observations.
  • Profiles are optional. Their identity bug does not currently corrupt search pooling.
  • No claim of zero-risk prompt changes. Even redundant instructions can influence a model.

Evidence: machine-readable observations · reproducible offline probes · numbered source excerpts. Synthetic venue names demonstrate identity failures; they are not claims about real businesses.

02 / Recommended design

Three identities. One honest current view.

Order revisionWhat operator approved. Immutable once saved.
Search attemptOne invocation and its result. Reuse references it.
Candidate snapshotWhich sightings were pooled, under which pooling rules.
Review snapshotWhich candidate evidence was checked against which cut.

These are local records, not new services or article stages. Keep existing search prompts, operator selection, role allowances and advisory flags while fixing their bookkeeping.

RecordProposed identity / fieldsInvariant

Request fingerprint: canonical serialized fields actually sent: kind, place, standard, exclusions, angle text, role, wanted, and search-prompt version. Preserve existing explicit-refresh policy; a matching fingerprint is not a promise of current opening hours. Do not invalidate solely because revision changed. Keep raw approved wording untouched.

Display policy: current order + current matching selected results + latest attempt state. A failed refresh reads “refresh failed; showing earlier result from [time].” A successful empty refresh becomes current with zero candidates; earlier success remains in history, never silently substituted.

03 / Failure → solution → acceptance

Implementation decisions for every finding.

R1Re-agreement keeps the old orderConfirmed · API path · Batch B
Observed: new transcript resolves to 20; stored order remains 40. Probe calls actual service.answer with a valid changed agreement returned by the engine stub.
service.py:127 returns existing order unconditionally.

Fix

Separate read_order, initial agreement creation, and explicit re-agreement. GET reads must never regenerate an existing order. At each agreement, save the resolved interview values alongside the order as its interview baseline. On a later agreement, compare new resolved values with that baseline:

  • Unchanged interview field → preserve current order value, including direct operator corrections.
  • Changed interview field → latest explicit interview answer wins; record a short note if it replaces a direct correction.
  • No effective change → keep revision; no fresh conflict call.
  • Effective change → atomically insert next revision, update baseline, recompute allowances, invalidate only affected result references and cut checks.

On first reopen of an existing order, capture the current resolved interview baseline before invoking engine. Keep angle IDs for unchanged approved selections; new angles get new IDs. Do not use fuzzy text similarity to silently identify an edited angle as an unrelated previous one.

Use expected revision in mutation requests. A stale browser mutation receives 409 with current revision; it cannot overwrite intervening corrections. All revision allocation/insertion happens in one short write transaction, with no LLM call inside it.

Acceptance

40 → re-agree 20 produces revision 2/count 20; GET retains it. Directly corrected cut survives a count-only re-agreement. Explicit later cut change supersedes it with a visible note. Duplicate agreement saves no extra revision. Concurrent corrections cannot share a revision.

Touches: service.py, spec.py, store.py, contracts.py, api.py; frontend expected-revision request handling. No change to grill_v4.py or its stop condition.

R2Refresh destroys successful workConfirmed · Search path · Batch A
Observed: two candidates before refresh; zero after injected timeout; one stored attempt remains, with no successful attempt.
runner.py:150 + store.py:258 overwrite the same row.

Fix

Create a unique attempt ID for each run_one_angle invocation. Save running state before the call; finalize only that ID. Keep terminal attempts and their original sightings. A per-order-angle selection points to the successful result currently displayed, independently of latest attempt status.

Default reuse scans all matching successful attempts, not just latest attempt per angle. Reuse across revisions writes a reference, never a copied execution. Failed or interrupted refresh leaves earlier matching success selected and visibly old. A completed zero-row response is a real new result, so select it and retain history.

Keep existing bounded provider retry behavior initially, but record each provider call within the invocation’s receipt. One invocation is not necessarily one billable call. Lost responses remain interrupted/uncertain; this does not promise exactly-once provider charging.

Acceptance

Success → timeout retains both attempts and earlier candidates; UI shows failure plus prior gathered time. Success → completed empty result shows zero, with old attempt retrievable. Revision A → B → A can reuse matching A. Role/prompt-version change prevents incorrect reuse.

Touches: contracts.py, store.py, runner.py, service.py, search.py; frontend types.ts and SearchResults.tsx. Use a dedicated history record, not a second unlabelled result blob.

R3Two callers can own one batchConfirmed · Paid duplication · Batch A
Observed: forced legal interleaving of two real SQLite connections → [true, true] from claim_batch.
store.py:373 reads before acquiring a write lock; line 387 upserts instead of refusing the second owner.

Fix

Use existing app.core.database.transaction() (BEGIN IMMEDIATE) for claim read/check/write. Return a random owner token. Renew lease while batch runs; keep the existing 30-minute expiry initially and renew every 30 seconds, including during blocking provider calls. This is one in-process heartbeat, not a new service.

Check owner token before dispatch and in the transaction that commits results. Release with DELETE ... WHERE run_id=? AND owner_token=?. Hold batch ownership through result selection and review persistence; current release happens before review. Always stop heartbeat in finally.

Do not keep SQLite write transaction open during network work. While lease is held, order mutation/reopen gets an actionable conflict rather than racing the batch. A process that loses lease stops dispatching and cannot replace successor’s selected results. A response already purchased may be archived as orphaned evidence, not promoted to current work.

Acceptance

Two simultaneous starts → one provider dispatch sequence, one conflict. Long batch renews beyond original expiry. After takeover, old owner cannot release new lease or publish current results. Crash recovery permits retry after expiry without claiming previous provider call was free.

Touches: store.py, service.py, runner.py; existing database transaction helper. Also protect revision mutations with expected revision and lease checks.

R4Name containment is mistaken for identityConfirmed · Candidate loss · Batch C
Observed: Hotel Sol / Centro + Hotel Sol Palace / Centro → one Palace candidate, two sightings, no warning.
search.py:470 uses token subset matching as a merge rule.

Fix

Make containment a possible-duplicate relation, never sufficient for automatic merging. Keep display name and raw sighting untouched. Separate exact observation grouping from fuzzy candidate suggestions:

  • Exact observation grouping uses Unicode-normalized full name, explicit district, and branch/room qualifiers. Do not strip years, articles or business words as identity proof.
  • Missing district, unqualified hotel name versus named hotel bar, conflicting district, or different branch qualifier → retain separate candidates and attach possible-duplicate IDs.
  • Similarity/containment may add hints only. Verified external identity or an explicit operator decision can justify stronger merging later; do not add paid Places lookups to every candidate.

Generate snapshot candidate IDs from sorted member sighting IDs and pooling version. Display names may match; IDs must not. Preserve every sighting, and show count as provisional where identities remain unresolved. Exact observation grouping is still provisional, not proof two sources named the same real venue.

Acceptance

Hotel Sol/Palace remain two candidates with reciprocal hints. Lobby/rooftop stays separate. Unknown district cannot bridge two known branches. Reordering sightings produces same groups and IDs. Every input sighting appears exactly once in output membership.

Touches: search.py, runner.py, contracts.py; frontend candidate keys and duplicate links. More visible duplicates is an accepted tradeoff; silent loss is not.

R5One branch’s cut flag reaches anotherConfirmed · Wrong exclusion flag · Batch D
Observed: reviewer flags only row 1 (Azul, Centro, inside hotel). Both Azul branches receive same clear flag.
cut_review.py:344 stores by name; runner.py:494 reads by name.

Fix

Keep numbered rows in model prompt for low output overhead. Maintain exact row number → candidate_id map for that review request. Validate number and existing name cross-check, then persist verdict by candidate ID. Never use name as storage key.

Multiple verdicts for the same ID may combine reasons. Same-name different IDs never share flags. React keys, duplicate references, and rendered verdict lookup all use candidate IDs. Reject out-of-range or mismatched findings as review-validation errors; do not silently declare complete when a returned finding was discarded.

Acceptance

Only Centro branch flagged. Row order changes preserve correct mapping. Duplicate names remain distinct. Invalid reviewer row number/name mismatch cannot produce a falsely complete clean review.

Touches: cut_review.py, runner.py, store.py; frontend types.ts/SearchResults.tsx. Retain advisory wording for both confidence levels.

R6Changed evidence keeps an old reviewConfirmed · False checked status · Batch D
Observed: Old Venue reviewed; refresh returns New Venue; review throws. New Venue pool says cut_checked=true, zero barred.
service.py:328 returns without invalidating old record; runner.py:431 loads by revision alone.

Fix

Bind review to canonical review material: kind, place, exclusions, ordered candidate IDs, names/districts, evidence, duplicate context, pooling version, reviewer prompt/schema version and resolved reviewer model. Store full/partial/failed status, not just a flags dictionary.

At assembly, only a matching, complete review may set checked=true. Historical review remains stored but does not apply to changed pool. Persist review under fingerprint of the snapshot actually sent, even if a newer snapshot exists by completion. Batch ownership check controls whether it can become current.

Cache complete matching review on reuse-only POST; no new call. A GET can look up cache but never invoke model. Semantic exclusions like “none” remain a separate prompt behavior; blank exclusions are the deterministic no-review-needed case.

Acceptance

Changed pool + failed review → unchecked/failed. Identical pool/cut + existing complete review → zero extra reviewer calls. Changed cut, candidate evidence or review version → cache miss. An older response cannot overwrite current review.

Touches: cut_review.py, store.py, runner.py, service.py; frontend checked-status copy. Preserve raw historical review for audit.

R7Only first 120 candidates get reviewedConfirmed · Partial coverage hidden · Batch D
Observed: nine attempts produce 121 candidates under legal count/allowances. Candidate 121 is absent from prompt; assembled pool reports checked.
cut_review.py:148 silently slices candidate input.

Fix

Replace truncation with deterministic chunks and a review manifest. Start with at most 60 candidates per chunk, additionally bounded by estimated input/output budget; this is a safety bound, not an empirically optimal number. A normal 43-candidate pool remains one call. Preserve per-row duplicate hints and identical cut in every chunk; no cross-chunk chain inference.

Store chunk completion and expected candidate IDs. Candidate-level status distinguishes reviewed, unreviewed, flagged. Whole-pool complete requires every expected ID covered by a valid completed chunk. If chunk fails, keep successful chunks and retry only missing chunks on explicit POST. One oversized row must be split/handled explicitly, never silently trimmed into a complete verdict.

Budget is explicit: additional chunks mean additional calls. Before dispatch, compute chunk count; report intended work in batch plan. Never report full coverage simply because a cost cap prevented the last chunk.

Acceptance

121 candidates → all 121 covered, including last row. Middle chunk failure → partial with exact reviewed/total count. Retry buys only missing chunk. Zero exclusions → “no exclusions to check,” with no model call.

Touches: cut_review.py, service.py, store.py, runner.py; frontend types.ts/SearchResults.tsx. Keep search-complete and cut-review-complete separate.

R8Wrong catalogue for accented or compound kindsConfirmed · Search planning · Batch E
Observed: cevicherías → ""; hotels with rooftop bars → bars; hotel bars → bars already correct.
shapes.py:104 uses ASCII matching and fixed bars-first precedence.

Fix

First normalize NFKD/casefold for classification only; preserve approved noun spelling. Resolve primary venue kind before secondary qualifiers: leading noun phrase before “with/featuring/that have…” chooses hotels in “hotels with rooftop bars”; head of “hotel bars” chooses bars. Use narrow phrase rules with explicit examples, not a new giant keyword contest.

Persist catalogue subject separately from literal searchable kind, with resolution source. Single unambiguous match is automatic. Genuine mixed head (“hotels and bars”) remains unresolved until existing kind question settles it; retain shared catalogue rather than guessing. Reuse already-settled subject during later menu generation.

Add listicle metadata field rather than changing shared interview engine. Existing records can compute subject locally on read without spending; unresolved classification must stay labelled unknown, not silently converted.

Acceptance

Accented Spanish names match unaccented aliases. “Hotels with bars” → hotels; “hotel bars” → bars; “restaurants with cocktail bars” → restaurants; “hotels and bars” → unresolved. Operator-selected primary kind beats helper inference.

Touches: shapes.py, spec.py, contracts.py, service.py, prompts.py; API order metadata. Classifier tests prove routing only, never search quality.

R9Distinct Place IDs share a profileConfirmed · Optional path · Batch G
Observed: open Azul/Place-A, then Azul/Place-B in another district → same profile; second call returns Place-A.
profile_store.py:168 falls through to provisional name; line 245 accepts it.

Fix

When strong ID is supplied, exact Place ID wins. Never return an already-anchored profile with a different ID. A provisional profile can be promoted only when its full branch-aware identity matches uniquely and no conflicting anchor exists. Otherwise create distinct anchored profile.

Replace global unique name/city provisional index with a partial unique index for unresolved profiles, using full normalized name, city and district/qualifier. Resolved profiles are uniquely identified by Place ID and may share names. Name-only lookup with multiple anchored matches returns explicit ambiguity rather than arbitrary first row. Pass district into resolver query when available; do not treat top search hit as validated branch identity.

Existing contaminated profile claims cannot be separated reliably by guessing. Preserve them, flag conflicting identities, and audit affected rows before moving any claim. Do not wire profile generation into candidate discovery.

A/B remain separate; same ID under renamed business reuses profile; unique provisional profile promotes safely; ambiguous name lookup refuses silent choice. Existing claims and sightings survive schema migration.

Touches: profile_store.py, profiles.py, service.build_profile and identity.resolve query. Optional branch of plan; not prerequisite for pure discovery comparison.

05 / Keep the useful structure, test the uncertain parts

Bars transfer. Hotels need their own examples.

Retain shapes, roles, literal approved wording, shared standard/cut, custom options and advisory overlap. No shape should be promoted or removed solely because a synthetic probe passed.

Concrete catalogue repairs

  • Family: one family operates it. Example: “family-run cevicherias in Lima.” Remove mandatory generations; old age belongs to institution.
  • District: “hotels in Barranco” / “bars in Pueblo Libre.” Remove “visitors miss”; lesser-known already owns that condition.
  • Examples must match core. Inspect every core/instruction/example trio; eliminate added fame, time windows, room counts or ratings absent from core. Distinguish deliberate core requirements from volunteered extras.
  • Search source guidance: hotels → local accommodation/travel reporting, hotel listings and review sites; bars/restaurants → local food/drink reporting. Always preserve local-language searching and exact local business names.
  • No menu rewrites after approval. Catalogue changes apply to newly generated options; stored operator wording remains authoritative.

Family source · District source · Shared source guidance

Hotel/bar improvements to evaluate

  • Hotels: keep lodging format, long stay, building character, families, transport. Give shared setting/price/institution shapes hotel-specific examples.
  • Origin and signature-item: recommend restricting restaurant/drink meanings to restaurants/bars; trial hotel equivalents only when they express a searchable lodging feature. Preserve existing selections.
  • Insider: retain where chefs/bartenders go; trial explicit travel-professional lodging recommendations instead of assuming hoteliers’ personal stays are documented.
  • Bars: inspect spread across drinking tradition, beverage, format, music and district. A single jazz angle is one slice, not coverage of all music bars.
  • Broad eligible baseline: trial an operator-selectable route with no extra angle restriction. Compare whether it recovers ordinary mid-priced places. Do not automatically add another paid search.

Evaluation that can actually change a decision

  1. Freeze cases and order first. Use existing eight cases: broad/specialist restaurants; broad/rooftop bars; broad/independent long-stay hotels; sparse location; operator-edited angles. Explicit kind/place/count/standard/cut; never parse city from a trailing title phrase.
  2. Two arms, same opportunity. Corrected current mix versus one proposed change. Same resolved model, location, requirements, execution-call budget and total requested places as closely as role bounds allow; record any mismatch. For broad-baseline experiment, replace one route rather than adding budget.
  3. Repeat and alternate order. Three repetitions per arm per case initially. Alternate execution order to reduce timing bias. Record all attempts, including failed calls and repeats. This is exploratory evidence, not a significance claim.
  4. Judge pooled union blind to arm. Resolve actual venue/branch, confirm published eligibility and angle fit, note current operation with dated source. Classify eligible / ineligible / unknown; unknown is not a pass. Inspect direct source pages, not model evidence sentences alone.
  5. Measure separately. Eligible distinct yield, precision, otherwise-missed eligible venues, coverage of intended dimensions, identity errors, operator edits/effort, source provenance, total cost and latency. Recall is against a separately curated reference set; if none exists, call it relative coverage, not absolute recall.
  6. Adoption rule proposed in advance. Mandatory mechanical invariants: zero lost sightings, wrong-ID flags, stale complete reviews or duplicate lease owners. For token variants: target at least 15% lower median measured token use, no lower eligible-yield median in any case, and no case precision decline above 5 percentage points; inspect all changed exclusions. For coverage variants: gain at least two unique eligible venues in two intended broad cases at same call cap, with no narrowed-case median yield loss. These are proposed practical thresholds, not measured facts or statistical guarantees.

Upgrade comparison script to persist raw responses, per-attempt receipts, explicit place, role/wanted, model and prompt versions, and judge records before buying runs. Existing --max-searches caps angle count; provider retries can multiply actual calls. Enforce experiment cap at each provider dispatch. Produce dry-run manifest with maximum calls and budget first. Paid comparison requires a separate explicit budget authorization; this plan does not run it.

Candidate evidence limitation: preserve angle source metadata and, where existing provider response exposes row-to-source support, carry that mapping. Missing mapping stays unknown. Do not attach an arbitrary angle source to each row. A future richer row format is a separately measured change, not a prerequisite for storage fixes.

07 / Safe implementation handoff

Migration, validation, boundaries.

Storage rollout

  1. Snapshot local SQLite with backup API; record counts of listicle orders, attempts, reviews, profiles, claims and sightings. Do this before migration; never point probe harness at real DB.
  2. Add versioned history/reference/review structures in explicit migration. Keep old rows as migration evidence. Existing listicle records are not deleted and no Prompt2Blog v2/v3 path is restored.
  3. Historical copied attempts lack true execution IDs. Group only byte-equivalent evidence with identical fingerprints and original timestamps where defensible; mark reconstructed origin. Ambiguous cases report unknown execution count instead of fabricated spend history.
  4. Import old name-keyed reviews as historical/untrusted for current candidate-ID coverage. Recheck only on explicit work request. No paid backfill during migration.
  5. Switch reader/writer and UI together. After migration, writes use new structure only. Validate foreign references, terminal immutability, source row counts and no lost sightings.
  6. Test rollback on cloned DB. Keep backup and old tables until rollout proven. Once new attempts exist, prefer forward fix; restoring old DB without exporting new records would lose paid work.

Implementation acceptance

  • Add focused behavioral regressions for these reproductions. They prove state/accounting invariants—not venue quality.
  • Use real temporary SQLite for races and migration; fake model responses for deterministic mechanics.
  • Browser-check refresh failure with retained prior results; same-name branches; partial review and retry; no-op reuse; revision conflict. Verify selected result and latest attempt are visually distinct.
  • GET endpoints never call research/reviewer. No-op order mutation creates no extra revision.
  • Run appropriate backend checks and frontend type/build checks once changes land. Broaden only for affected shared interfaces.
  • Update ADR 0037 and glossary for attempt/reference, candidate snapshot and review coverage. Do not change article-engine semantics.

Scope held

Plan and evidence only now. No application edits, paid calls, deploy, Payload migration, auto-pruning, new article step, new external service, or profile research for every candidate. Future implementation starts with Batch A.

Ready to implement:

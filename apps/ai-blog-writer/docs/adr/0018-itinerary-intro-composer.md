# Itinerary Intro gets a dedicated plan-signal composer, separate from the blurb batch

The itinerary **Intro** (`header.introMarkdown`) was generated as a second-class passenger inside the *blurb* pipeline: `buildIntroTarget` added an `intro` target to the same `buildItineraryGenerateListicleContentRequest` batch as every stop, flowed through `_generate_single_listicle_target`, and was gated by machinery built for blurbs (Critical Fields; Research Profile is explicitly blurb-only). Because that batch shares one **frozen** `article_context` (computed once at `routes.py:1061`, never updated between targets), the Intro only ever saw `Selected stops: <titles>` — the richest signal the autobuild already produces (`planOverview`, per-stop `selectionReason`) went unused, and the "Why this pick → seeds the blurb" promise in the UI was fiction.

We decided to **rebuild the Intro generator from scratch as its own editor-assist node** — a third sibling to `generate_title` and `compose_itinerary_brief`, each of which already has its own graph runner (`graph/runner.py`). The new composer reads plan signal directly: **`planOverview` as the narrative spine, per-stop `selectionReason`s as summarized texture (never enumerated), and title + location + `listTone` as framing constraints**, transforming internal rationale into reader-facing prose rather than echoing it. The intro-in-blurb-batch path (`buildIntroTarget`, the `intro` target, its reliance on `_generate_listicle_content_impl`) is retired. Output boundary is **intro prose only** — the headline stays an input from the existing Title writer. The storage field (`header.introMarkdown`) and the `BuilderHeaderPanel` "Auto Write / Regenerate" surface are unchanged.

## Considered Options

- **Enrich `buildIntroTarget` in place** — feed `planOverview`/`selectionReason` into the existing intro target's `supportingContext`. Smallest change, but keeps the Intro shackled to a batch whose shape (frozen context, blurb-only gating) is wrong for trip-level prose; the distortion compounds with every future intro change.
- **Full sequenced "unity" loop now** — generate the Intro first, then make `article_context` *accumulate* mid-batch so blurbs read the fresh Intro. Maximally coherent, but a real backend change to the per-target loop and out of scope for the first pass; deferred.
- **Subsume the headline too** — one system owns headline + intro. Rejected for this iteration: larger teardown (would retire `generate_title` for itineraries) and the title is often operator-decided before autobuild.

## Consequences

- **Current stops are the ground truth** the Intro is always written against (the live `draft.days` stop list — titles, categories, order — is always accurate). `planOverview` is a **non-gated soft hint**: a slightly stale overview self-corrects because the writer also sees the real stops. No recompute, no freshness gate.
- **Orphaned `selectionReason` is fixed in the same change.** `selectionReason` was sticky — it survived pick-swaps (`BuilderStopsPanel.tsx:1452`) and block-type resets (`:274`), so a stale reason could describe a stop no longer present. We clear it on both, making the rule reliable: *a `selectionReason` that exists describes the current pick*. The composer uses reasons that are present and tolerates absent ones (manual or post-swap stops).
- **Degrades without autobuild.** Gated on title + ≥1 stop with a resolved identity, not on autobuild having run. With no `planOverview`/reasons (hand-built itinerary), it falls back to stops + categories + order + day structure + title + location + tone — still richer than the old "titles only".
- **No staleness-warning UI** this iteration; a "stops changed since autobuild — regenerate?" nudge is a clean follow-up.
- Output: markdown into `header.introMarkdown` (clearing `introJsonText` so the Lexical editor re-derives), 1–3 short paragraphs, no headings, length/register driven by `listTone`, single intro (no variants) for v1.

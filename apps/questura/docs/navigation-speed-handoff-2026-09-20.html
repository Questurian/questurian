Implementation handoff · 2026-09-20

The click freeze is a local-development artifact. Do not fix it with loaders.

A click on localhost can sit frozen for four seconds. The same click against a production build of the same commit takes 30 milliseconds. This document records what was measured, what is genuinely worth changing, and — importantly — what must not be built.

Written after PRs #599–#602. All measurements taken on the Mac, 2026-09-20, against main at 99a4fb2e, backend on localhost:4000 with the local Postgres.

Read this before writing any code. The owner explicitly rejected full-screen loading skeletons, and he is right to. Section 4 explains why adding loading.tsx across the public routes would make the site feel worse, not better. Two tasks in section 5 are worth doing; one of them is the only one with a real SEO argument.

1 · The symptom, as reported

Clicking a link on localhost:3000 leaves the old page on screen, apparently frozen, for a noticeable beat — sometimes several seconds — and then the new page appears all at once. There is no spinner, no skeleton, no visual acknowledgement that the click registered. It is worst on a page type the session has not opened before.

The owner's two questions were: is this only local? and could it hurt SEO by making Google's crawler wait? The answers are yes, almost entirely local and a little, on one route family only.

3 · Why dev and production differ so much

Two mechanisms stack on localhost, and neither survives a deploy.

  1. On-demand compilation. next dev builds a route's code the first time that route is requested — once per route pattern, not per URL. Measured directly with RSC: 1 requests: cold 0.3–4.2 s, warm 40–120 ms. Restarting pnpm dev resets every route to cold, which is why it feels worst right after a restart.
  2. Link prefetching is off in development. This is documented Next behaviour rather than something isolated here, but the production numbers are consistent with it: a link that had been sitting in the viewport resolved in 30 ms, while the same kind of link clicked the instant it scrolled into view took 828 ms. In production, next/link warms the destination before the click; in dev it does not.

The codebase is already set up to benefit from this. 42 files import next/link, there are no raw internal <a href="/…"> anchors, and prefetch is disabled in exactly one place (features/Payments/components/PricingDisplay.tsx:87, deliberately). Nothing needs changing here.

4 · Why loading.tsx everywhere is the wrong fix

An earlier draft of this advice suggested adding loading.tsx to the public routes so a click paints immediately. The production measurements do not support that, and it should not be built.

  • The interval a loader would fill is 30–58 ms in production. A skeleton that appears and disappears inside 50 ms reads as a flash of noise, not as responsiveness. The owner's objection — that it would add a visible jitter to something already instant — is the correct read.
  • The only case where a loader would be on screen long enough to be useful is the 828 ms cold-URL click, and that case has a better fix (task A below) that removes the wait entirely rather than decorating it.
  • One loading.tsx already exists, at (public)/[country]/[city]/itineraries/[slug]/loading.tsx, added 2026-07-20. Leave it. Do not use it as a precedent to add more.

If a future measurement on real hosting shows navigations consistently above ~300 ms, revisit this — but measure first, on the real platform, and prefer making the page fast over covering the wait.

5 · The work worth doing

Task APre-build the public URLs with generateStaticParams

Why. Every public route is marked ○ (Static) in the build output, but not one of the 19 page files calls generateStaticParams. So no concrete URL exists at deploy time. Each URL is rendered live on its first request and only then cached. That first request is frequently Google's crawler rather than a person, and on the city homepage it costs 902 ms of server render against the Payload backend.

This is the SEO answer the owner asked for. The crawler is not erroring — the pages return 200 — but it is paying a live render on first contact with every URL, and the city pages are the slowest and the most important.

Scope is small. Local content counts: 18 published articles, 3 single-type listicles, 3 listicle itineraries, 5 authors, 31 locations across 5 cities. Pre-building all of it is cheap. Check the live database before sizing — these are local numbers.

What to do

  • Add generateStaticParams to the dynamic public pages, starting with the highest-value ones: [country]/[city]/page.tsx, [country]/[city]/[category]/[slug]/page.tsx, [country]/[city]/maps/[slug]/page.tsx, [country]/[city]/itineraries/[slug]/page.tsx, authors/[slug]/page.tsx, articles/[slug]/page.tsx.
  • Source the params from the same public endpoints the pages already use, not from a new query path.
  • Leave dynamicParams at its default (true). A slug published after the last deploy must still resolve — rendered on demand, then cached — rather than 404.
  • Decide, and write down, what happens when the backend is unreachable at build time. A build that silently yields zero params is indistinguishable from today's behaviour; a build that fails loudly is probably better. Do not let a backend blip ship an empty sitemap.

Acceptance

  • The build output lists concrete URLs for those routes, not just the pattern.
  • First-ever curl to a pre-built city page is in the same range as a cached one (single-digit to low-tens of ms), not 900 ms.
  • A slug that exists in the database but was created after the build still renders, does not 404.
  • Build wall-clock recorded before and after.

Task BFinish the city page's backend cost — issue #596

Why. The 902 ms cold city page is the slowest server render on the site, and it is slow because of the endpoint behind it. PR #601 took it from 428 follow-up queries to 350 by giving every block repository a shared populate map. The remaining half needs a different tool.

The specific remaining cause. hotel-grid, tour-grid and things-to-do-attractions call findByID at depth: 2 with no top-level select at all, so every relationship on an accommodation, tour or attraction is still fetched — createdBy, locationRef, sharedNeighborhoods, tags, the Instagram gallery. populate cannot help: it narrows what a populated document brings back, but Payload still issues the query. Only a select on the root read removes it.

What to do

  • One repository at a time. Add a top-level select covering exactly what that block's normalizer reads. The normalizers are in <block>/lib/candidate.ts and reference-grid/candidate.ts.
  • Diff the full endpoint body after each one. Byte-identical is the bar, same as #601.
  • Extend homepage-featured-content/populate.test.ts to cover the new selects. It already runs the real normalizers over recording proxies and fails when one reads a field that is not fetched; the same technique applies to a root select.
Known limitation, stated in the issue thread. No city in the local database has attractions-block content, so a select on things-to-do-attractions cannot be diffed byte-identically here. Either seed content first, verify against the live database, or ship the two that can be proven and say plainly that the third was not.

Do not doAdding loading.tsx across the public routes

See section 4. The interval it would cover is 30–58 ms in production. The owner has rejected it. Do not revive it as a "quick win".

HousekeepingFree disk space on the Mac

Not a code task, and not one an agent should act on. 21 GB free of 460 GB with 8.6 GB of swap in use is making every local build and every local measurement slower than the code deserves. Worth telling the owner again; worth nobody deleting anything on his behalf.

6 · How to verify (exact recipe)

Local timings are only meaningful against a production build. next dev will mislead you by an order of magnitude.

Build and serve without disturbing the running dev servers

# apps/questura/apps/client
# 1. Temporarily add to next.config.ts, inside nextConfig:
#      distDir: process.env.NEXT_DIST_DIR || ".next",

NEXT_DIST_DIR=.next-prod NEXT_PUBLIC_BACKEND_URL=http://localhost:4000 npx next build
NEXT_DIST_DIR=.next-prod NEXT_PUBLIC_BACKEND_URL=http://localhost:4000 npx next start -p 3200

# 2. Afterwards, ALWAYS:
#      git checkout HEAD -- next.config.ts tsconfig.json   # the build rewrites tsconfig include
#      rm -rf .next-prod
#      pkill -f "next start -p 3200"

Measure a click the way a person experiences it

In the browser, on the page you are navigating from:

const href = '/authors/carlos-lima'
const a = [...document.querySelectorAll('a')].find(x => x.getAttribute('href') === href)
a.scrollIntoView(); await new Promise(r => setTimeout(r, 2500))   // let prefetch happen
const t0 = performance.now(); let at = null
const poll = setInterval(() => { if (at === null && location.pathname === href) at = performance.now() }, 8)
a.click()
await new Promise(r => setTimeout(r, 8000)); clearInterval(poll)
Math.round(at - t0)   // ms the screen showed nothing new

Count the queries behind a page

# Per-table DB reads, no code changes needed:
psql -c "select pg_stat_reset()" "postgres://$(whoami)@localhost:5432/google-login"
curl -s -o /dev/null http://localhost:4000/api/public/location-homepages/peru/lima
psql -At -F'|' -c "select relname, coalesce(seq_scan,0)+coalesce(idx_scan,0) as scans
  from pg_stat_user_tables where coalesce(seq_scan,0)+coalesce(idx_scan,0) > 0
  order by scans desc" "postgres://$(whoami)@localhost:5432/google-login"

For Payload-level counts, wrap payload.find / payload.findByID on the singleton inside the route and restore on a setTimeout of several seconds — a 0 timeout fires before the request finishes and you will count one query instead of hundreds.

7 · Traps

  • :3000 may not be pnpm dev. It has been observed running next start against a stale build, launched by a different tool. Hashed chunk filenames (8945-a8f0….js) give it away. Check ps -o command= before debugging why an edit "did not apply".
  • A hidden browser pane freezes requestAnimationFrame and CSS transitions. getComputedStyle then returns a transition's start value forever, so an opacity check reads 1 when the rule says 0. Inject transition: none !important before reading, or front the pane.
  • Do not touch the caching already set in (public)/layout.tsx (dynamic = "force-static", revalidate = 3600). It is correct. Task A adds params; it does not change the caching model.
  • Announce any port you occupy, and free it when done. A previous agent session left a proxy.mjs on :4015 running for seventeen hours and an orphaned backend held :4000 overnight, which silently stopped the owner's own pnpm dev from starting its backend. This cost real time and real trust.
  • The city endpoint's locationKey is not dead. Issue #596 claims it is always null; it is not. location is a text field on all three featured collections — locationRef is the relationship, and it is not in homepageFeaturedSelect. Do not delete the field.

8 · What this does not cover

  • No measurement on real hosting. Everything here is a production build served from the same Mac. A serverless platform adds cold starts and network latency that nothing local can predict. The production platform is still undecided; re-measure after the cutover.
  • No throttled or mobile measurement. All numbers are loopback on a desktop. A phone on mobile data will see longer intervals, which is the one scenario where the section 4 conclusion could change.
  • No Core Web Vitals. LCP, INP and CLS were not captured in this pass.
  • Crawler behaviour was inferred, not observed. No Search Console data was read. The SEO argument in task A rests on the cold-render timings above, not on evidence that Google is currently being slowed.
  • Only Lima has meaningful content locally. Medellin and Mexico City return empty homepages (188 and 191 bytes). Any before/after body comparison is effectively a Lima-only test.

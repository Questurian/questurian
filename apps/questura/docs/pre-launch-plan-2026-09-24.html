How to run this

One at a time, in a fresh session each

  • Do the steps in order, one session each. Almost every step starts the same practice copy of the site on this laptop. It uses fixed ports and most of the laptop's memory, so two sessions running it at once will collide or crash. Step 1 is the only one that is safe to run alongside another.
  • Each step is one PR. The agent merges it itself after CI is green, then the next step starts from fresh main.
  • If a step goes sideways, the agent should stop and say so. Nothing here is urgent enough to force.

2

Database time limit and an honest health check

small–medium · ~2 huses sandbox

Why: if the database freezes (instead of going down cleanly), the API waits forever and pages spin. Meanwhile /api/health/ready keeps saying "ready", so the host never notices. readiness:faults already reproduces both problems; they show as its 3 KNOWN gaps.

Prompt to paste 
Questura server (apps/questura/apps/server, Payload 3.79 + @payloadcms/db-postgres). Two known gaps, reproduced by `pnpm readiness:faults` (listed as KNOWN, see scripts/readiness/fault-checks.ts):
1. When Postgres is paused (not stopped), API requests hang forever: the pg pool has no client-side time limit.
2. /api/health/ready stays 200 while the database is unreachable.

Fix:
- Give the pg pool a client-side limit, e.g. `query_timeout` and `connectionTimeoutMillis` in the db-postgres `pool` options, and also a server-side `statement_timeout`. Choose values by measuring: find the slowest legitimate query first (article pages, sitemap, admin list views, migrations). Migrations and long admin jobs must not be cut off. If they need a longer limit, exempt them explicitly.
- Make /api/health/ready run a cheap DB probe (e.g. `select 1`) under its own short timeout and return 503 when it fails. Keep /api/health (liveness) DB-free, so a DB blip doesn't make the host restart the app.
- Turn the KNOWN fault checks into real passing checks. Update the expected counts in docs/launch-day.md.

Use the readiness sandbox exactly as docs/launch-day.md describes: Postgres :5442, Redis :6390. Never touch 5433 or 6379 on this laptop; those are live data. Run heavy jobs one at a time (7.5 GB RAM). Unit tests plus readiness:faults, readiness:routes and readiness:purchase must pass. One PR, green CI, squash-merge yourself. Follow AGENTS.md; use the caveman skill.
3

Google sign-in and staff/visitor separation tests

medium · half a dayuses sandbox

Why before the upgrade: step 4 updates the sign-in library. These tests are the safety net for the part nothing covers yet:

  • someone who signs up with a password and later uses Google with the same email;
  • staff and visitor logins never leaking into each other.
Prompt to paste 
Questura launch test harness, item B4. Read apps/questura/docs/launch-test-harness-handoff-2026-09-23.html (section on auth), and docs/launch-day.md for how the readiness sandbox runs. Existing sign-in attacks are in apps/questura/apps/server/scripts/readiness/auth-checks.ts (29 checks), with Playwright specs in apps/questura/apps/e2e.

Build readiness checks for:
- Account linking with Google OAuth. Use a fake OAuth provider written inside the test harness (a tiny local HTTP server that speaks enough OIDC for Better Auth). Install no new packages. Cases: a password account, then Google with the same verified email; the same with an UNverified email, which must NOT silently link; Google first, then a password reset; two Google accounts attempting the same email; the state/nonce replayed or swapped between two browsers.
- Staff (Payload `users`) vs visitor (Better Auth) isolation. A visitor cookie must never open /admin or staff APIs, a staff cookie must never count as a visitor member, and signing out of one must not sign out of the other.
If a check finds a real bug, fix it in the same PR with a unit test, the same way PRs #671–#676 did.

Rules: sandbox only (Postgres :5442, Redis :6390; never 5433/6379), heavy jobs one at a time, no deploys, no real Google/Stripe. Add the new command and its expected count to docs/launch-day.md. One PR, green CI, squash-merge yourself. Follow AGENTS.md; use the caveman skill.

Executive assessment

Improve work per request before buying more compute.

Backend contains concrete performance flaws. The most immediate issue is location pagination: a bounded response can cause unbounded growth in documents fetched. Homepage concurrency limits also operate at the wrong scope. Search work increases with content volume.

A separate deployment concern deserves early attention: session-level advisory locks cannot simply move onto a transaction-pooled database connection. That is a correctness issue, not a speed optimization.

What already helps

  • Public frontend content uses caching and revalidation tags.
  • Article indexes already select card fields rather than entire bodies.
  • Featured reads have bounded concurrency within each block; prior sequential work was improved.
  • Location scope can reuse an already loaded location.
  • Public images are delivered directly through Bunny rather than proxied through Payload.
  • Connection acquisition timeouts and some sensitive-route rate limits already exist.

Earlier frontend report is historical context. Its sequential-homepage and menu-deadline findings must not be copied forward as unchanged defects: current code already includes improvements.

01Fix first

Unbounded location pagination

A small response can require a huge read.

What the code does

Location listing caps page size at 50 but does not cap page number. It requests page × pageSize documents from each of three collections, populates card relationships, merges and sorts in memory, then slices out one page.

Why it matters

Page 100 with 50 items requests up to 15,000 documents to return 50. Actual work is limited by matching content, but a crawler can request deep pages directly. Growing content increases CPU, memory, relationship queries and pool pressure.

Recommended change

  1. Immediately validate safe integer page values and enforce a bounded retrieval budget.
  2. Move cross-collection ordering and pagination into a SQL union or dedicated public content index. Fetch IDs first; hydrate only the requested page.
  3. Use deterministic ordering, including a tie-breaker, and preserve publication, language and location rules.
Acceptance evidence

Compare first, middle, last and out-of-range pages. Verify stable ordering across equal publication dates, correct totals and an upper bound on hydrated documents. Reject extreme inputs before expensive reads.

02Fix first

Concurrency limit is per block

The documented six-read page limit is not enforced.

What the code does

Page assembly runs blocks through Promise.all. Each qualifying block separately calls readWithBoundedConcurrency, whose default is six workers. Each call owns its own counter; the budget is not shared across the page.

Why it matters

Seven qualifying blocks could start up to 42 document reads. Those reads also populate relationships. The Payload pool has 20 connections across requests. Four simultaneous local homepage requests each took about one second; that observation supports further investigation but does not prove pool saturation.

Recommended change

  1. Create one request-scoped concurrency budget and share it across block resolvers.
  2. Deduplicate document references across blocks with a request-scoped promise map. Include query shape and access context in cache identity.
  3. Batch compatible references by collection; retain placement-specific media resolution and curated slot order. Do not increase pool size as the first fix.
Acceptance evidence

Instrument peak active reads and actual SQL count per request. Test repeated references, missing documents, draft exclusion and original slot order. Compare concurrency 1, 4 and a bounded higher level under identical production-build conditions.

Repository evidence: apps/server/src/features/homepage-featured-content/resolve-page-blocks/operations/resolve-blocks.ts · audit reference line 15. Line numbers may move after edits.

03Before content grows

Search rebuilds searchable text

Every query performs content assembly work.

What the code does

Search SQL aggregates text from many block tables, combines article/map/itinerary content, constructs weighted full-text vectors, ranks matches and counts all matches. Result hydration is already batched by collection; text preparation remains request-time work.

Why it matters

Cost grows with corpus size rather than only the number of returned cards. Small scratch data can hide the problem. The query also supports substring matching, which must be accounted for when designing an index.

Recommended change

  1. Maintain a public search document when content changes, with an indexed tsvector and explicit publication/language fields.
  2. Preserve title weighting, phrase behavior and cross-content ordering; choose a deliberate strategy for substring matching.
  3. Backfill existing content through a reviewed migration/workflow. Add request budgets and measure query plans before selecting indexes.
Acceptance evidence

Use representative corpus sizes and EXPLAIN (ANALYZE, BUFFERS) on an appropriate non-live dataset. Compare rank relevance, empty queries, pagination and publish/unpublish freshness. Record SQL time separately from hydration.

Repository evidence: apps/server/src/features/articles/public/search/search-sql.ts · audit reference line 9. Line numbers may move after edits.

04Contained improvement

Author pages load full documents

Card summaries do not need complete article bodies.

What the code does

Author route requests up to 100 documents from each of three collections at depth 2, without the card-specific select already used by article indexes. It then serializes the documents into summary cards.

Why it matters

An established author can trigger up to 300 populated documents in one response assembly. Listicle bodies and venue relationships can add work unrelated to the visible summary.

Recommended change

  1. Reuse INDEX_ITEM_SELECT and the required card image depth.
  2. Paginate the combined author feed or provide a bounded initial result with continuation.
  3. Preserve author visibility rules, date ordering and valid card thumbnails.
Acceptance evidence

Compare card output before/after for all three content types. Confirm article body relationships are not read for cards. Measure query count, response size and memory with a prolific author.

Repository evidence: apps/server/src/app/api/public/authors/[slug]/route.ts · audit reference line 116. Line numbers may move after edits.

05Protect expensive routes

Caching does not cover every caller

Frontend cache helps; direct API calls still reach the backend.

What the code does

Public frontend reads use a one-hour cache with revalidation tags. The sampled backend endpoints returned no explicit Cache-Control header. Reviewed search and location routes have no application rate limiter; server middleware adds none. External edge protection was not inspected.

Why it matters

Cached browsing can be inexpensive while search, crawlers or direct API traffic repeatedly invoke costly queries. Adding more public cache layers without invalidation can also delay published changes.

Recommended change

  1. Apply route-specific input limits and rate limits to expensive public reads.
  2. Consider short-lived public response caching and coalescing identical in-flight reads, with clear cache keys and publication invalidation.
  3. Keep member-specific and authenticated responses private. Verify existing edge controls before adding duplicate layers.
Acceptance evidence

Test direct API traffic separately from cached frontend navigation. Verify hit/miss behavior, invalidation after publishing, recovery after errors and isolation between anonymous and authenticated responses.

Repository evidence: apps/client/src/lib/cache/public-cache.ts · audit reference line 1. Line numbers may move after edits.

06Contain failure

Deadlines stop short of SQL execution

Connection timeouts are not query timeouts.

What the code does

Configured pools have ten-second connection acquisition timeouts. Reviewed pool configuration does not explicitly bound running SQL statements or advisory-lock waits. Article frontend fetches lack an application deadline. Database-level settings were not inspected.

Why it matters

A slow query or blocked lock can hold resources while more work queues behind it. Aborting an HTTP fetch does not by itself guarantee that database work stops.

Recommended change

  1. Define separate connection, statement and lock-wait budgets appropriate to each operation.
  2. Add frontend deadlines and explicit failure behavior for cold public reads.
  3. Check database-level defaults and pooled-connection compatibility; ensure query cancellation or server-side timeout actually bounds work.
Acceptance evidence

Exercise slow SQL, unavailable DB, lock contention and frontend aborts in an isolated environment. Check resource release, error responses and recovery. Long maintenance operations may need separate budgets.

Repository evidence: apps/server/src/payload.config.ts · audit reference line 62. Line numbers may move after edits.

07Before Neon migration

Session locks need a direct connection

A pooled URI swap can break correctness.

What the code does

Advisory locking uses pg_advisory_lock and pg_advisory_unlock on a dedicated pool that shares the ordinary database URI. These are session-level locks used in payment workflows. PgBouncer transaction pooling does not support session-level advisory locks.

Why it matters

Switching the shared URI to a transaction-pooled endpoint can violate lock ownership and release assumptions. This is a conditional deployment risk, not evidence of a current live payment failure. Pool maxima also add up: Payload 20 + auth 10 + locks 10 per process, plus one temporary startup connection.

Recommended change

  1. Give session locks an explicit direct connection configuration, or redesign locking around compatible transaction semantics.
  2. Budget all pools across every process/replica; maxima are not permanently open connections.
  3. Validate lock contention, nesting and failure release before migration. Never assume changing to transaction-level locks is a drop-in replacement for a multi-query workflow.
Acceptance evidence

Test concurrent operations on the same logical key, unrelated keys, nested locks and disconnected lock holders using non-financial fixtures. Verify the actual deployed connection mode and budgets before launch.

Repository evidence: apps/server/src/shared/utils/advisory-lock.ts · audit reference line 64. Line numbers may move after edits.

08Before frequent cold starts

Startup performs schema work

Initialization cost grows more important with sleeping instances.

What the code does

Payload onInit calls an auth schema guard. The guard issues table/index creation checks and an orphan-profile query. Production visitor auth also requires Redis, so deployment has more dependencies than app hosting and Postgres.

Why it matters

On long-lived processes, startup cost is infrequent. Frequent cold starts can repeat schema checks and scans. Neon suspend/resume and application startup may combine into first-request delay; neither was measured here.

Recommended change

  1. Move production schema changes into controlled migrations; retain lightweight startup validation where needed.
  2. Run orphan audits deliberately rather than on every cold start. Preserve existing data safeguards.
  3. Account for Redis, region placement and sleep policies when planning hosting. Keep work portable beyond the temporary laptop.
Acceptance evidence

Measure clean startup, first request and subsequent requests separately. Validate readiness with DB/Redis unavailable and confirm missing schema fails clearly. Do not enable Payload push:true.

Capacity model / assumptions, not a forecast

Visitors are not simultaneous database requests.

1,000 visitors/hour→3 pages/visitor→3,000 pages/hour→0.83 page views/second

Three pages per visitor is an assumption. Visitors arriving at 1,000/hour means 0.28 new visitors/second on average. API demand also depends on search, auth, prefetching, browser behavior and cache effectiveness.

Illustrative scenarioCalculationWhat it means
Every page requires one origin content read3,000 ÷ 3,600 = 0.83 reads/sExcludes auth, search and additional API calls.
90% of those reads served by frontend cache0.83 × 10% = 0.083 reads/sAbout 300 origin reads/hour, if assumptions hold.
Tenfold short burst, no cache benefit0.83 × 10 = 8.3 reads/sExpensive page assembly can overlap and queue.
Three backend processes3 × (20 + 10 + 10) = 120Configured pool maxima, not guaranteed active connections; temporary startup connections are additional.

Request rate and concurrency differ. Average in-flight work is approximately arrival rate × response time under stable conditions. This does not predict behavior near saturation, when queues grow and response times rise.

Railway and Neon

Railway charges for its plan and actual resource usage. A base plan fee is not an unlimited compute allowance. Neon meters compute and storage. This audit does not provide a current price quote or monthly cost estimate; both require deployment configuration and measured usage. Railway pricing · Neon billing model.

Place application and database in nearby regions. Decide deliberately whether application/database sleep is acceptable. Neon can suspend inactive compute; waking it introduces latency. Cache misses may still reach a sleeping database even when the website receives visitors. Neon compute behavior.

Production auth requires Redis. Include it in dependency planning and failure tests. Hosting choice does not remove the need to bound queries, manage connections or preserve payment-lock semantics.

Hosting recommendation: size from production-mode measurements, then retain headroom for bursts and editorial activity. Do not buy larger compute solely to hide unbounded pagination or excessive relationship hydration.

Reporting rules

  • Choose numerical latency/error targets before declaring a pass. This audit did not establish them.
  • Compare distributions under identical conditions, not the fastest single request.
  • Keep frontend LCP separate from API latency; faster APIs help cache misses but do not remove browser render delays.
  • Record DB query plans before declaring an index missing or effective. This pass did not inspect representative live plans or actual index usage.
  • Keep local fixtures separate from claims about live Stripe, auth, membership or cross-subdomain cookies.

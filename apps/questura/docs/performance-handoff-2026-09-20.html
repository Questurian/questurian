F1 · High · backend latency

Cold location assembly repeats and serializes content reads

Measured slow endpoint; contribution of each query remains unprofiled.

What is wrong

A warm cached location page hides expensive backend assembly. The city endpoint first fetches the location, then the enabled homepage, then resolves location scope. Because the homepage location is normally an ID at depth 0, scope resolution can fetch the same location again. Blocks resolve concurrently, but featured-article slots inside each block await one document at a time. Each document lookup populates relationships at depth 3. Repeated references across blocks may repeat resolution work.

Evidence and limits

Three direct local homepage API requests took 2,310 / 745 / 1,439 ms and returned 56,251 bytes. These are endpoint timings, not database-query timings. Code confirms serial per-slot awaits; it does not establish how much Payload internally deduplicates or caches them.

Where to start

apps/server/src/app/api/public/location-homepages/[country]/[city]/route.ts:29

Location lookup; homepage lookup at line 44; scope and blocks at 65–66.

apps/server/src/features/homepage-featured-content/resolve-page-blocks/operations/resolve-scope.ts:19

Extra findByID when given a location ID.

apps/server/src/features/homepage-featured-content/resolve-page-blocks/operations/resolve-blocks.ts:10

Blocks already use Promise.all. Do not mistake this for serial block execution.

apps/server/src/features/homepage-featured-content/featured-articles/operations/selection.ts:32

Per-slot loop; awaited document lookup at line 41.

apps/server/src/features/homepage-featured-content/featured-articles/lib/repository.ts:27

findByID with selected fields and depth 3.

Reproduce and measure

  • Add temporary phase timings and query counts around location, homepage, scope, and each block. Use scratch data and uniquely tagged instrumentation; remove it after validation.
  • Run first-process and repeated endpoint reads separately. Record median and p95 over a declared sample count, plus reference counts and DB pool settings.
  • Use a fixture with repeated articles, missing documents, drafts, and mixed article collections. Compare query counts as well as duration.

Proposed implementation

  • Reuse the location already fetched by the endpoint when resolving scope, after confirming its shape satisfies the scope resolver. This is the smallest first change.
  • Introduce request-scoped document resolution keyed by collection + ID + relevant query/access options. Share it across blocks; avoid a global cache that silently crosses users or publication state.
  • Batch selected IDs per collection where Payload supports the needed shape. If batching is unsuitable, use bounded concurrency rather than unrestricted Promise.all over every document.
  • Restore results to original slot order and preserve invalid-slot reasons. Keep media placement resolution and population requirements intact.
  • Verify the equivalent neighborhood path separately. Do not assume country pages share this exact endpoint.

Acceptance checks

  • Published output, slot order, invalidItems, and completeness match the existing behavior for representative fixtures.
  • Repeated references cause fewer application-level reads; already loaded scope does not trigger a second location lookup.
  • Cold latency improves under the same fixture/process conditions; p95 and pool pressure do not regress.
  • Draft/publication rules, access tiers, MediaSet variants, and on-demand invalidation still hold.
Tradeoffs and failure modes. Depth 3 is partly needed for featuredImage → MediaSet → variants. Reducing it blindly breaks imagery. Parallel reads can saturate Postgres. This should not require a database schema migration. If scope grows into one, follow the repository migration rules.

Implement after measurement baseline; first backend work package.

F2 · High · client startup

Closed modal code is requested on initial mount

Confirmed import/mount pattern; byte and main-thread savings need a waterfall.

What is wrong

The interaction provider declares four dynamic imports with ssr:false but mounts every renderer immediately. Each renderer imports its heavy modal implementation. A modal returning null because it is closed still requires its module to load. Dynamic import splits code; it does not postpone work until user intent when the imported component is already mounted.

Evidence and limits

LoginModalRenderer, PasswordResetModalRenderer, UserModalRenderer and MenuModalRenderer all render inside the provider on initial mount. UserModal also calls user/logout hooks before its closed-state return. Shared query deduplication may avoid duplicate network calls; do not claim four independent auth requests without measuring.

apps/client/src/components/layout/MenuModal.tsx:1

Open-only query and search reset behavior to preserve.

Reproduce and measure

  • Capture cold-load script requests and long tasks with all modals closed. Identify which chunks contain auth forms and modal bodies.
  • Open each modal once, close it, then reopen. Separate download latency from data latency and hydration.
  • Test pointer, keyboard, touch, and URL-triggered login/reset flows.

Proposed implementation

  • Keep small store subscribers mounted; conditionally render dynamically imported modal bodies when open. Do not conditionally call hooks.
  • Warm body imports on a clear pointer/focus intent if first-open latency warrants it. Avoid immediately warming every modal on page mount.
  • Preserve existing initialLocationMenu data when the menu mounts. Loading its code later must not require refetching known menu data.
  • Define expected close/reopen state explicitly: login fields, reset email, search query, focus return and scroll locking.

Acceptance checks

  • Cold page with all modals closed no longer requests the heavy modal-body chunks.
  • Each modal opens through keyboard, touch and existing URL flows; close restores focus and scrolling.
  • Menu opens using supplied data without a new data request when fresh.
  • Repeated open/close produces no stale form state, extra listeners or missing auth callbacks.
Tradeoffs and failure modes. Deferring code may increase first-open delay. Measure that tradeoff; do not hide the effect behind an unnecessary animation. Keep access/auth logic unchanged.

Independent client work package after baseline; coordinate with F7 around the menu boundary.

F4 · Medium · interaction design

Navbar deliberately consumes wheel input before scrolling

Confirmed behavior in code; user-perceived impact not quantified.

What is wrong

Navbar.tsx tracks virtual wheel movement. The first 120 pixels are consumed by navbar collapse instead of normal page movement; a lerp smooths the collapse. The non-passive listener calls preventDefault. This can make a fully loaded page feel unresponsive even when load metrics look good.

Evidence and limits

ABSORB_PX is 120; wheel handling prevents default while below the threshold and at the top during upward scrolling. This was intentional interaction design, so the audit left it unchanged.

Where to start

apps/client/src/features/Navigation/Navbar.tsx:10

Threshold; preventDefault at 68/74; non-passive wheel listener at 87.

Reproduce and measure

  • Compare wheel, trackpad, touch, PageDown, Space, Home/End and programmatic scrolling. Record actual scroll displacement after the first input.
  • Test top-of-page reversal and sticky consumers such as map panels. Check whether scroll listeners or layout writes create long tasks.

Proposed implementation

  • Review whether the intentional wheel absorption should remain; changing it is a UX decision, not a transparent download optimization.
  • If changing it, derive collapse from actual scroll position and use passive observation. Avoid consuming input just to animate the header.
  • Retain the existing navbar-height contract and ResizeObserver updates for sticky consumers. Coalesce DOM writes and stop animation work when settled.

Acceptance checks

  • First downward input moves the page normally; keyboard and touch stay native.
  • Navbar reaches expected collapsed/expanded states without jumps or scroll oscillation.
  • Sticky map/other panels maintain correct offsets. No continuously running idle animation loop.
Tradeoffs and failure modes. Changing this can alter the feel of the whole site. Do not add motion as a substitute for responsiveness. If preserving it, document the accepted tradeoff.

Separate design-sensitive work package; do not mix with backend/cache edits.

F6 · Medium · responsive bandwidth

Policy confirmed; offscreen contention requires breakpoint-specific measurement.

What is wrong

heroImagePriority.ts marks all items of block zero eager/high. That corrected visible-image starvation on wide Lima layouts, where seven items share the first block. The same rule can prioritize offscreen carousel items or content below the mobile fold in other layouts.

Evidence and limits

F7 · High on failure paths · shell availability

Public shell waits for a menu fetch with no deadline

Await chain and absent timeout confirmed; induced stall not yet tested.

What is wrong

PublicChrome awaits getLocationMenu before returning the navbar and page shell. The helper has an hour cache and catches failures, but fetch has no explicit application timeout. A cold/stale-cache request to a backend that hangs can delay the shell even though the returned menu payload is tiny.

Evidence and limits

Menu API samples were 360 / 48 / 80 ms for only 864 bytes. Those samples were healthy responses, not a reproduced hang. The new Subscribe fix removes the auth wait after the shell arrives; it does not remove this earlier server-side wait.

Where to start

apps/client/src/components/layout/PublicChrome.tsx:13

await getLocationMenu before returning chrome.

apps/client/src/features/Navigation/lib/getLocationMenu.ts:23

Cached fetch with no AbortSignal deadline.

apps/client/src/components/layout/MenuModalRenderer.tsx:1

Consumers of server-provided menu data.

apps/client/src/components/layout/MenuModal.tsx:1

Fallback query only when open.

Reproduce and measure

  • Use a local stub/delayed response for the menu endpoint; test a cold data cache. Do not disrupt the live backend.
  • Measure first shell byte and visible navbar arrival independently of menu completion. Test timeout, 500, malformed JSON and recovery.

Proposed implementation

  • First add an explicit bounded read that safely returns null on timeout. Choose the deadline from a UX budget and observed latency rather than an arbitrary large default.
  • If needed, stream only the menu-dependent island; keep the logo and public Subscribe link outside its await.
  • Preserve initial menu data on healthy cached requests and retain the existing open-triggered fallback. Avoid fetching on every closed-menu mount.
  • Check cache behavior after failure: a null fallback must not unintentionally keep navigation empty for the entire hour. Define recovery behavior explicitly.

Acceptance checks

  • A hung menu backend cannot indefinitely delay the public shell.
  • Healthy cached menu opens without a browser fetch; failed menu recovers on open/retry.
  • No full route becomes dynamic solely to solve menu availability, and no hydration mismatch appears.
Tradeoffs and failure modes. Timeouts improve worst-case behavior but can discard useful data if too aggressive. Streaming changes ownership of data/provider props; coordinate with F2 and preserve public-page caching.

Early resilience package after baseline; small timeout first, streaming only if justified.

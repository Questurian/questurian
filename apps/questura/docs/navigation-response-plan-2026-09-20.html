A click should never feel ignored.

Targeted frontend work, not a site rewrite. Keep the prepared-page architecture. Remove secondary content from the article’s waiting path, and acknowledge navigation without replacing the page with a loader.

Goal: ready pages open immediately; unfinished pages acknowledge the click immediately and reveal useful content as soon as it is ready. No minimum display times, artificial pauses, or full-page skeletons.

What is happening

Next.js keeps the current page visible while it requests the next page. In development, routes may need compilation and automatic link prefetching is disabled. In a production build, known public pages are prepared ahead of time and links can preload them. Neither mode needs to make every click wait a second.

Confirmed code issue: ArticlePage.tsx awaits sidebar data before returning its title and body. Sidebar lookup fetches local recommendations and then global recommendations. An uncached secondary request can therefore delay primary content.

Existing public-page caching, one-hour revalidation, canonical URLs, metadata, and static route enumeration are valuable and stay. The earlier navigation handoff measured 30–58 ms prepared production-build clicks on this Mac, but also an 828 ms unprepared click. Those historical samples are not fresh measurements of this change.

What we want instead

  1. Click: preserve native Next.js link behavior and automatic production prefetch. Let its actual pending state drive feedback.
  2. While pending: native working cursor immediately; a thin, static blue line only if the wait lasts 150 ms. The line is an activity signal, not fabricated percentage progress. Keep the current page usable.
  3. Main article ready: render heading, image, and reading column independently of sidebar recommendations.
  4. Recommendations ready: fill their existing locations. Preserve the ad rail’s dimensions while waiting; no pulsing placeholder.
  5. Finished or interrupted: remove feedback using framework lifecycle, not a guessed timer. Feedback must survive the source menu closing.

Keyboard/touch users also get the blue line; assistive technology gets a short status message from the message catalog. Reduced-motion users see no moving animation. Standard modified clicks, downloads, external links, and explicit prefetch opt-outs retain their behavior.

Implementation sequence

1. Prove the dependency

Add a server-render regression test around the real ArticlePage composition with recommendations deliberately unresolved. Heading and body must stream before recommendations resolve. Confirm the test fails against the current code before changing it.

2. Stream secondary article content

Start one shared recommendation promise. Consume it in async server children under local Suspense boundaries for rail and footer. Keep the synchronous article shell independent. Reuse the existing empty ad rail as its fallback; do not suspend the entire article. Keep recommendation selection semantics unchanged. Run local and global index reads concurrently where independent, avoiding a duplicate global read on fallback.

3. Make public links respond

Create one thin shared Link wrapper using Next.js 15’s useLinkStatus. Adopt it for public discovery, navigation, article, author and shared menu/footer links. Keep Next’s anchor, ref, props, prefetch rules, and navigation handling. Add scoped feedback CSS to the shared foundations stylesheet. Existing programmatic private account/auth redirects are outside this public-link pass. Include nested author links, public search submission and disappearing menus; see the lifecycle issue in the handoff findings below.

4. Verify locally

Run the streaming regression, meaningful sidebar selection/concurrency checks, client tests and typecheck. Exercise city → article, article → city, author and Join links in the browser. Verify feedback clears, modifier-click behavior is preserved, content/paywall markup stays correct, and the layout does not replace the reading column with a loader.

5. Record actual results

Record measured outcomes below. Distinguish real-route delivery samples from controlled delayed-data tests. A controlled test proves dependency removal; it is not a promise of a fixed percentage speedup on all clicks. If optional production-mode comparison is performed locally, isolate build output and port, announce the port, and stop only that owned process afterward.

Acceptance criteria and boundaries

  • With recommendations held unresolved, the article heading/body are emitted before their release.
  • One sidebar result feeds both placements; local/global selection and deduplication remain correct.
  • Pending public links provide feedback without blocking navigation or adding minimum wait time.
  • Fast completed links do not flash a loading page.
  • Client checks pass; failures unrelated to this work are recorded explicitly.
  • No backend schema change, migration, Stripe operation, deployment, or hosting infrastructure is needed.

Will this carry into production?

Yes: the dependency removal and click feedback are the same application code. On an already cached/prefetched page there may be little speed to gain; the main benefit appears when a page must render or a request is slow. Development compilation is separate and remains. Network, devices, cache misses, and serverless cold starts still need measurement on the eventual host.

Size and risk

Small-to-medium frontend change: one shared link component with mechanical import changes, article composition, sidebar orchestration, tests and this report. No framework replacement. Main risks are link semantics, feedback persisting after navigation, recommendation placement shifts and lost streaming through a parent boundary. Verify these rather than promise instant navigation under every condition.

Rollback

Revert this change’s shared-link imports/component, article composition and sidebar orchestration together. Preserve unrelated work and existing cache/static-route configuration. No data rollback required.

Investigation results and handoff status

Status (September 21): implemented and verified — see Measured results. The text below is the original September 20 handoff, kept as written.

A temporary prototype exercised the real ArticlePage composition with React server streaming and stubbed unrelated media/auth leaves. Recommendations were deliberately held for 1,000 ms. Original composition emitted its first content at 1,006 ms; the prototype emitted it at 5 ms. Both finished around 1,003–1,007 ms. This proves that moving the waiting boundary can expose primary content earlier; it is not a 200× whole-site speedup or a real-browser paint benchmark.

The temporary regression test failed before the change and passed after it. Prototype checks passed 162 client tests and TypeScript. These checks describe the removed prototype, not a shipped implementation. The receiving AI must recreate appropriate tests.

Browser checks of that prototype observed Next’s pending state on city-to-article navigation, confirmed a progress cursor and blue feedback styling during author-to-Join navigation, and confirmed pending state cleared on arrival. City return and author navigation also completed. A cold author route still waited on development work; do not promise this frontend change removes development compilation.

Important issue found before handoff

MenuModal.tsx and UserModal.tsx close themselves on link click and return null when closed. A pending marker owned only by the clicked link disappears if that link unmounts. A link-only implementation is insufficient for those paths. Design a persistent transition owner for disappearing menus, or keep the source mounted until the transition commits; preserve instant menu dismissal and cancellation/error cleanup. Use framework transition state, not a global click timer that can get stuck. Nested AuthorLink uses router.push, so it needs explicit transition feedback as well. Public search submission also uses programmatic navigation and closes the menu—include it in this lifecycle check.

Visual risks to check

Keep the existing ad rail in the fallback so its column geometry stays stable. Footer recommendations may shift the footer when they arrive; test a short article and mobile view, reserve appropriate space only where justified. Verify that parent layouts and navigation boundaries actually allow the reading column to commit early, not merely that the server emits bytes early.

Measured results

Outcome: every measured click now acknowledges itself in 5–74 ms (before: never). With uncached data the article heading arrives about twice as early. Already-prepared pages are not faster, as predicted: there was nothing to remove from their path.

What shipped

  • ArticlePage no longer awaits the sidebar. One promise feeds StreamedArticleRail and StreamedArticlePartners, each behind its own Suspense boundary; the rail's fallback is the same ad rail with an empty trending list, so the column geometry holds.
  • fetchStandardArticleSidebar starts the global index read alongside the local chain and reuses it when the local chain falls back to global (the old code read global twice on that path). Selection and deduplication are unchanged — the new selection tests pass against the old code except for that read count.
  • PublicLink wraps next/link with useLinkStatus; 36 public files use it. Private account/auth screens stay on plain next/link, enforced by an allowlist test.
  • NavigationFeedback, mounted once in the root layout, owns a useTransition for navigations whose source disappears: menu and user-menu links (keepFeedbackAfterUnmount, via Next's onNavigate, so modified clicks never reach it), menu search submission and the nested author byline.
  • html[data-navigating] gives the progress cursor at once; a static 3 px --accent line appears only if the wait passes 150 ms; a polite status reads navigation.loading from messages/en.json. No timers decide when feedback ends — the framework's transition does.

Edge cases checked

  • Modifier-click: Next ignores it, page stays, no feedback.
  • Keyboard Enter on a focused link: feedback in 20 ms, arrives, clears.
  • Back and forward: nothing left pending.
  • Second click 30/80/150 ms after the first: ends on the second page, feedback cleared.
  • Mobile 390 px menu: menu closes immediately, feedback and "Loading page…" status persist until arrival, then clear.
  • Reduced motion: the line has no motion to remove (0 s animation, 150 ms delay, static bar).
  • Production build succeeds; prepared article HTML still contains the trending and partner lists (resolved inside the same file).
  • Client tests 167/167 (158 existing + 9 new), typecheck clean, no console errors on article pages.

Limits

  • The nested author byline (FeaturedArticleOne block) is not used on any local page, so it was verified by types and source guard, not in a browser.
  • No public page has same-page anchor links, so that case had nothing to test.
  • The rendering test needs installed dependencies; CI's client job has none, so it skips there. The source guard in publicLinksGiveFeedback.test.mjs runs in CI instead.
  • When recommendations are slow, the "From Our Partners" row arrives after the article and can push the footer down. It sits at the very bottom of the page, so no space was reserved.
  • All numbers are from this Mac on the local dev server; hosting, cold starts and real networks still need measuring after the serverless move.

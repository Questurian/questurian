Controlled hosted deployment

Reasonable next proving stage, with restricted exposure, verified origin access, explicit resource ceilings and reversible releases. Existing local evidence supports trying the intended architecture. It does not establish that its real bindings, cookies, routing or quotas work.

Aggressive campaign

Not ready to claim 10×–100× spike tolerance. Uncached account routes lack complete admission control; Payload mount protection has a credential-presence bypass; hosted cache behavior and cost limits remain unverified. A popular link can leave the article visible while account features fail.

The intended stack is Cloudflare Workers/OpenNext for the frontend, Railway for the Node backend, Neon for Postgres, Railway Redis and Bunny for images. This is the recorded direction, not a verified deployed inventory. The Linux laptop is an optional live-like test environment; its performance cannot certify this stack.

Fifty articles is enough to create a serious surge. Repeated hits to one cached article are relatively cheap. Thousands of independent identity checks, cold renders, searches, images and sign-ins are different workloads. Prioritize request amplification and simultaneous work—not an 8,000-article library.

3. Tests that need both stages

Build and validate these locally, then repeat the platform-dependent portion after hosting is available:

  • Complete visitor journey: local request map and synthetic identities → hosted mobile/browser, cookie, OAuth and challenge checks.
  • Surge and recovery: local proof of admission, retries and emergency stops → hosted measurement of sustainable throughput, 10×–100× offered spikes within an approved envelope, and recovery.
  • Publish/deploy under traffic: local revision and worker correctness → hosted regional purge, cold-cache behavior and real rollout overlap.
  • Dependency failure and restore: disposable local simulations → isolated hosted recovery, managed backups and platform-specific failure behavior.

1. A fake credential bypasses Payload mount protections

An attacker can add an arbitrary Authorization or x-api-key header to skip whole-request admission and URL clamps. GraphQL’s “authenticated only” wrapper makes the same presence check. Publicly readable content stays readable when authentication resolves to no user; authentication failure is not automatically an HTTP rejection. This opens a route around the work budgets protecting normal visitors.

Candidate change. Authenticate before granting a resource-control exemption, or retain admission and safe read limits through authentication. Close unused anonymous mounts where product consumers allow it. Apply ingress protection before waiting on Redis.

Test and pass condition. Local integration: absent, malformed, expired and arbitrary credentials against REST globals, collections and aliased GraphQL. Invalid credentials must get an explicit rejection or the same bounded anonymous policy; no bypass of whole-request gates. Valid staff/service access must retain intended permissions.

Technical evidence and source paths

Independently inspected installed Payload JWT and API-key strategies plus executeAuthStrategies. Invalid JWT pure probe returned {user:null}, not a rejection. Mount tests explicitly expect arbitrary credentials to pass through. Collection beforeOperation still clamps reads when req.user is absent; this finding does not claim that clamp or private-content authorization disappears. Globals are not decorated by that collection plugin. No expensive endpoint exploit or live request was run.

2. Account traffic can escape the admission budget

Bookmark refs/list and member-body routes resolve sessions without the private gate. Member bodies have a 30-per-minute IP limit, but many distinct visitors can each stay under it while exhausting shared pools. Sign-in has Better Auth rate limits but no analogous route-wide concurrency bound. A valid-looking session flood can hold the /api/me private gate continuously because that route has no per-caller limiter.

Candidate change. Choose bounded admission for all costly account reads and auth work, before dependencies; preserve the cheap no-cookie identity path. Add abuse/fairness controls that distinguish valid accounts, invalid sessions and anonymous callers. Budget combined public/private/background demand against the shared pools.

Test and pass condition. Local mixed workload: valid, expired, random and malformed cookies; bookmark list/refs/writes; member body; bounded sign-in simulations. Pass: work/queue counts stay within declared limits, invalid traffic cannot bypass them, legitimate private/public service meets agreed SLO, recovery returns queues to baseline.

Technical evidence and source paths

Candidate change. Use server-only render identity consistently where intended; retain a bounded shared render budget. Give search an explicit unavailable state. Decide IP/account/route limits using real browser and shared-network traffic; do not equate one IP with one visitor.

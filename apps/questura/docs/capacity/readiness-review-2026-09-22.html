What to measure

Incoming website visits per second.

Millions per month describe total volume. A crash is more likely to depend on how tightly those visits cluster and what each visitor does. Video views and website visits must be counted separately.

Illustration—not a forecastWebsite arrivals
1 million website visits evenly over 30 daysAbout 0.39 visits/second
100× that averageAbout 39 visits/second
1 million external video views; 1% click through within one minute10,000 visits in a minute ≈ 167 visits/second
Same one-minute example; 5% click through50,000 visits in a minute ≈ 833 visits/second

Each visit may cause several requests: a page, identity check, bookmark state, navigation, images and perhaps search or member content. That is why the existing “1,000 page requests/second” script cannot stand in for 1,000 full visits/second.

Discovery requirement: define an absolute arrival range alongside 10×/100× multipliers. Test sharp steps and sustained load, a concentrated destination and a spread of destinations. Find the failure point and recovery behavior instead of promising an unlimited surge.

02 · Fix code behavior

A temporary bookmark failure can look like a logout.

What the code shows. The bookmark store starts with authenticated=false. If its first load fails, the catch marks it ready without changing that flag. A subsequent bookmark click returns unauthenticated. A signed-in visitor can therefore be asked to sign in after an outage; this is a UI classification problem, not proof their server session was lost.

Candidate work. Distinguish unavailable/unknown from genuinely signed out. Allow bounded recovery instead of permanently settling the first failed load as ready.

Needed test. First bookmark request returns 503 or loses its connection; next request succeeds. A signed-in visitor recovers without a false login prompt or cross-user bookmark state.

06 · Verify abuse defenses

Fake sessions can compete for the same slots as real members.

What the code shows. /api/me selects the private-work gate using cookie-text presence, before session validity is known. That is not an authentication bypass, but invalid-session traffic can occupy the same budget real members need. There is no explicit per-IP limiter in this route; the impact depends on how quickly the auth library rejects each cookie.

Candidate work. Measure no-cookie, malformed, forged and expired-cookie costs. If invalid traffic materially occupies capacity, add appropriate early abuse controls while retaining aggregate limits. Auth endpoints already have Redis-backed rate rules; production Turnstile exists but is configuration-dependent.

Needed test. Flood invalid synthetic cookies while valid sessions request identity and member bodies. Valid users must retain a declared service level. Also verify auth challenge rejection and shared-IP false positives with no real emails or charges.

Security discovery

Use Cloudflare, but close the route around it.

Cloudflare supplies automatic DDoS mitigation. Its request-rate rules are not an exact ceiling on traffic reaching your server. App-level capacity limits still matter. DDoS documentation · Rate-limit limitations.

What existsWhat remains to prove or implement
App trusts one configured proxy’s IP header.The proxy must really be the only public entrance. The source explicitly assumes this. A caller reaching a direct backend URL could supply that header themselves. This is a conditional bypass risk, not a confirmed deployed vulnerability.
Checklist recommends Cloudflare in front of the API.Choose and implement origin restriction/authentication supported by the backend host; verify alternate hostnames cannot bypass it. A note saying “make it unreachable” is not an implemented control.
Per-IP public/auth/member limits; optional production Turnstile for selected auth forms.Verify enabled configuration, invalid-session abuse, malformed requests and many-source pressure. Prove regular mobile users and legitimate link-preview crawlers are not accidentally blocked. CORS does not authenticate a non-browser caller.
Cloudflare adapter and cache bindings are in the repo.They do not establish account WAF rules, rate rules, origin protection or spending limits. Inspect the actual account/host configuration during hosted preparation.

Needed security checks: forged IP headers; direct-host bypass; repeated expensive requests; cache-busting URL variations; invalid auth traffic; missing/invalid form challenge tokens; false positives for shared networks. Keep payment webhooks and trusted scheduled jobs working without broad security bypasses.

Likely investment: targeted app fixes plus explicit hosted security configuration and verification. No evidence here supports building our own DDoS mitigation network or purchasing the most expensive tier by default. Route public site and API through the intended controls; inspect separately hosted images/assets on their own delivery path.

Standards / documented contracts

Four implementation findings.

These concern resource and worker guarantees already claimed by the code and readiness plan. They are not observations of a production outage.

P1 · Budget correctness

Pooled rollouts ignore the previous generation

Code-confirmed; failure under load not reproduced

The pooled branch uses current pool sizes for every serving, surge and job process. It reads the previous generation’s ceiling but does not use it here. A release that shrinks pools can pass admission while old processes still hold larger pools. This matters for the intended pooled Neon deployment.

Next check. Use old/new generations with different pooled-client and direct advisory-lock limits. Both client allowance and physical backend allowance must cover their overlap; an over-budget rollout must refuse boot. A single previous total needs a conservative rule or separate pool components.

P2 · Budget correctness

A running fleet can declare zero serving processes

Reproduced with pure configuration function

APP_REPLICA_COUNT=0 and APP_PROCESSES_PER_REPLICA=1 return processCount=0 with no validation problems. The derived count bypasses the positive APP_PROCESS_COUNT requirement. Pure probe calculated only five reserve connections for that fleet.

Next check. Require positive, bounded, safe integers for replicas and processes per replica. Test zero in each field, overflow, mismatched explicit totals and the final production boot guard.

P2 · Worker recovery

Four jobs leased, then worked one at a time

Code-confirmed; multi-worker slow-job consequence untested

The worker calls this concurrency=4, claims four rows, then awaits them serially. Later rows spend their 60-second lease waiting behind earlier jobs. Delivery has a timeout per chunk, not per complete fanout. Another worker can reclaim a waiting row. Fencing protects completion ownership, but duplicate delivery and wasted work remain possible.

Next check. Run four slow jobs and two workers across a lease boundary; record start times, ownership and duplicate delivery. Include shutdown during a multi-chunk job, failure on the final chunk, retry and eventual convergence. Choose actual bounded concurrency or just-in-time claims.

P2 · Memory bounds

An oversized fallback bypasses the byte ceiling

Reproduced in memory

A final entry is deliberately retained even above maxBytes. A 100-byte configured limit retained 1,002 estimated bytes in a pure probe. One large page can evict the smaller fallbacks and remain over budget. The estimator counts serialized characters, not heap memory.

Next check. Test single oversized values, replacement of an existing entry and multibyte text. Skip caching oversize entries or explicitly adopt a soft limit; do not claim a hard memory bound from serialized size alone.

P1 · Recovery proof

Restore success stops before service recovery

Code-confirmed assertion gap

The restore script preserves selected row counts and a pending obligation. It labels table existence as search rebuildability, but never rebuilds, starts the restored application, drains the queue or reads a restored page. psql also lacks ON_ERROR_STOP, so SQL errors do not reliably fail the command immediately.

Next check. Restore → boot → rebuild search → drain pending work → verify exact public and private responses. Include media sets and auth/profile integrity, not just current counts. Headline consistency is narrower than page consistency

Code-confirmed assertion gap

Code-confirmed metric mismatch

The matrix asks for document TTFB and successful dynamic latency. k6 gates full response duration and mixes response outcomes.

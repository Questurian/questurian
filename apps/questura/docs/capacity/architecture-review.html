Questura / Architecture review / 21 September 2026

Cheap reads.
Controlled overload.
Platform proof still owed.

Questura’s design can keep popular pages cheap by serving cached HTML from Cloudflare, while Railway handles fresh content, identity and payments against Neon Postgres and Railway Redis. CAP-01–06 made that code cheaper and better at refusing excess work; they did not prove a production traffic ceiling. All recorded capacity measurements came from a Mac. Cloudflare’s OpenNext cache, actual fleet limits, recovery and spend controls remain unproven. A 10× burst looks plausible with warm pages; 100× demands proof of the dynamic paths and cold-cache behavior. The largest immediate risks are an unconfigured shared cache, work outside admission gates, and refresh jobs whose success guarantees are weaker than the docs suggest.

01 / How it is built

One public page, several independent paths

Intended deployment: Next.js frontend on Cloudflare Workers through OpenNext; Payload inside a Next.js server on long-lived Railway instances; Neon Postgres for persistent records; Railway Redis for session storage and shared rate counters; Bunny for image delivery; Stripe for billing. “Serverless” does not mean the backend runs once per request. Nothing in this intended stack is provisioned. [platform]

Deployment: what exists versus what must move

The parked laptop currently has a concrete release mechanism: immutable commit snapshots, reviewed forward migrations, server activation and exact-SHA health checks, then client build/activation against that server. Failed activation can restore paired release links; it does not reverse database schema. That systemd/symlink machinery is temporary. The intended platform needs its own Railway release/health/rollout settings and Cloudflare adapter deployment, with migrations before serving, correct runtime/build secrets and prewarming after release. There is no implemented production pipeline to assume already provides those guarantees. [softprod README / launch checklist]

Visitor trace: /peru/lima

  1. Browser asks Cloudflare for the page. With valid cached public output, HTML returns without a backend content query. The browser receives navigation and city blocks, then fetches images and hydrates small interactive components. Public HTML is shared, not personalized. Local cookie and RSC variant checks passed; target cache separation remains unproven. [status]
  2. On a miss, the frontend renders. fetchCityHomepage fetches /api/public/location-homepages/peru/lima using a server-only render token and one-hour tagged data caching. Redis checks the public-read rate counter first. Identical concurrent city work joins one promise inside each backend process; this is neither stored content nor cross-instance deduplication. A distinct city assembly then needs an admission slot. [city] [gates]
  3. Payload assembles records from Postgres. A request-scoped read cache and semaphore avoid repeated references and limit concurrent logical document reads. Batch fetches fill block references. The ORM turns these into SQL; the Payload pool supplies connections. Lima still costs 171 SQL statements / 17 logical reads in the small measured dataset. JSON returns to Next.js, which renders HTML and caches successful output. Images themselves do not pass through these SQL reads. [batch] [measurements]
  4. Identity follows independently. Navbar calls /api/me; a valid visitor session needs Redis plus profile/account reads in Postgres. No-cookie or invalid-signature paths measured zero SQL and zero Redis. React Query reuses identity for two minutes: the recorded client navigation from Lima to an article made no extra /api/me, but a fresh page load can. Errors do not become proof of membership. [identity]

Visitor trace: an article

Cached public article HTML follows the same Cloudflare path. On a miss, the canonical-path public API passes through the query gate, reads Payload/Postgres and returns the public article representation. Related shelves are secondary: their failure can still produce an empty shelf by deliberate policy. Article bookmarks make a separate private request; full member content uses a private, server-authorized endpoint. Stripe is not consulted for each public page or each membership display: the app reads its stored entitlement. During invalidation plus backend failure, articles have no LastGood fallback; local measurement returned 500 until recovery, avoiding deliberate resurrection of an old access state. This does not prove that the future CDN purges an access change correctly. [surface] [identity] [cache]

Publishing and buying are separate workflows

An editor’s save normally inserts a refresh job in the same Postgres transaction. Workers read committed content, update the search index, and call the frontend’s secret-protected revalidation endpoint. The process has a periodic drain; an external scheduler is still owed. A buyer opens Stripe Checkout only after a backend request. Stripe later sends signed webhooks; handlers refetch current billing state, coordinate through Postgres advisory locks, update membership and record the event. Reconciliation is the repair path. No live correctness claim is made here. [outbox] [payments]

Each square is one request. The default sends 100 distinct cold city requests simultaneously into the proposed four-instance fleet: 8 start, 32 queue, 60 are refused immediately. Database budget: (4 serving + 1 rollout + 1 job) × 41 + 5 reserve = 251 connections.
Per process: 20 Payload + 10 Better Auth + 10 advisory-lock + 1 startup. These are maximum connections, not pre-opened reservations. Four serving processes alone have up to 80 Payload connections; the animation only lights this pool. Railway and Neon must actually match these declarations. [pool-budget.ts]

Simulation assumptions: even round-robin routing; distinct cold URLs, so no coalescing; no previous rate-counter usage; finite batch, no retries or background traffic. Assembly takes 2 ÷ 12 ≈ 0.167 s, an illustrative duration derived from the Mac’s ~12 assemblies/s with two slots, not a measured target latency. Query uses the same illustrative duration solely for comparison. Each active assembly models six connections; each query models three, based on admission.ts’s sizing comments. The actual semaphore limits logical reads, not PostgreSQL sockets. Query demand beyond 20 waits inside the pool; its modeled duration is stretched proportionally. Neither allocation nor duration predicts Payload behavior. Gate numbers are exact defaults: assembly 2 active / 8 queued; query 8 / 32; queue wait ≤1.5 s. Playback is slowed for readability. Reduced-motion starts paused; Play advances states without transitions. [gates] [read budget]

Cold burst guardrail: a full queue refuses immediately; queued work may also time out at 1.5 seconds if the database slows. An admitted request continues after the reader disconnects. Identical city misses can share work per process, but joined requests still occupy HTTP/runtime memory and have already hit the rate counter. A global bound on all requests is unproven.

03 / What the program changed

CAP-01 through CAP-08

CAP-01 · Measure honestly

The old harness mixed errors into latency, mishandled warmup, lacked request deadlines and mostly modeled callers waiting for previous work. The replacement separates successful latency from failures, records dropped arrivals, adds arrival-rate workloads and pool diagnostics. It exposed Lima’s old ~4–5 cold assemblies/s ceiling and a growing pool queue. In practice: a fast 503 no longer masquerades as a fast successful page. Early “cold” evidence is only first-request-per-URL because the restart helper was unreliable. [status, CAP-01]

CAP-02 · Stop accepting more expensive work than can run

Pool sizes were scattered; undeclared database capacity could skip checks; boot refusal was swallowed. Pool budgeting now counts serving processes, rollout overlap, jobs and reserve, distinguishes direct/pooler limits, and exits on invalid production declarations. Public assembly/query gates limit active work and short queues, returning uncached 503 on overflow. In practice: deliberate refusal replaces runaway waiting on these routes. Fleet-wide safety still depends on a real provider instance cap. [gates] [pools]

CAP-03 · Keep anonymous identity cheap

Anonymous identity cost was unknown; instrumentation proved the existing no-cookie and forged-cookie paths already did no SQL or Redis work. Signed-in identity did duplicate session lookup; it now resolves the session once and reads profile/account information in parallel. Redis deadlines and jittered reconnects replace indefinite command waiting. In practice: anonymous traffic stays cheap, while logged-in traffic does less work. Valid-session throughput and Redis-outage behavior remain unmeasured on target. [identity] [Redis]

CAP-04 · Cover public reads and stop caching failure as content

Several custom routes lacked shared limits/diagnostics; anonymous Payload reads could return huge responses; backend errors could become false empty pages or 404s. More routes now use the wrapper, collection reads are clamped, frontend render traffic gets a separate secret-backed bucket, and primary public reads distinguish 404 from failure. Curated pages keep an in-memory last good answer; articles deliberately do not. Prewarm tooling was added. In practice: fewer ways for overload to corrupt shared public output, but no universal public-surface gate and no Cloudflare purge proof. [surface] [cache]

CAP-05 · Reduce cold-page database work

Curated blocks fetched references repeatedly and sitemap visibility grew with author count. Per-block batching now seeds the request read cache; sitemap uses minimal fields, complete pagination and grouped author visibility. Lima fell from 382 to 171 SQL statements and 43 to 17 logical reads, with byte-identical recorded output; local cold assembly throughput rose to about 12/s. In practice: a cold page costs much less, but large-corpus query plans and mixed-workload capacity are still unknown. [batch] [status, CAP-05]

CAP-06 · Remember refresh work after a save

Inline post-save hooks ran before the transaction committed, so search and revalidation could see old data; delivery failures were only logs. A Postgres outbox now normally records obligations with the save, merges duplicate jobs, retries failures and exposes failed jobs for replay. Production no longer seeds at boot; currency sync skips fresh data. In practice: normal refresh failures are recoverable. Enqueue fallback, missing delivery config and worker ownership races weaken the guarantee; a real publish-through-frontend proof is still absent. [outbox] [findings below]

CAP-07 · Prepare platform, recovery and cost decisions

Local performance did not identify a paid deployment envelope. CAP-07 records the intended Cloudflare/Railway/Neon/Railway-Redis stack, example pool budgets, scheduler duties, alerts, restore drills and a byte-based cost model. In practice: provisioning requirements are clearer, not completed. Budget, maximum instances, campaign URLs and recovery targets remain undecided; nothing is verified on target. [platform readiness]

CAP-08 · Prepare capacity proof

A cache-hit demo cannot establish campaign readiness. Six k6 scripts cover reader load, burst/recovery, hot arrivals, cold pages, signed-in mix and soak; tiny local smoke runs exercised them. In practice: there is a starting test matrix, not a release certificate. No target campaign run exists, and script assertions need strengthening before the claimed correctness and abort gates can be trusted. [k6] [proof gaps]

05 / Scale means rate, shape and cost

What 10× and 100× mean

Baseline: 70 million campaign impressions/reached opportunities × 12% clicks = 8.4 million visits; × 2 pages = 16.8 million page views per 30-day month. These are assumptions, not analytics or unique people. Average: 3.24 visits/s, 6.48 pages/s and about 583 active readers at 180-second dwell. Here 10× / 100× means an instantaneous multiplier of that average; it does not automatically multiply monthly spend. The plan’s 100M-impression stretch is only 1.43× the 70M baseline, not 100×. Why the refresh race is credible

Worker A claims job J. An editor changes that document: enqueue resets J to pending. Worker B claims J, making it running again. A finishes its older work; its UPDATE ... WHERE id=J AND status='running' now matches B’s claim. No token distinguishes them. Separately, claiming 50 rows at once and allowing each delivery up to 5 seconds can outlive the 60-second lease before later rows even start. These are source-level counterexamples to “newer change survives” and “no duplicate work,” not a claim that recorded local checks observed them. Add claim generations and verify side-effect ordering, not just row status. [worker] [5 s delivery deadline]

Documentation disagreements resolved by code and raw evidence
  • Old campaign HTML still says all tickets planned and frontend Vercel. Current code plus STATUS support CAP-01–06 locally implemented; ADR-0014 and owner direction establish Cloudflare.
  • “Every public read is covered and bounded” is too broad: collection clamp does not prove global-hook coverage or aggregate load control.
  • “Refresh is durable” holds for successfully recorded jobs under the normal path, not enqueue fallback, skipped delivery or all overlapping-worker schedules.
  • “Seven days bounded staleness” describes configured cache/entry limits, not a verified global maximum age for published content.
  • “0 refused at 6/s” after CAP-05 means no admission 503s; raw JSON includes one 429. The ~12/s ceiling is short, saturated local evidence.
  • “No code change needed” in launch checklist predates the missing OpenNext adapter and unresolved Railway ingress support.
  • CAP-07’s sub-millisecond Railway Redis expectation is unmeasured. Provider proximity is a design choice, not latency evidence.

08 / Decisions and work

Before a real campaign

  1. Define the envelope: monthly and daily spike budget, actual max serving/rollout/job instances, campaign URLs, recovery time/data-loss targets. Record a stop/slow-campaign owner and spend response. These are the four remaining owner decisions, not reasons to rewrite the application. [D3–D6]
  2. Implement and pin OpenNext: production-compatible adapter build, incremental cache, tag store, revalidation queue and cache purge. Verify HTML/RSC keys, tracking parameters, cookies, private no-store, access-change/delete/negative-cache invalidation across regions. Do not put a stale shared JSON cache in the render path. Decide whether curated fallback needs durable shared storage with explicit freshness semantics. [OpenNext]
  3. Fix refresh correctness: fail production configuration when required revalidation destination/secret is absent; do not mark skipped delivery done. Preserve durable obligations on enqueue failure or surface an explicit failed save. Fence claims with ownership/version checks, keep leases valid or claim just-in-time, and test newer-save/overlap/lease-expiry side effects through real publish → commit → search → frontend. [worker] [delivery]
  4. Close admission gaps deliberately: decide which anonymous mounts are needed, cover globals and GraphQL complexity, and test remaining ungated paths under multi-IP pressure and Redis failure. Do not mistake per-IP throttling or finite pool size for aggregate admission. Validate mixed assembly/query/auth/editorial work. [bounds]
  5. Configure the real fleet and database: actual Railway max replicas and overlap must match pool declarations; choose same-region Neon compute with sufficient measured allowance; use direct lock connections; disable scale-to-zero as planned. Secure API origin, validate trusted IP headers and parent-domain cookie/CORS behavior. Test new deployment generations and cold starts. [platform]
  6. Complete launch/recovery work: migrate authoritative data from the parked laptop during an authorized window; compare critical row counts; set managed backups/history and restore into scratch; rehearse rollback. Rotate secrets, narrow Stripe key, set catalog charging prices, configure/verify webhook events, schedule reconciliation and refresh/rate jobs, and route errors/backlog/spend alerts to an owner. Leave intentional laptop pricing unchanged during preparation. [checklist]
  7. Strengthen then run CAP-08 with explicit billed-load approval: validate exact page content, authenticated membership expectations, cache isolation, fast-503 thresholds and rolling stop rules. Use representative distinct URLs and dataset size; capture images/JS separately, valid sessions, publish/media contention, failure/recovery and spend. Report offered/achieved rate and reserve below the safe measured ceiling. A target failure changes the campaign envelope or implementation, not the acceptance gates. [matrix]

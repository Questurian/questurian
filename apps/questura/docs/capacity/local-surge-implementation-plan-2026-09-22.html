What “finished” means

A fresh checkout can build and run the two applications against a disposable, deterministic local database; execute the relevant journeys and failure cases; and produce evidence showing bounded work, correct identity/content isolation, eventual refresh and reliable test stops. Required checks fail clearly when fixtures, services or telemetry are missing.

  • Included: application fixes, regression tests, local production builds, isolated Postgres/Redis, local browser captures, finite loopback-only experiments, restore rehearsal, CI definitions and written results.
  • Excluded: Cloudflare/Railway/Neon provisioning, DNS/WAF changes, real-domain changes, deployments, live or test Stripe calls, OAuth-provider calls, email delivery, paid image/maps calls, hosted load and live database mutations.
  • No large-library project: use ~50 realistic published articles across the three content types, plus draft/missing/deleted cases. Do not repeat 8,000-article or 16,000-article fanout work to certify launch.
  • No capacity promise: local requests/second describe this machine, workload and build. Campaign readiness remains a separate hosted acceptance step.
Repository rules remain binding. Read applicable AGENTS.md files and caveman skill. Never set Payload push: true. Preserve public/private rendering separation, pricing copy, entitlement semantics and existing staff/service access. Local google-login is stale scratch, not authoritative data. Laptop is parked and not needed for this plan.

Implementation choices below are recommended defaults. Change one only with a short rationale and equivalent acceptance coverage. Product-policy changes—such as removing public API consumers, limiting total saved bookmarks or changing stale-content entitlement policy—need an explicit decision; they are not prerequisites for routine defensive fixes.

Prevent experiments from measuring another process, touching unrelated data or claiming results without enough context.

Close Payload credential-presence bypass and early-ingress gaps

Preserve supported public/staff/service reads while ensuring fake credentials never remove resource limits.

Implementation requirements

  • Add a failing integration covering an arbitrary Authorization header, x-api-key and forged payload-token against public REST globals and GraphQL. Existing predicate unit tests deliberately pass such values through; replace that assumption with verified identity semantics.
  • Recommended flow: cheap bounded ingress → authenticate/resolve staff or service identity once → classify real caller → apply anonymous clamp/limiter or approved authenticated policy → bounded work → release in finally. If invalid credentials are rejected outright, ensure public clients without credentials still work and invalid headers cannot force expensive unbounded verification.
  • Anonymous GraphQL remains closed. Do not rely on Payload returning 401 when a strategy returns user:null; enforce the refusal before GraphQL execution. Do not reopen it by recognizing a header name or cookie substring.
  • For REST, cover whole-request admission and globals as well as collection hooks. Preserve limit/depth/pagination clamps; keep collection hook as defense in depth, but avoid accidental double spending of one logical request’s limiter bucket. Document where authentication occurs and avoid resolving it twice.
  • Place ingress before Redis or auth dependency waits. Hold work admission through actual handler completion; no gate acquired and released before SQL. Keep private/no-store refusal response and Retry-After behavior.
  • Retain generated route wrappers and tests that catch Payload regeneration removing them. Audit authenticated requests for a deliberate finite policy; valid credentials should not mean infinite work. Do not silently restrict existing writer/Location Manager operations without checking their expected limits.

Required verification

  • Credentials matrix: absent, unrelated cookie, malformed header, expired JWT, forged JWT, bogus API key, valid staff, valid service account and disabled account. Exercise REST collection, REST global and GraphQL with alias-heavy query in a bounded disposable test.
  • Pass asserts exact status/policy, downstream handler/auth call counts, clamped args and active admission while handler is blocked. Invalid credentials never execute anonymous GraphQL or skip REST protections.
  • Inject slow/unavailable Redis and auth; max active and queue stay within configured limits; waiter abort removes queued work; thrown handler releases slot. Assert subsequent legitimate request succeeds.
  • Regression: supported staff/service request remains authorized; collection access and field privacy unchanged.
Done when

No presence-only exemption remains. Public mounts and credential verification have finite ingress/work bounds, and integration tests prove the real Payload behavior rather than mocking it away.

Evidence: Route/credential matrix, focused unit + real route results, and explanation of limiter count ownership.

Complete account admission, caller fairness and invalid-session handling

A flood of account requests must not bypass resource control or monopolize shared pools.

Implementation requirements

  • Produce a coverage table for every method on identity, bookmark refs/list/add/delete, member body and Better Auth routes. Record auth, rate limit, ingress/work gate, data pools, timeout, cache headers and failure policy. Include server-side auth API calls: do not assume Better Auth HTTP middleware protects internal getSession calls.
  • Preserve zero-DB/Redis no-cookie identity shortcut. Use an explicit session-cookie parser/name match rather than allowing arbitrary substring text to choose the expensive branch. Malformed/invalid tokens may reject cheaply; prove actual work with counters.
  • Wrap costly private reads in common bounded admission before dependencies. Cover bookmark writes’ session-resolution cost even though their write-rate limit remains account-based. Cover auth ingress/password hashing and callback work deliberately; do not break OAuth or provider callback contracts.
  • Choose gate ordering once and document it. Avoid nested reacquisition of the same gate, deadlocks and unused slots. Check Origin before avoidable costly work where applicable. Ensure route exceptions still preserve private CORS/no-store semantics.
  • Add lightweight pre-auth abuse control for session-bearing identity/auth traffic, with account-based limits after verified identity where useful. Hash identifiers; never use untrusted raw cookie text as an unbounded metric label. Shared-IP limits are coarse guardrails, not per-person identity.
  • Keep public counter failure fail-open only behind functioning local admission; member-body and bookmark-write protection fail closed. A counter outage should have an explicit unavailable reason where response compatibility permits, not be misrepresented as proven abuse. Record policy for each class.
  • Validate total demand: public query + assembly + private + auth + background work all compete for pools. Gate counts are not reserved DB connections. Prefer conservative bounded defaults and measured waits; do not increase pool sizes to hide queuing. Add needed per-class observability without logging personal data.

Required verification

  • Under low-volume simultaneous blocked handlers, every costly route obeys configured active/queue/wait bounds and releases permits after success, exception, timeout or waiter cancellation.
  • Mix member A/B, nonmember, expired/random/malformed cookies and anonymous requests. Assert exact identities, no cross-user bookmark/body leakage, no-store on success and failure, and no false “logged out” response for a temporary dependency failure.
  • Exercise one noisy account/IP beside other synthetic callers. Show one caller cannot circumvent its limiter by rotating fake headers; quantify any intentional shared-IP throttling.
  • Slow Redis/auth while public and private requests coexist: public no-cookie /api/me stays zero SQL/Redis; pool waiting drains after release; valid users recover without restart.
Done when

Coverage table has no unexplained costly ungated route. Bounds and failure semantics hold through real route tests, with no private data leaks or entitlement changes.

Evidence: Method-level coverage table, gates/pool demand rationale, session-work counts and mixed-caller test results.

Design constraints and traps

This plan does not require real OAuth or real payments. Local callback/provider stubs prove application branches only; leave actual provider limits and cookie behavior explicitly unverified.

A configuration accepted by local validation must not undercount the connection demand it claims to allow.

Implementation requirements

Validate product overflow, explicit-versus-derived disagreement and malformed strings. Report variable names, never secret URIs.

Recommended representation: prior-generation component sizes when pool sizes change. Compute the maximum over those states instead of assuming “current serving count + old surge” covers every rollout. Count job and bootstrap processes plus reserve. Keep calculated budget distinct from actual host enforcement.

Prevent tests from certifying one env while boot uses another. Do not inherit migration-only zero timeout settings into serving.

Keep temporary failure separate from anonymous or empty content

Reduce browser request amplification while preserving identity, entitlement and saved-state correctness.

Implementation requirements

  • Introduce structured request errors carrying status, retry metadata and category even when body is HTML or malformed JSON. Parse status/headers first; cap error-body details and do not echo a full challenge page into UI/logs. Parse Retry-After seconds and HTTP-date safely.
  • Provide a bounded default request deadline and caller AbortSignal support. Avoid a library-wide mutation retry: writes remain non-retried unless idempotency is separately established. Cancellation is not an authentication failure. Clean up timers/listeners.
  • Centralize retry classification and bounded jittered backoff. Do not automatically retry 401/403 or browser challenge HTML; handle rate-limit guidance deliberately. Honor valid Retry-After within overall deadline; if it exceeds the UI budget, surface a retry-later state instead of retrying earlier. Keep finite attempts and maximum elapsed time.
  • Share browser identity request/state between navbar and gated content without wrapping public page output in a dynamic server session. Recommended: a provider-independent in-flight/shared identity service that existing query consumers can use. Deduplicate concurrent reads and propagate login/logout/expiry invalidation; never store personalized identity in a server-global/shared render cache.
  • Gated identity error becomes “unable to verify access” with retry, not anonymous/paywall. Member-body error stays a temporary failure. Abort obsolete full-body requests on navigation and clear prior identity/body state before rendering another user’s data.
  • Bookmark refs error retains an error/unknown state distinct from signed out. Recover on explicit retry and appropriate identity changes. Ensure logout clears refs and pending state; prevent a late response from previous user overwriting next user’s store. Preserve optimistic update rollback semantics.
  • Article search must send server render credentials through a server-only boundary and distinguish unavailable from zero results. Audit helper import sites before adding render headers; a browser-callable helper must never receive a secret. Preserve bounded render bucket. Keep 429/503 out of successful empty-result caches.
  • Remove unnecessary JSON Content-Type on bodyless GETs if compatible with API contract, reducing avoidable preflights. Do not solve preflight load by relaxing CORS. Measure navigation/prefetch traffic before disabling useful prefetch broadly.

Required verification

  • Pure request/retry tests with controlled clock/random: JSON error, HTML 403 challenge, 429 with valid/invalid/date Retry-After, 503, network failure, stalled body, cancellation, malformed JSON on 200. Assert finite attempt/duration and no tight retry loop.
  • Component/browser test: fresh gated page with navbar yields one shared identity lookup for concurrent consumers; member/nonmember/anonymous state remains correct. Rapid A→logout→B transition cannot reuse A body/bookmarks.
  • Fault tests: identity 503 does not display subscription paywall or login prompt as fact; search 503 does not display “No results”; bookmark refs can recover without full reload. Mutation still has no automatic retry.
  • Production browser capture records document, RSC/prefetch, /api/me, refs, full-body and OPTIONS counts before/after. Confirm secret canary absent from public build assets.
Done when

Each failure has correct UI semantics, identity sharing is safe, retries are finite and staggered, and synthetic browser journeys show reduced/understood automatic requests.

Do not assume React Query is available inside article content; PublicChrome currently mounts its provider around navbar only. Preserve that architectural constraint or deliberately redesign it with static-output tests.

L06 · Depends on L01

Claim refresh jobs only when they can start

Prevent queued leases from expiring before work begins, while retaining fenced at-least-once delivery.

Implementation requirements

  • Replace “claim four, process serially.” Recommended simplest fix: serial worker claims one job just in time. Choose real bounded concurrent workers only if local backlog evidence warrants it; each free execution slot claims work it can start immediately.
  • Preserve claim token/generation checks on every completion, retry and fenced search side effect. No claim may finish another generation’s job. Retain idempotent at-least-once delivery; do not claim exactly-once semantics.
  • Bound complete revalidation delivery duration as well as each chunk; account for claim age, shutdown grace and drain deadline. If a job can legitimately exceed lease, define renewal or resumable delivery policy before adding concurrency. Do not truncate targets to fit a lease.
  • Propagate abort/deadline through delivery. Stop claiming on shutdown; allow bounded finish or leave recoverable ownership. Route all drain entry points through existing lifecycle serialization.
  • Keep retry jitter and terminal failure visibility. Document how failed jobs are inspected/replayed locally. Record job duration, oldest pending age and duplicate delivery count without high-cardinality content logs.

Required verification

  • Four jobs with controlled slow delivery, two real processes/connections and explicit barriers: no unstarted job consumes a lease behind unrelated work.
  • Hold first worker across lease expiry, reclaim in second, then release first; assert stale completion cannot mark current generation done or overwrite current search row.
  • Fail final chunk after earlier chunks succeeded; retry all required targets and converge. SIGTERM/SIGKILL mid-delivery preserves obligation; no new claims after shutdown starts.
  • Inject new publication while prior generation is in flight. Exact final revision and empty healthy backlog after recovery; terminal failure visible and replay restores it.
Done when

Claim/execution policy matches actual concurrency; timeouts and shutdown are bounded; no lost current-generation refresh or invalid stale completion.

Evidence: Worker timing/ownership timeline, duplicate-delivery accounting and generation/queue assertions.

Design constraints and traps

Use tiny deterministic fanouts and delayed local receiver. A 16,000-article fanout test is unnecessary for this lease bug.

Repair workload realism, metrics and emergency stops

A green result must mean correct service at the offered load; a failed run must stop predictably.

Implementation requirements

  • Extend existing manifest for launch corpus, sessions and request classes. Assert exact identity ID/entitlement and article revision/body visibility, not only authenticated boolean. Store no real cookies in committed manifests.
  • Model browser-informed flows: fresh free landing, gated landing for member/nonmember, repeat/client navigation, submitted search, bookmark refs/list/add/delete and bounded local sign-in. Use distinct sessions and documented synthetic client addresses. Do not accidentally make the whole crowd share one rate-limit bucket.
  • Tag HTTP requests themselves with route class, signed-in state and expected outcome. Threshold successful-request latency separately from all-request availability; expose document TTFB and full duration as different metrics. Carry signed-in tags through page()/identity()/api(), not just check().
  • Use open arrival-rate scheduling for capacity/spike claims. Detect generator saturation and dropped iterations; a closed-loop test is allowed for deterministic correctness but must be labeled. A fast-503-only run must never pass sustainable-capacity criteria.
  • Cold means observed cache reset/new process and measured origin work—not merely an unused query string. Application coalescing can ignore that string. Keep dataset launch-sized; include same-hot-key misses and dispersed launch keys as distinct cases.
  • Feed per-instance pool/admission/backlog samples into supervisor through an explicit collector stream or dedicated local metrics bridge. Include zero values, instance identity/restarts and sample timestamps; deduplicate instances. Do not expose diagnostics publicly or poll through a load balancer that hides half the fleet.
  • Combine rolling HTTP failure, semantic correctness failures, sustained queue growth, stale/missing telemetry, wall-time/request limit and generator health into clear stop reasons. Validate every abort parameter before starting. Stop all owned generators/children after grace; bound output storage.
  • Gate every safety assertion: Retry-After presence/validity, no-store refusals, exact response and privacy checks. Add explicit successful-throughput floor appropriate to measured workload when accepting controlled-overload runs. Preserve rate-limit refusals as real visitor failures within a claimed service envelope.

Required verification

  • Negative controls assert exact exit reason/code and bounded stop time for wrong 200 body, leaked member marker, false identity, cacheable private response, missing/invalid Retry-After, queue growth, missing telemetry and invalid config.
  • A queue returning to zero clears growth history correctly; one unhealthy instance is not hidden by fleet averages. Unknown/duplicated/stale instance samples fail evidence validity.
  • All-503 target cannot pass sustainable workload; deliberately expected overload can pass infrastructure-containment check only while reporting useful success/refusal fractions separately.
  • One generator saturation test proves dropped arrivals invalidate a capacity claim. One false-positive control proves benign short fluctuation does not immediately terminate under declared policy.
Done when

Metrics have producers and consumers, every claimed safety assertion affects outcome, and negative controls demonstrate correct failure reasons before any substantial run.

Evidence: Versioned workload, telemetry schema, threshold/abort table and negative-control results.

Design constraints and traps

Prefer extending existing supervisor over introducing another monitoring stack. This local stop system is a prerequisite, not proof of a real provider billing cap.

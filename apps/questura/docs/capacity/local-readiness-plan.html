L01 · P0Local

Make publication and refresh responsibility atomic

Dependencies: L00

Problem verified now: request.ts catches enqueue errors and performs best-effort inline work, which can run before content commits. enqueue.ts silently falls back to the adapter outside a found transaction. delivery.ts treats missing URL/secret as successful return; production config does not require these settings. Thus “save succeeded” need not mean refresh responsibility was preserved.

Proposed changes

  1. Recommended publication policy: when refresh is required, a content mutation and its durable obligation must commit together. If enqueue fails, return a clear retryable save error and roll back the mutation; do not silently fall back inline. Preserve editor input and explain this behavior change. If product insists on accepting saves, require an equally durable repair marker written atomically; logs are not an alternative.
  2. Validate transaction participation for collection/global create, update and delete, including Local API callers. A supplied transaction ID that cannot resolve must fail explicitly. Supported no-transaction entry points must establish a transaction around both mutation and enqueue; writing an outbox row alone is not atomic with a separate save.
  3. Require frontend revalidation destination and secret in serving production configuration; a missing destination/secret must fail delivery and remain retryable, never become done. Dev-only disconnected mode must be explicit and must not claim delivered status. Reject REFRESH_OUTBOX=off in the normal production publication contract or expose it as an explicitly degraded emergency mode with documented repair work, not safe rollback.
  4. Validate required worker/scheduler secrets according to selected process role. Keep builds independent of deployment-only secrets. Replace tests that currently assert silent fallback with the new publication contract.

L02 · P0Local

Fence refresh claims and prevent stale search side effects

Dependencies: L00; integrate L01 before end-to-end acceptance

Problem verified now: worker.ts claims a batch for 60 seconds, processes it sequentially and completes/retries by id plus status=running. A newer enqueue or expired-lease reclaim can give another worker ownership that the old worker can still overwrite. Default batch is 50; internal HTTP drain requests 100. A claim token alone would protect job metadata, not stale search writes.

Proposed changes

  1. Add an additive claim token and monotonic work generation/version. Increment generation when newer work is enqueued; each worker records the generation it owns. Completion, retry and lease renewal must compare both generation and token and check affected-row count. Report superseded work separately from done.
  2. Claim only work that can start immediately within configured concurrency, rather than leasing a large waiting batch. Bound each drain by jobs and wall time; renew a live lease or enforce a deadline shorter than lease lifetime. Stop new claims on shutdown; crashed claims remain reclaimable.
  3. Protect search side effects as well as outbox status. Preferred design: apply search delete/insert and final generation check in one database transaction that locks the relevant job row, so enqueue cannot interleave between validation and commit. Another design is acceptable only with equivalent generation-aware writes/deletion tombstones. Do not hold a DB transaction across a frontend HTTP request.
  4. Revalidation is repeatable invalidation, so duplicate HTTP delivery can be tolerated; never promise exactly-once delivery. Preserve pending newer obligations, union targets, backoff and failed-job inspection. A generation must not reset to an old value when completed rows are pruned.

Relevant existing files / directories

Acceptance tests

  • Barrier-driven, separate-connection test: A claims; newer save enqueues; B claims; A finishes/fails. A cannot complete, retry or overwrite B’s obligation.
  • Lease expiry while A is paused: B finishes latest work; resume A. Latest search row and outbox generation remain correct. Repeat with unpublish/delete so stale work cannot recreate searchable content.
  • Drain more jobs than fit in a lease window with a slow local receiver: jobs not yet started are not prematurely leased; no runaway duplicate execution.
  • Kill worker after claiming and after side effect but before acknowledgement. Another worker converges correctly. Verify retry limits, jitter bounds, failed replay, target merging and retention still work.
  • Compare counters with affected rows: stale completion cannot increment done. Add migration review and schema tests per migration protocol below.

Local completion: At-least-once delivery with fenced ownership and newest-content convergence proven across local processes.

L08 · P1Local

Define cache freshness and fallback contracts before adding storage

Dependencies: L00, L01, L05

Problem verified now: LastGood is a 500-entry process-local map. Its seven-day clock resets on any successful fetch, even potentially cached data, and fallback can become newly cached page output. Therefore a seven-day entry age is not a global maximum content age. Articles intentionally have no fallback; that is not a bug.

Proposed changes

  1. Write separate contracts for public curated stale serving, article access changes, true 404/deletion, transient errors and private data. Recommended local target: use an origin-issued content revision and authoritative validated-at time, not repeated cache-hit time, for curated fallback eligibility.
  2. Add byte/entry eviction and provenance if LastGood remains. Never renew freshness on fallback or merely reading cached data. On an authoritative deletion, evict/tombstone stale entries; during backend failure never claim that an unknown deletion is known safe.
  3. Ensure fallback cannot be stored as indefinitely fresh output; trace both fetch cache and full-route cache. If Next/OpenNext cannot enforce the desired freshness boundary, narrow the promise and record a hosted blocker rather than adding an unproven shared cache.
  4. Preserve primary throw-on-non-404 semantics, article fail-loud behavior and private no-store. Add an interface for shared curated fallback only if restart/multi-instance tests show it is required by the chosen availability target; do not add KV/R2 solely because it exists.

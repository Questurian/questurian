Questura test gap audit

Before paid hosting exists: what the tests we have would miss, ranked, with a prompt for each fix. Nothing in the app was changed to write this. It builds on the pre-launch plan (steps 1–7 done), docs/launch-day.md, the launch harness, and the capacity work. It doesn't re-propose anything those already cover.

For you

The 5 scariest gaps, in plain words

1. The website could go live pointing at "localhost"

The website's address for the API is baked in when the site is built. The build steps in our setup checklist leave it out, so the live site would quietly fall back to http://localhost:4000. Every visitor's sign-in, bookmark and Subscribe button would fail. A similar setting controls where images come from. The template labels it confusingly, and one wrong value breaks every image. What we do: make the build refuse to finish without the real addresses, scan the built site for "localhost", and check it again on launch day. About an hour of work, and it needs no hosting (prompt 1).

2. A refunded or disputed customer may keep getting charged

Stripe changed the shape of its data in the API version we use: a charge no longer says which invoice it paid. Our dispute handling relies on exactly that field, so a chargeback probably does nothing today. Refunds rely on it too, and will break the same way once the new webhook is created on the new host. The tests all use hand-made data that still has the old field, so they pass anyway. What we do: fix the lookup, test it with data in the new shape, pin the webhook's version, and prove it with your one real refund on launch day (prompts 2 and 6).

3. When something breaks, nobody will know

No error reporting is set up, the website's logs are off on Cloudflare, and there are no alerts and no uptime check. Emails also go out from a placeholder address (you@questurian.com) with no anti-spam records written down, so password-reset emails may land in spam or never send. What we do: pick an error sink (a free option works), turn on logs, request ids and one uptime check, fix the sender, and write down the DNS records to add (prompts 3 and 4).

4. Moving day can break things quietly

The new host needs fresh secret keys. Changing them also, without any warning, disconnects the machine accounts that publish into the site: the writer pipeline and Location Manager. Sign-ups and Stripe events that land on the laptop during the move would be lost. The laptop's own Stripe webhook, nightly job and key would keep running afterwards. Backups on Neon aren't set, and a restore has never been timed. What we do: rehearse the whole move on this laptop, rotated secrets included, and write the cutover and backup runbooks before paying for anything (prompts 5 and 12).

5. Most of what a visitor does has never been clicked through, and the checks don't run by themselves

Browser tests cover the paywall, signing in and out, and redirects. Nothing clicks through sign-up, checkout and return, password reset, the account page, cancelling, the phone layout or a slow connection. A 5-minute sweep today found a JavaScript error on the account page. The big readiness suite and the browser tests only run when someone starts them by hand, so after launch a change can break sign-up with CI still green. What we do: add those journeys, fail on any console error, and run the whole suite in CI (prompts 7 and 8).

What needs you: three small decisions, all in their prompts. (a) Which error sink: a free, no-vendor setup, or Sentry (prompt 3). (b) Whether visitors can delete their own account, or ask by email at launch (prompt 14). (c) The design of a time-boxed "load test key" so a load test through Cloudflare isn't counted as one visitor (prompt 9). Everything else is agent work on this laptop.

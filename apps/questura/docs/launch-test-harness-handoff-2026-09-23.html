Handoff, 2026-09-23. The next agent's job is to build the tests before launch, so that launch day is running them, not writing them. Payments and sign-in come first. While writing them, look for real bugs. Finding one is a success, not a detour.

What the owner wants

Deploy straight to the new platform: frontend on Cloudflare, backend on Railway. Before that, set up every test we can, and write the launch-day tests ahead of time. More tests is better. Be creative with coverage, go past industry standard, be a little paranoid. It has to work the first time. Payments matter most, then auth and login. The tests may turn up critical bugs.

The owner has plenty of token budget for this. Depth is wanted.

Target stack, already decided: Cloudflare Workers through OpenNext for the client, Railway for the server, Neon Postgres, Railway Redis in the same project. Details and open decisions are in apps/questura/docs/capacity/cap07-platform-readiness.md §1a. Configuration still to redo on the new platform is in apps/questura/docs/serverless-launch-checklist.md. Don't re-ask these or plan for Vercel.

Rules that bind this work

Live Stripe is real money. Test mode proves nothing about live. sk_test is only for capturing fixture JSON that gets committed, and you must say so when you use it. Never use the Mac's stripe CLI key. Live reads go through apps/questura/scripts/stripe-live. A real purchase happens only when the owner says yes to that specific one. See AGENTS.md, which overrides the bundled stripe-* skills.

New dependencies need the owner's approval. Playwright, fast-check and Stryker are not installed. Ask before adding them (AGENTS.md: downloading new code).

Don't deploy, resume the laptop, or change live config. The owner decides those.

Workflow: one branch and one PR per piece of work. Wait for green CI, then squash-merge it yourself (owner's standing preference). Use the caveman skill (AGENTS.md). Payload schema changes follow the migration steps in AGENTS.md.

Databases: port 6379 on the Linux laptop is the live Redis. Never point local at it or flush it. The local Redis is 6380 (infra/local/compose.yml). In the last session, the tool's permission checker blocked both a pg_dump of the live DB and reads of the scratch DB. Don't work around that; ask the owner.

It covers sign-up, two sessions, a Redis flush, password-change revocation, the 429 limit, sign-out, and the five payment routes for anonymous, non-member, foreign-origin, signed-out and expired callers.   • apps/server/src/app/api/payments/fresh-session.test.ts: every payment route skips the cookie cache.

  • Readiness sandbox, apps/server/scripts/readiness/: disposable Postgres and Redis, production builds, real sign-ins. route-checks.ts has the /api/me identity matrix, stripe-stub.ts is a loopback Stripe that knows two prices, restore-rehearsal.ts rehearses a restore, and adapter-smoke.ts tests the Cloudflare build. Plan: docs/capacity/local-readiness.md.

What's missing: no browser end-to-end tests at all. The readiness route checks never touch the payment routes. Webhook signature checking has only ever been tested with a mock. No property-based tests or mutation tests. And nothing yet is written against Cloudflare, Railway or Neon specifically.

Start here

Things already spotted, not yet fixed

P0

up.railway.app is missing from the shared-suffix list

apps/server/src/shared/config/session-cookie.ts — SHARED_PUBLIC_SUFFIXES

The list has pages.dev, workers.dev and vercel.app, but not the chosen backend host. A cookie domain or a same-site check involving a Railway default host would be judged by the wrong rule. Add it with a test (cases in session-cookie.test.ts). Check the rest of the list against the Public Suffix List for every host this project might use.

P0

Railway origin versus the trusted proxy header

apps/server/src/shared/config/trusted-proxy.ts · cap07 §1a item 3

With TRUSTED_PROXY=cloudflare, anyone who reaches *.up.railway.app directly can write CF-Connecting-IP themselves and get a fresh rate-limit bucket on every request. That's the X-Forwarded-For bypass already verified on live once, back again. You need both a test that proves the origin is unreachable or ignores the header, and a platform decision. Railway has no entry in trusted-proxy.ts.

P1

Webhook signature checking has never run for real

stripe-webhook.route.test.ts mocks constructEvent; lifecycle-simulation replaces it

Nothing proves the route hands Stripe the exact raw bytes it received. If a framework or adapter change re-serializes the body, every live webhook fails while every test passes. See test A1.

P2

No livemode check on incoming events

Signatures already separate the modes, since each endpoint has its own secret. Rejecting an event whose livemode disagrees with the key's mode is still a cheap second lock. Decide, test, record.

P2

A revoked session still reads paid content for up to 5 minutes

That's the cookie cache from #650, by design. auth-smoke.sh shows /api/me still says signed in after sign-out or expiry. The member article body uses the same cache. Confirm the owner accepts this for paid content. If they don't, route the article body through freshSession and measure the cost.

P2

The server and client principal types have drifted

The client's VisitorPrincipal.membership.graceUntil exists at runtime but isn't in the server type (current-principal.ts). See test D3.

Tier A · Payments

Money paths

A1

Real webhook signatures through the real route

P0local

The mocks can't catch a body that was changed before verification. That failure is silent and total.

How: sign payloads offline with stripe.webhooks.generateTestHeaderString (no network) and a test secret. Check that a valid signature gets 200. Check that a wrong secret, a flipped body byte, a changed whitespace, an old timestamp (past the tolerance), a missing header and a header with several v1 values get refused correctly. Then run the same tests against the OpenNext and Railway builds, not only next dev.

A2

Webhook ordering and duplicates against a real Postgres

P0readiness DB

The fakes in lifecycle-simulation model locks and uniqueness. Real Postgres decides whether they actually hold.

How: a *.integration.test.ts in the readiness harness. Deliver the same event twice concurrently, deliver deleted before updated, and send an event for an unknown customer. Run two customers in parallel and prove the advisory lock separates them but not across customers. Pass: exactly one email, one row, and the right final entitlement.

A3

A captured payload for every handled event

P1local

Only the subscription and invoice lifecycle has real captured payloads. Refunds, disputes and checkout.session.completed run on payloads we typed ourselves.

How: list which events in handled-events.ts have a fixture. Capture the missing ones in test mode as committed fixtures. This is the one allowed use of sk_test; say so in the PR. Replay each through the route, the way F1/F2 do.

A4

Property tests for entitlement

P1local

Hand-written cases cover the states someone thought of. Random combinations find the ones nobody did.

How: generate random status × period dates × cancel flag × grace × revocation × clock position, fed to deriveSubscriptionState and deriveVisitorMembership. Invariants to hold:

  • never entitled on incomplete, incomplete_expired, or canceled-and-unpaid;
  • never entitled past the paid date plus grace;
  • a refund revocation always wins;
  • entitlement never lands exactly on a boundary.

fast-check needs approval. Without it, a seeded random loop still works.

A5

Checkout guardrails, attacked

P0local

A table of hostile inputs:

  • returnTo: //evil.com, /\evil.com, %2F%2F, javascript:, look-alike Unicode slashes, very long values, CRLF.
  • plan: unknown, array, object.
  • referralId: @, newlines, 101 characters.
  • A double click must produce one Checkout Session.
  • A second live subscription must be refused.
  • A price with the wrong interval, currency or amount must be refused. At launch the catalog price replaces the $0.50 laptop price, so test both.

Use the readiness Stripe stub, extended to answer customers and checkout.

A6

Cross-user access and CSRF on the five routes

P0local

Signed in as A, send subscriptionId / customerId for B in the body and query of every route. They must be ignored.

POST attempts that must fail:

  • a cookie with no Origin;
  • Origin: null;
  • Content-Type: text/plain (a "simple" request);
  • an origin that shares only a suffix, like www.questurian.com.evil.io.

Extend auth-smoke.sh or route-checks.ts.

A7

Money paths when things fail

P1readiness

Point the Stripe stub at a hang (no answer), a 500, and a slow 7-second reply.

  • Routes answer within the 8-second Stripe budget, with no second customer or session.
  • With Redis down, payments fail closed and public reads stay up (cap07 §6.3).
  • With the DB down: a clean 503.
  • A pooled DATABASE_URI with no unpooled one refuses to boot.
A8

The whole purchase in the sandbox, no Stripe

P1readiness

Stub checkout returns a URL. A test signs checkout.session.completed with the sandbox secret, then:

  • /api/me reports a member;
  • the member article opens;
  • cancel, then move the clock past the period end;
  • the article locks and Subscribe comes back.

Repeatable in CI.

A9

Launch-day payment suite

P0launch day

Read-only unless the owner says otherwise. One command against the new origin:

  • verify:stripe-webhook-events: no MISSING, not DISABLED;
  • /api/payments/plans lists $12.99 and $79.99 from live prices;
  • the anonymous and foreign-origin matrix from A6;
  • the webhook delivery log shows 200;
  • a reconcile dry run shows 0 changes.

Tier B · Auth

Sign-in, sessions, accounts

B1

Browser end-to-end on three engines

P0locallaunch day

No browser test exists. Cookies, redirects and Safari's tracking prevention only show up in a real browser.

How: Playwright (needs approval) on Chromium, WebKit and Firefox. Flows: sign up, sign in, sign out, reset password, change email, subscribe up to the Stripe page, and the member article. Locally, read emails from a local mail sink rather than Resend. On launch day, run the same specs against the real domains with a dedicated test account.

B2

Session tampering and cookie mix-ups

P0local
  • Flip one byte of session_data.
  • Pair A's session_data with B's session_token, and the reverse.
  • Replay a cache cookie after the session is revoked (payments must refuse; /api/me behaviour recorded).
  • A cookie signed under a rotated secret must be refused with 401, never 500.
  • Session fixation: a token planted before sign-in must not survive it.
  • Oversized and duplicated cookie headers.
B3

Enumeration, brute force and limits behind the proxy

P0locallaunch day
  • A wrong password and an unknown email give the same status, body, and timing to within noise.
  • Password reset behaves the same for unknown emails.
  • Rotating spoofed X-Forwarded-For or CF-Connecting-IP must not rotate the rate-limit bucket under each TRUSTED_PROXY setting.
  • Every limit in better-auth.ts customRules is hit and returns Retry-After.
B4

Account linking and staff isolation

P1local
  • Google sign-in on an existing unverified local address must not link. Use a mock OAuth provider locally.
  • A staff email is refused by visitor auth.
  • A Payload admin cookie never makes /api/me signed in.
  • A visitor cookie never opens /admin.
  • An email change needs verification and then updates the Stripe customer's email.
  • Changing email while Google is linked is refused.
B5

Password rules on the server

P1local

Call the API directly, not through the UI, on every path that sets a password. Try: 7 characters, 129 characters, missing character classes, Unicode and emoji, leading and trailing spaces, NUL bytes. Sign-in with an older weak password must still work (see visitor-password-guard.ts).

B6

Cookie contract on the real domains

P0launch day
  • The __Secure- prefix, Secure, HttpOnly, SameSite=Lax, and the intended Domain and Path.
  • No Set-Cookie on any response Cloudflare may cache.
  • Private responses carry no-store and Vary: Cookie.
  • The same-site boot check passes for www on Cloudflare and the API on Railway's custom domain.
B7

Losing Redis on the platform

P1platform, before launch

Restart Railway Redis while signed-in traffic is running. Sessions survive from Postgres, rate limits follow their documented fail mode, and payments fail closed, then recover without a restart. auth-smoke.sh already proves this locally.

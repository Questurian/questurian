# Reader-facing images are served direct from the CDN

Every photo URL the site renders points at the Bunny pull zone, not at `api.questurian.com`. The storage plugin's `disablePayloadAccessControl` flag makes Payload's `url` field resolve to the pull-zone address on every read and, as a consequence, unregisters the static handler that used to stream each file out of Bunny through the Node process. Nothing is given up by bypassing Payload's access control here: `mediaAssetAccess.read` already returns `true` for an anonymous request, so public photos were never protected by it.

One function owns the address shape — `features/media/lib/bunny-public-url.ts` — and it is deliberately byte-identical to the storage adapter's own `generateURL`, so a URL Payload stores and a URL the app builds are the same string. The host is never written in source; it is `BUNNY_STORAGE_HOSTNAME` on the server and `NEXT_PUBLIC_IMAGE_CDN_ORIGIN` on the client, which is used only for the root layout's preconnect.

The cutover is sequenced as an overlap, not a flip-and-flush. Public pages are cached SSR (ADR 0003) and a cached page holds rendered HTML full of the old `/api/media-assets/file/{filename}` URLs; the client's revalidation endpoint takes explicit tags and paths and cannot be shown to flush every cached route. So `app/api/media-assets/file/[filename]` answers that path with a 301 to the pull zone, and stale HTML keeps working while the page cache ages out. The redirect is not free to delete: the writer app still builds those URLs in six places, and its Python backend downloads through them, so it outlives the page cache and goes only when the writer app stops asking.

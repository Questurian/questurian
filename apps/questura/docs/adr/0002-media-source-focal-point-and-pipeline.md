# MediaSet source, focal point, and the variant-generation pipeline

A `MediaSet` carries a `source` (relationship to the uncropped original `MediaAsset`) and a `focal_point` (`{ x, y }` normalized to `[0, 1]` on the source image). The 7 variant `MediaAsset`s attached to a `MediaSet` are derived artifacts: the pipeline crops the source toward the focal point at each variant's target aspect ratio. Storing source plus focal point on the `MediaSet` makes regeneration possible when a new variant spec is added or an operator nudges the focal point. Per-variant overrides remain possible via the existing `VariantCropParams` shape on the source-to-variant call.

The Sharp-based variant pipeline lives in Questura, not Location Manager. It is exposed as `POST /api/media-sets/from-source` and accepts one source image, focal point, photographer credit, alt text, optional `locationRef`, and optional per-variant `VariantCropParams` overrides. The endpoint creates the source `MediaAsset`, generates and uploads all 7 variant `MediaAsset`s, assembles the `MediaSet`, and returns the resolved set. Location Manager's `UploadsService` calls this endpoint instead of running its own Sharp crops; editorial uploads in Questura admin call the same endpoint. One pipeline, one focal-point implementation, no drift between apps.

`autoCreateMediaSetForAsset` is removed. The two legal paths for variant creation are `POST /api/media-sets/from-source` (new sets) and direct `MediaAsset` upload with both `mediaSet` and `variant` set against an existing `MediaSet` (variant replacement / per-variant override). A direct `MediaAsset` upload that sets `variant` without an existing `mediaSet` is rejected. Carve-out uploads (profile pictures, inline article body images, migration tooling, external images) carry no `variant` field and are unaffected.

The public client does not call `resolveMediaSetForPlacement` directly. Each public-facing feature that loads a Payload doc for SSR exposes a view-model module (e.g. `features/articles/public/view-model.ts`, `features/location/public/view-model.ts`) that takes the raw doc plus the placement context and returns a fully-resolved view object whose image fields are `PublicImage` shapes. SSR pages render `image.url` dumbly. The resolver remains the single source of placement decisions, called only from the server.

Each collection's MediaSet migration ends with deletion of the legacy field, not with a permanent fallback. Per collection: backfill `featuredMediaSet` from existing assets; flip readers to MediaSet only via the view-model; relax the legacy field to optional; delete the legacy field once production reads have moved over. `bunny_original_url` reads are removed in the same step that completes the open-graph variant backfill for that collection.

Variant nomenclature follows Questura's `MEDIA_VARIANT_KEYS`. The Location Manager `ImageVariantType` literal `'social'` is renamed to `'open_graph'` everywhere in `@questurian/lm-shared`, controllers, services, and clients. The `toPayloadMediaVariant` translator in `payload-media.client.ts` is deleted. Per the meta-CONTEXT cross-repo rule, when a domain term crosses a boundary the consumer adopts the producer's definition; Questura is the owning context for the variant vocabulary.

Accepted MIME types align across the chain. Location Manager upload controllers and Questura's `MediaAsset.upload.mimeTypes` agree on `image/jpeg`, `image/png`, `image/webp`. `image/gif` is dropped from LM's allow-list to match Payload's; if GIF support is needed it is a separate decision that includes Sharp/Bunny implications.

`MediaSet.status` retains its admin-coarse meaning (empty / partial / usable) and is never consulted for public readiness. Public readiness remains per-placement via `resolveMediaSetForPlacement(...).status`. Admin list views and the MediaSet detail page surface a per-placement readiness summary derived from `isMediaSetReadyForPlacement`, so operators see "ready for `card`, missing `wide` for `hero`" rather than a single coarse label.

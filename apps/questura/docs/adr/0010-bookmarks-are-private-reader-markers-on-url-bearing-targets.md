# Bookmarks are private reader markers, and only on targets that have a URL

A **Bookmark** is a Visitor account's own marker on one editorial item so the visitor can return to it later. It is available to every signed-in Visitor account regardless of **Membership entitlement**, it grants no access, and it is not a **Membership entitlement** signal in either direction — bookmarking a **Gated item** while unentitled is allowed and changes nothing about the **Free sample** that item serves.

The qualifying test for a **Bookmark target** is that it has a public URL of its own. A Bookmark exists to return the reader somewhere; a document with no page has nowhere to return to. Today that admits `articles`, `single-type-listicles`, and `listicle-itineraries`, and nothing else. Venues — `dining`, `accommodations`, `attractions`, `nightlife`, `tours` — were wanted and were rejected on this test: they render only inside listicles, itineraries and curated homepage blocks, and `app/(public)` has no route for any of them. `/[country]/[city]/[category]/[slug]` looks like a venue route and is not; it renders a standard article. A venue Bookmark would therefore have to be a card carrying the venue's own data with no destination, plus provenance for where it was saved from, which is a trip list rather than a bookmark and is a different feature. Venues qualify the day they get pages. `targetType` is stored as an open value using the existing `ArticleTypeKey` keys from `features/articles/public/scope.ts`, so admitting one later is an added option and a migration rather than a redesign. Authors were also rejected, on a different ground: they do have a page, but a marker on a person promises a feed of their new work, which is a Follow — a concept with its own mechanics that is not being built, and shipping it under the Bookmark name would teach readers the wrong model.

A Bookmark stores a reference — type and document id — and never a snapshot of its target's title, image, or path. Everything displayed in the **Bookmark list** is resolved live on read, through the same `status: "published"` gate the public article index uses, so there is no second definition of publicly visible to drift from the first. The rejected alternative was denormalising title and href at save time, which reads faster and survives deletion, at the price of a list that shows stale titles and frozen paths. Frozen paths are the specific reason it loses: a published article that changes country, city, category or slug auto-creates an `ArticleRedirect`, so a snapshot would work only by leaning on the redirect table, and every re-slug would quietly degrade the list. Storing an id makes redirects irrelevant to Bookmarks entirely.

**A Bookmark never blocks an editorial action**, and this is the part most likely to be "fixed" wrongly later, because the codebase already contains the opposite pattern. A **Homepage reference lock** deliberately refuses to delete an article that a homepage still points at, and a **Homepage publication lock** refuses to unpublish one. Bookmarks get neither. A homepage reference is an editorial commitment whose severing breaks a public page; a Bookmark is a private reader marker whose severing inconveniences one person. Locking on it would hand deletion policy to the audience and would not scale — a popular article accumulates thousands of holders, any one of whom could veto an admin. The consequence is accepted rather than mitigated: an unpublished or deleted target is omitted from the **Bookmark list** silently, with no placeholder card. A "no longer available" card was considered and rejected because it raises a question that cannot be answered without exposing editorial state to the public. The row itself is retained, since unpublishing is usually temporary and a republished target should simply reappear; rows are removed only by explicit cleanup, never as a side effect of an editorial action.

Bookmarks live in their own collection keyed by the BetterAuth user id from the **Visitor session**, not as an array field on `VisitorProfiles` and not keyed to the profile. `VisitorProfiles` is the paywall record — access is `isFuture(paidThroughAt)` and nothing else — with admin-only field access on every membership field and an audit hook on change. Routing a bookmark click through an update to that document would amplify writes onto the billing record, grow an unbounded array in a single row, offer no uniqueness constraint, and lose writes to read-modify-write races on a double-click. Keying to the session identity rather than to the profile also keeps the two lifecycles independent, so bookmarking cannot fail because a profile row has not been lazily created yet. Uniqueness of `(authUserId, targetType, targetId)` is a database constraint, declared as a collection-level compound `indexes` entry so Payload emits it in the generated migration. It is load-bearing rather than an optimisation: without it a double-click writes two rows, and the delete path would then leave one behind.

The collection is readable in the admin panel by admins only and hidden from the admin navigation, with no create, update or delete path. A reader's bookmark list is personal data with no support use: it does not affect billing, entitlement, or delivery. It is present for incident forensics, not for browsing.

Bookmarks do not change the caching posture set by ADR-0003. Public content pages stay cached and anonymous-first; the bookmark control is a client island that resolves its own state after hydration, and the read, write and delete endpoints are dynamic `no-store` routes under `/api/account/*` requiring a **Current principal**. No cached response ever varies by who is asking.

# Service accounts as machine identity

Machine callers will authenticate as **`ServiceAccounts`**, a separate auth-enabled Payload collection, rather than as rows in `Users`. `Users` becomes humans-only and its role enum keeps exactly the three human roles `admin`, `editor`, and `writer`. This completes the boundary ADR-0004 drew between auth surfaces: that ADR separated visitor auth from staff auth, and this one separates machine identity from human staff identity.

`ServiceAccounts` authenticates with Payload API keys (`auth: { useAPIKey: true }`) and carries **no `authorSlug` field and no human role enum**. This is the point of a separate collection rather than a fourth `service` role on `Users`: a service account cannot appear in the staff list ABW renders, cannot be given a public `/authors/<slug>` page by `authorSlugHook`, and cannot be counted as staff by `isStaffEmail`, because the fields and hooks that produce those behaviours do not exist on it. Structure enforces the exclusion instead of a rule that each new staff-facing query has to remember.

Location Manager's `PayloadAuthClient` stops posting `PAYLOAD_SERVICE_EMAIL`/`PAYLOAD_SERVICE_PASSWORD` to `/api/users/login` and presents an API key instead. `PAYLOAD_SERVICE_PASSWORD` is retired rather than kept as a fallback; a long-lived shared password that cannot be rotated or scoped is the thing this decision exists to remove. Credential rotation becomes issuing a new key on the account, and revocation becomes disabling or deleting that one account, neither of which touches a human's login.

The `/api/auth/login` fallback in `PayloadAuthClient` is removed outright. ADR-0004 establishes that retained `/api/auth/*` routes are compatibility adapters over BetterAuth **visitor** auth, so that fallback aimed staff service credentials at the visitor auth system; it was not merely dead, it was pointed at the wrong auth surface. It also logged the response body on failure, which is a credential-adjacent log line with no reason to exist.

Access control for `ServiceAccounts` is default-deny and admin-managed: only `admin` may create, read, update, or delete service accounts, and service accounts may not manage themselves or each other. A service account's grants are expressed as explicit collection access, not inherited from a human role, so "what may this machine do" is answerable by reading one place.

The same principle — **network position is not identity** — extends to the ABW FastAPI backend, which currently accepts any caller when `ABW_API_KEY` is unset and defaults `ABW_ALLOWED_ORIGINS` to `["*"]`. Its callers must present a credential that the backend verifies, and the ABW frontend must actually send one, so that enabling enforcement is not a change that breaks the UI. Authorization for who may run a pipeline or publish stops living only in `usePermissions.ts`, which is a UI affordance and not enforcement.

This costs more than adding a role to `Users`: a new collection, a migration, changes to the LM client and its environment, and an access-control review. It is chosen anyway because the alternative keeps machine credentials inside the collection that governs human CMS access, where every future staff-facing query is one forgotten `role !== 'service'` filter away from leaking a service account into a human surface.

Framework security upgrade

Next.js, Payload CMS and Better Auth have published security holes in the versions Questura runs, including two critical ones. This page gives another agent everything it needs to upgrade them safely. It covers what is wrong, what the target versions are, the order to do it in, and how to prove nothing broke. The owner has approved doing the upgrade.

The catch

Why the server cannot just take a patch release

All of the Next.js fixes live on the 15.5 line (≥15.5.24) or on 16.3.3 and later. Payload's Next adapter does not accept 15.5 at all. Even the latest @payloadcms/next@3.90.2 declares:

next: ">=15.2.9 <15.3.0 || >=15.3.9 <15.4.0 || >=15.4.11 <15.5.0 || >=16.3.3 <17.0.0"

15.4.11 is already the newest version in the 15.4 range, and it is still vulnerable. The server's only patched route is therefore Payload 3.90.2 with Next 16.3.3 or later. The client has no Payload, so it can take the small step to 15.5.26.

Order

Three PRs, smallest first

Use one branch and one PR per step. Wait for green CI, then squash-merge. Run heavy jobs (builds, the readiness stack, Stryker) one at a time: the Linux laptop has 7.5 GB of RAM, and running two together has already caused out-of-memory kills.

PR 1: Better Auth 1.6.11 → 1.6.33 (server)

  • Read the Better Auth changelog from 1.6.12 to 1.6.33 for anything touching cookie cache, ipAddressHeaders, rate limiting, X-Retry-After, social sign-in or the Payload/Postgres adapter. The Questura code leans on several of these on purpose; see src/features/visitor-auth/lib/current-principal.ts and client-identity.ts.
  • If the Better Auth tables change, follow the migration steps in AGENTS.md exactly. Stop and ask if visitor_auth_* tables would change unexpectedly.
  • Prove it with the unit tests, then readiness:auth (29/29), readiness:oauth (71/71: Google linking against a fake Google, staff/visitor isolation), readiness:purchase (22/22) and the Playwright suite.

PR 2: Client Next 15.4.11 → 15.5.26

  • This stays within Next 15, so no async-API or config rewrite should be needed. Check the 15.5 release notes for anything touching middleware.ts, experimental.isrFlushToDisk or next lint. next lint is deprecated in 15.5 and the client's lint script uses it.
  • Bump eslint-config-next to match.
  • Prove it with pnpm build and the OpenNext build (opennextjs-cloudflare build), the readiness stack against the rebuilt client, and Playwright (20/20 on Chromium and Firefox).

PR 3: Server Payload 3.79.1 → 3.90.2 and Next 15.4.11 → 16.3.x

Move every @payloadcms/* package and payload together, pinned to the same exact version. Payload refuses mixed versions. Split the work into commits in this order so a failure is easy to trace:

  1. Payload to 3.90.2 on Next 15.4.11 first. 3.90.2 still accepts 15.4.11, so this isolates Payload's own changes. Read each minor's release notes (3.80–3.90) for breaking changes and required migrations.
  2. Schema check. Run pnpm db:migrate:create payload-3-90-upgrade > /tmp/questura-migrate-create.log 2>&1 and follow the migration rules in AGENTS.md. If Payload generated nothing, delete the empty migration. If it generated destructive SQL, stop and ask the owner.
  3. Then Next to 16.3.x, along with react/react-dom if Payload 3.90.2 asks for newer ones. Next 16 is a major release. Use the official upgrade guide (npx @next/codemod@canary upgrade latest, then read nextjs.org/docs/app/guides/upgrading/version-16) and verify each item below against it instead of trusting this list.

Known Next 16 points that touch this server:

  • Turbopack is the default for next build. apps/server/next.config.mjs has a custom webpack() block (the extensionAlias for .js → .ts). Expect Next 16 to refuse to build with a webpack config, or to ignore it. Either move the alias to turbopack.resolveExtensions/resolveAlias, or build with next build --webpack. Payload's withPayload may already handle this in 3.90, so check.
  • The eslint key in next.config and next lint are removed. The server config has eslint.ignoreDuringBuilds; delete it. The server's lint script already calls eslint . directly.
  • middleware.ts is renamed to proxy.ts and the old name is deprecated. apps/server/src/middleware.ts exists. Rename it (the export becomes proxy) and keep the same matcher. Proxy runs on the Node runtime.
  • Synchronous request APIs are gone. cookies(), headers(), draftMode(), params and searchParams must be awaited. A grep on 2026-09-23 found no un-awaited calls in src, but the codemod will catch route handlers that read params synchronously.
  • Node ≥ 20.9. The laptop has Node 22.23. The engines field still allows 18; tighten it.
  • typescript.ignoreBuildErrors: true means the build will not catch type breakage. Run pnpm --dir apps/questura/apps/server typecheck yourself before and after, and compare the error count. CI does not typecheck yet; see "Run the Questura typecheck in CI" if that task has landed.
  • Security headers come from async headers() in next.config.mjs (SECURITY_HEADERS). Confirm they still appear on every response, including errors. launch:verify and security-headers.test.ts check this.

Proof

What "nothing broke" means

A test harness exists to make this upgrade safe; it is in docs/launch-day.md. Run everything below before the upgrade to record the baseline, then again after each PR. The counts must match.

# unit tests
pnpm --dir apps/questura/apps/server test
pnpm --dir apps/questura/apps/client test

# production build of both apps in the readiness sandbox
# (Postgres :5442, Redis :6390, fake Stripe :3191, fake Google :3192; see launch-day.md for setup)
pnpm --dir apps/questura/apps/server readiness:stack -- up --build
pnpm --dir apps/questura/apps/server readiness:routes     # 114/114
pnpm --dir apps/questura/apps/server readiness:payments   # 43/43
pnpm --dir apps/questura/apps/server readiness:purchase   # 22/22
pnpm --dir apps/questura/apps/server readiness:auth       # 29/29
pnpm --dir apps/questura/apps/server readiness:oauth      # 71/71
pnpm --dir apps/questura/apps/server readiness:faults     # 22/22
pnpm --dir apps/questura/apps/server readiness:contracts  # all ok

# browser tests against the sandbox
pnpm --dir apps/questura/apps/e2e test                    # 20/20 chromium + firefox

# the Payload admin still loads and saves (manual, in the sandbox):
# sign in as staff, open an article, edit a field, save, reload

If readiness:contracts reports a changed response shape, Payload or Next changed what an endpoint returns. Find out why before running --update. The contract files in apps/questura/contracts/ are what the client relies on.

Rules

Do not break these

  • Do not deploy, resume the Linux laptop's live window, or change live config. This work is sandbox-only.
  • Port 6379 and Postgres on 5433 on the laptop are live data. Never point a test at them or flush them. The sandbox uses 6390 and 5442.
  • No Stripe test mode as evidence about live, and never use the Mac's stripe CLI key. The fake Stripe (scripts/readiness/stripe-stub.ts) covers payments.
  • Do not enable Payload push: true. Schema changes go through migrations only, following AGENTS.md.
  • Check row counts (locations, articles, media_assets, media_sets, users, visitor_profiles, visitor_auth_*) before running any migration against data you care about.

If Payload 3.90 + Next 16 turns out to be too much in one go: Next 15.4.11 on the server is the exposure. The critical AVIF bug needs the image optimizer; check whether the server serves /_next/image at all. If it does not, set images.unoptimized: true as a stopgap. Tell the owner which advisories stay open. Do not sit on a half-finished upgrade.

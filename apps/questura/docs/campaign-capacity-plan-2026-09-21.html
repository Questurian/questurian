Outcome and limits

Prepare Questura for campaign-driven traffic while preserving publication, authentication, membership and payment correctness. Retain Next.js, Payload, Postgres, Redis and Bunny. Reduce unnecessary work, bound resources, measure sustainable capacity, and prove recovery. Do not promise capacity from source inspection or local timing.

Confirmed: 10–100 million monthly views refer to external campaign/social views before clicks. Modeling assumptions: 3–12% click-through, 30-day month, 180-second visits, two pages/visit, 10× burst. These are not observed analytics or a ceiling. At 70M × 12%, model yields 8.4M visits/month and 5,833 active burst readers; at 100M, 12M visits and 8,333 readers. A burst concentrating 1% of 8.4M visits into ten minutes yields 140 arrivals/second, far above the 10× model.

Target workload: 6,000 active readers, 8,500 stretch, plus independent arrival-rate tests progressing toward 1,000 predominantly cached page requests/second. At 180-second sessions and two pages/session, 6,000 readers imply about 67 page requests/second—not 6,000 requests/second. Record identity, search, RSC, prefetch and asset traffic separately. No test level passes unless its error and latency gates pass too.

Execution tickets

CAP-01 — Trustworthy baseline and load harness

Problem: apps/server/scripts/measure-public-api.ts mixes response statuses in latency summaries, excludes one sample as cold even for concurrent batches, lacks request deadlines and does not model sustained arrival rates.

Change: separate warmup from measurement; report successful latency separately from 4xx/5xx, timeouts and transport failures; validate bounded CLI arguments; report offered/completed throughput, sample count and workload metadata. Add explicit cold/warm modes and JSON evidence. Add protocol arrival-rate and session scenarios, with per-scenario URL/data manifests. Extend existing diagnostics before adopting another monitoring stack.

First regression cases: a fast 429 or 500 cannot lower successful p95; every warmup response is excluded; hung fetch is timed out and counted; invalid run/concurrency arguments fail clearly. Extract pure helpers only if needed to test behavior. Existing server vitest config covers src tests, not scripts: deliberately register any script test location or test extracted helpers in its covered tree.

Deliverables: repaired harness, focused tests, initial anonymous/cold-content report, scenario definitions and execution instructions. Capture SQL count/time, pool wait, request latency, cache state and payload bytes where available. Missing diagnostics must say unavailable, not zero. Identify load-generator limits and dropped arrivals.

Gate: reproducible small local run against verified production build; status/body validation confirms requests exercised intended content rather than auth errors, empty responses or throttling. Record any baseline failure without hiding it. No heavy load until limits and abort conditions are in place.

CAP-02 — Connection budget and overload boundaries

Depends on CAP-01 instrumentation; config regression fix can precede full baseline if baseline unavailable.

Problem: shared/database/pool-budget.ts permits allowance=0; config process count defaults to one; actual Payload max is separately hardcoded in payload.config.ts. Autoscaling multiplies pools. Per-request page-read semaphore does not bound all simultaneous requests.

Change: require finite positive integer production budgets/process limits; single-source actual maxima and budget calculation. Account separately for pooler client allowance and physical Postgres backends, direct advisory-lock connections, startup, jobs, administrative reserve and rollout overlap. Do not blindly treat every pooled client as a dedicated backend. Provider-specific enforcement must match selected platform.

Introduce bounded admission for expensive public work, with queue length/age limits and release in finally. Select initial concurrency from baseline and DB budget; document it. Keep cheap identity and critical private work from being crowded out. A per-instance limiter only becomes a total bound when maximum instances are bounded. Aborted requests must not leave abandoned waiters; HTTP cancellation alone does not cancel SQL. Preserve server-side SQL timeouts.

Gate: tests for omitted/invalid config, exact allowance boundary, multiple instances and rollout overlap; overload rejects predictably and queues drain; throwing/timeouts cannot leak slots. Do not increase pools simply to pass a load test. Record how to revert limits safely.

CAP-03 — Anonymous identity and request amplification

Depends on CAP-01. Start by measuring, not by introducing a session hint.

Trace: PublicChrome → Desktop/Mobile navbar → useAuth → useUserQuery → /api/me → current-principal → Better Auth/profile/account methods. Relevant paths are apps/client/src/lib/user/hooks/useUserQuery.ts, apps/server/src/app/api/me/route.ts and apps/server/src/features/visitor-auth/lib/current-principal.ts. React Query deduplicates within one cache; each fresh visitor can still trigger identity work.

Measure absent, malformed, expired and valid session cookies; SQL, Redis, imports/cold initialization and response bytes. Do not assume no-cookie requests hit the database. Optimize only observed unnecessary work: safe absent-cookie server shortcut, defer account-provider details to account UI if compatible, eliminate duplicate lookups. A client hint is optional and requires a separate correctness rationale; it must not suppress valid sessions or authorize access.

Gate: no-cookie path remains cheap; valid membership, logout, expiry, reconnect, OAuth and cross-tab behavior preserved. Record identity requests/visit before and after with real-browser checks. Live cookie/OAuth claims require separate live evidence under project rules. Local tests are explicitly local evidence.

CAP-06 — Durable refresh and safe startup

Depends on CAP-04; integrate CAP-05 if a public read model is needed. Database outbox schema follows migration rules.

Move production seed and currency-sync work out of per-instance startup. Keep boot checks read-only/small. Implement durable failed-work recovery for search indexing and public revalidation: enqueue with committed content change, deterministic dedupe keys, idempotent processing, capped retry/backoff and failed-job inspection/replay. Use existing facilities if suitable; do not provision a queue by default.

Translate attention into workload

A reader can spend three minutes reading while the server does no work for them. An HTTP request might last a fraction of a second. Never equate active readers, requests per second, in-flight requests, or database connections.

Request concurrency ≈ request rate × mean response time, using the same request class. At 100 requests/sec, 0.2 seconds means about 20 in flight; 2 seconds means about 200. A slowdown itself increases concurrency.

Timing matters more than the month total. 1% of 8.4M visits arriving within ten minutes means 140 arrivals/sec, roughly 25,200 active readers at three minutes, and 280 page requests/sec at two pages/visit. Campaign analytics must replace the illustrative 10× assumption.

Architecture for readers who mostly read

Public readingBrowser → global CDN / shared Next.js ISR → cached public HTML.

Hot campaign pages prewarmed. Public cache keys ignore tracking parameters only where they cannot change content. Verify cookies, query strings and RSC variants do not fragment or leak cache.

Personal interactionBrowser → bounded API → shared Redis / managed Postgres.

Session, bookmarks, member content and payments stay private. Different budgets for cheap identity, search and expensive content assembly.

Publishing and mediaPayload → durable refresh work → public cache. Images → Bunny CDN.

Move expensive image work off serving path if contention is measured. Versioned artifacts, retry records and last-good public output.

Frontend target already recorded as Vercel in ADR-0003. Confirm shared ISR behavior and bills on the selected plan; do not add a second public-cache platform without evidence. Backend stays Node-compatible for Payload, with managed Postgres and Redis nearby. Use the platform’s routing and bounded autoscaling; no custom load balancer needed initially.

Single-region writes plus global cached reads fit this workload. Self-hosted multi-instance Next.js requires deliberate shared cache and invalidation coordination. Current isrFlushToDisk: false is a local/laptop decision, not proof of durable global caching. Next.js guidance; Vercel cache request flow.

Conditional optimization: if batched homepage assembly still misses its latency/SQL budget, precompute public page representations at publish time. Serve compact published data; rebuild only affected pages. Keep private entitlements separate. This adds a versioned read model and recovery obligations, so measurements must justify it.

Work sequence

Phases explain the strategy. The execution contract above defines tickets CAP-01–08, dependencies, verification and handoff. Follow that contract when implementation is requested. No production resources or services provisioned by this report.

1 / Baseline
Required first

Make demand and capacity measurable

  • Repair measure-public-api.ts: warmup phase, status-separated latency, request deadlines, throughput, error counts and realistic URLs.
  • Add k6 scenarios for constant arrivals and reader sessions. Record load-generator saturation and dropped iterations; limiters get a separate abuse test.
  • Correlate route latency, SQL count/time, pool acquire/wait, memory, event-loop lag, Redis latency, cache hits and external calls. Export across instances; existing db-stats only samples one process.
  • Measure anonymous identity waterfall, cold homepage assembly and authenticated reads. Capture sanitized representative data volumes, including many authors and content URLs.

Done when: one reproducible report shows workload, build SHA, data scale, cache state, offered/completed traffic, success p50/p95/p99 and all failure classes. Failing and throttled requests cannot improve the success metric.

2 / Bound resources
Before scale-up

Prevent database exhaustion and retry cascades

  • Require explicit production connection budgets and max instances. Account for rollout overlap, jobs, operational reserve and direct advisory-lock connections.
  • Single-source actual pool sizes and budget constants; tune from measured throughput, not a target visitor count. Transaction-pooler compatibility and timeout settings verified on selected provider.
  • Add bounded admission for expensive reads, maximum queue age, deadlines and controlled overload responses. Preserve room for auth and editorial operations; do not bypass query guards for internal requests.
  • Set Redis command/connect deadlines and bounded retries. Keep existing fail-open versus fail-closed security policies deliberate; add jitter where safe.

Done when: missing/invalid budgets fail config validation; burst and rolling-deploy tests stay below actual backend connection allowance; queues drain after overload without a restart.

Files: apps/server/src/shared/database/pool-budget.ts; shared/config/assert-production-config.ts; features/visitor-auth/lib/redis-secondary-storage.ts; shared/http/public-read-rate-limit.ts.

3 / Spectator path
Largest cost lever

Keep public browsing cheap and correctly cached

  • Measure /api/me with absent, invalid and valid cookies. Ensure cookie-absent check can avoid unnecessary heavy initialization; avoid account-provider lookup until account UI needs it.
  • Evaluate optional UI session hint or deferred identity lookup only with logout, expiry, OAuth and cross-tab tests. Hints never grant access; do not read HttpOnly cookies from JavaScript or personalize shared HTML.
  • Verify public HTML and API cache hits at edge and ISR layers, across URLs, regions, UTM parameters and cookies. Separate trusted renderer traffic from anonymous rate-limit buckets.
  • Add consistent public-route limits and controlled miss behavior; prewarm campaign landing URLs with bounded concurrency.
  • Timeout/5xx must not become an empty successful homepage or false 404. Keep last-good output on failed regeneration.

Done when: repeat public navigation stays cached, identity requests and SQL cost are quantified, account correctness holds, and origin work does not rise one-for-one with hot anonymous page traffic. Aim ≥99% hit rate on prewarmed campaign HTML; long-tail traffic reported separately.

Files: apps/client/src/lib/user/hooks/useUserQuery.ts; apps/server/src/features/visitor-auth/lib/current-principal.ts; apps/client/src/features/CityDashboard/lib/fetchCityHomepage.ts; apps/client/next.config.ts.

4 / Cold content
After baseline

Reduce SQL per page

  • Batch homepage references by collection and shape; preserve order, publication rules, image placement and per-request deduplication.
  • Use narrow select/populate fields. Keep existing batched feed hydration; do not redo solved work.
  • Replace sitemap per-author counts with grouped visibility. Paginate minimal sitemap fields and cache generation.
  • Use EXPLAIN (ANALYZE, BUFFERS) on safe SELECTs against representative data. Confirm feed/search indexes installed; add only indexes justified by plans.
  • If still too expensive, implement publish-time public representation as a separate decision with schema, versioning, invalidation and backfill plan.

Done when: statement/read counts and p95 improve versus identical baseline; increasing blocks/authors does not create uncontrolled parallel work; all content/access snapshots stay equivalent.

5 / Recovery
Before campaign

Make failed refreshes recoverable

  • Move production seeds out of startup; schedule exchange-rate work once. Keep boot checks small.
  • Durable outbox/retry records for cache revalidation and search updates: commit-aware enqueue, idempotent consumers, capped backoff, failed-job inspection and replay.
  • Measure publishing/media CPU contention with reading. Isolate heavy image generation when it affects serving; preserve original upload and variant correctness.
  • Configure managed backups and point-in-time recovery; prove restore and deploy rollback. Use existing reconciliation workflow on platform scheduler.

Done when: injected refresh failures replay successfully; stale-index backlog is visible; restarts do not duplicate uncontrolled jobs; a documented restore succeeds. Agree recovery-time and acceptable-data-loss targets before provider selection.

Files: apps/server/src/instrumentation.ts; features/public-revalidation/revalidation/delivery.ts; features/articles/public/search-index/service.ts; docs/serverless-launch-checklist.md.

6 / Prove & release
Campaign gate

Validate target platform, economics and failure behavior

  • Choose production provider/plan and region using measured resource demand. Confirm quotas, scaling behavior, shared caches, database/pooler caps and billing units.
  • Run local production-build tests first; run final capacity tests on chosen production-class platform with representative non-sensitive data. Laptop is not the capacity target.
  • Configure portable latency/error, pool-wait, refresh-backlog and spending alerts. Define campaign pause/reduce action and operator.
  • Retain report per release and run a smaller regression workload in CI. Repeat full proof after material database, cache or runtime changes.

Done when: gates below pass, spend projection fits approved budget, launch checklist closed, recovery playbook rehearsed. Provisioning, paid tools and externally billed load runs require explicit approval.

Cached traffic still has a bill

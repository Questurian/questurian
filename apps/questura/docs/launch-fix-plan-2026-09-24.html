Plan · 2026-09-24

Launch fix plan

How to fix everything the test gap audit found: in what order, what depends on what, what can run side by side, the decisions only the owner can make (with a recommendation for each), and a short prompt per job. The audit holds the detailed "how" for each item, so every prompt here points at the audit's prompt and adds the amendments decided in this plan. Where the two differ, this plan wins.

For you

The short version

  • 18 local jobs (audit prompts 0–17), each one PR, run one at a time on this laptop, plus 4 checks on the real hosting during the quiet go-live (PL1–PL4).
  • The minimum before go-live is 12 of them (marked before go-live). They stop outages, lost money, lost email and a blind launch. The other 6 are before announcing or after launch.
  • What's needed from you: nine small decisions, listed next with my recommendation for each. Two need an explicit yes before anyone builds (Sentry, and the load-test key). Everything else can go ahead on the recommendation unless you say otherwise.
  • Nothing here deploys, pays for anything or touches live data. The paid hosting only enters in Phase 5, with you present.

What can run side by side

The sandbox (fixed ports, most of the laptop's memory) takes one job at a time. These jobs don't need it, so each can run next to one that does:

  • Item 16 (time zones): unit tests only.
  • Item 4 (email): skip its optional sandbox assertion, or run that part last on its own.
  • Item 3 (errors): code and unit tests. Run its one sandbox proof when the sandbox is free.

Everything else is one at a time, in the order below. Keep one light job at most alongside a sandbox job, never two, because the desktop app crashed once today under memory pressure.

Every agent

Rules for every job

  • Read AGENTS.md, this plan (the item and its amendments) and the matching audit prompt before starting. The plan wins where they differ. Use the caveman skill.
  • Never touch ports 5433 or 6379 on this laptop (live Postgres and Redis) or the questura-postgres / questura-redis containers. The sandbox is Postgres :5442 and Redis :6390.
  • Memory: about 7.5 GB, with the desktop app using ~1.5 GB. Never build while the readiness stack is up. Build with NODE_OPTIONS="--no-deprecation --max-old-space-size=3072". Check free -m before each heavy job, and stop if less than 2,500 MB is available. Stop the stack when done.
  • Commit and push after each milestone, so a crash or usage limit loses nothing.
  • No deploys, don't resume the laptop's live window, no live Stripe or Google, no paid services, no load against anything outside this machine. New dependencies need the owner's yes. Payload schema changes follow the AGENTS.md migration steps.
  • If readiness:routes rewrites docs/capacity/runs/<date>-surge-routes.json and the run isn't evidence for your change, revert it.
  • Workflow files (.github/workflows/*): git's stored credential can't push them. Push with git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push …, since the gh login has the workflow scope.
  • Wait for CI in the foreground (two agents stalled on background waits). Repeat this until it prints DONE, then squash-merge with gh pr merge <N> --squash --delete-branch and git checkout main && git pull:

Phase 1 · Things that would break launch or lose money

1

Build and config traps: localhost, image host, workers.dev, canonical

before go-livesmall · ~2 hsandbox

Problem

The API address is baked in at build time and falls back to localhost:4000, and the checklist's build step doesn't pass it. The Stripe key would be empty, the image host is easy to set wrong, and a workers.dev copy of the site would be crawlable.

Fix

The build refuses to finish without real https addresses and a live Stripe key (the sandbox gets an explicit flag), a post-build scan for localhost, the image host is checked, metadataBase and absolute canonicals are added, workers_dev is turned off, and launch:verify gets host checks.

Done when

A build without the env fails, naming the variable. readiness:adapter still passes 13/13, and the new launch:verify checks have unit tests.

Amendments

The adapter smoke already refreshes its worktree (#688), so rely on it for the "built correctly" proof. Keep the guard's error message understandable to a non-developer.

2

Refunds and disputes under Stripe's new data shape (basil)

before go-livemedium · half a daysandboxmoney

Problem

Stripe removed invoice from Charge (and PaymentIntent). A dispute probably revokes nothing today, and refunds break once the new webhook endpoint is on the same version. Tests pass because they use old-shape data. Confirmed: the pinned SDK's Charge type has no invoice field.

Fix

Resolve charge → invoice → subscription through invoicePayments (falling back to charge.invoice only when present). Add new-shape tests for full and partial refunds and for disputes created, won and lost. The Stripe fake learns charges, disputes and invoice payments, and readiness:purchase drives a refund and a dispute. The webhook verify script fails on an API-version mismatch.

Done when

New-shape tests fail on today's code and pass after the fix, readiness:purchase covers refund and dispute end to end, and the launch-day count is updated.

Amendments

Also search the whole payments feature for any other read of .invoice on a Charge or PaymentIntent, or .charge/.payment_intent/.subscription on an Invoice (confirmed absent from the pinned SDK's types; an invoice's subscription now lives at parent.subscription_details.subscription), and fix or pin each one with a test. The owner has no Stripe test key for this, so skip the optional fixture capture.

16

Time zones in dates members see

before go-livesmall · ~2 hno sandbox: can run alongside

Problem

Dates in emails, API messages and the account page use the server's time zone. Railway and Workers run in UTC, so "access ends" can be a day off, and server and browser can render different text, causing hydration errors.

Fix

One date helper per app: access dates in UTC with the month name, article dates in one fixed zone. Use it at every listed call site, and run the tests under two extreme time zones.

Done when

Tests pass under TZ=UTC and TZ=Pacific/Kiritimati, and no bare toLocaleDateString() is left in those areas (a grep proves it).

Amendments

Run this before item 8. Note in the PR whether it's the likely cause of the /account React #418 error, so item 8 can confirm it.

Phase 3 · Moving day

10

API front door: the in-app half of ADR-0016

before go-livemedium · half a daysandbox

Problem

The chosen protection (Cloudflare in front plus a secret header) has no code yet. If it's done wrong, the edge rule blocks the site's own pages, or every render shares one rate-limit bucket.

Fix

ORIGIN_AUTH_SECRET is checked in src/proxy.ts with a constant-time comparison and two modes. The header is stripped and never logged. The client's server-side fetches send it from a Worker secret. Unit, readiness and launch:verify checks are added.

Done when

With the secret set, the sandbox refuses a direct call without the header, and the client still renders every page in the route list.

Amendments

Keep /api/health open (liveness). Record the two unknowns that only the platform can answer (Transform Rule on Worker subrequests, and the IP they present) as PL1 items.

Rehearse moving day, and write the cutover runbook

before go-livemedium · ~1 daysandbox

Problem

New secrets on the new host silently break the writer pipeline's and Location Manager's API keys, and make stored Google tokens unreadable. The Postgres versions differ. Sign-ups and webhooks can land on the laptop mid-move. The laptop's webhook, nightly job and key would keep running afterwards.

Phase 5 · Quiet go-live on the real hosting (you present)

Order: provision (H01 checklist) → cutover (item 5 runbook) → deploy → PL1 go-live verification → PL2 Stripe settings check, then your one purchase and refund → PL3 load test with your spending cap → PL4 ops drills (a forced error, downtime alert, Redis restart, restore, rollbacks, cold start) → announce.

The prompts are in the audit, "Prompts · on the real hosting". Every live action needs your yes to that specific step. Nothing is announced until all four pass.

Added to PL1 by item 10 (the API front door, ADR-0016). Two questions only the platform can answer, both read-only, from the API's log and Cloudflare's dashboard:

  • PL1-10a · Does the Transform Rule reach the Worker's own subrequests? The site sends X-Questura-Origin-Auth itself from the Worker secret, so pages render either way. Record whether the header on a Worker render is the Worker's or the rule's (a temporary Transform Rule value that differs from the Worker's, for one request, with the owner's yes), and whether pages still render with the rule on. If the rule does not reach them, nothing changes; if the Worker secret is missing, every page that needs the API fails, which launch:verify's home, article and author checks catch.
  • PL1-10b · Which address do Worker renders present to the API? From the API log, record the CF-Connecting-IP a Worker render arrives with (a Cloudflare address, one per colo, or the reader's). Public reads carry the render token and have their own bucket either way; any other limiter a render reaches counts by that address. If all renders share one address, say so and check that no render path hits an address-counted limiter.

Also for PL1: launch:verify --origin-edge <the target api.questurian.com's DNS record points at> must report 403 for a caller who skips Cloudflare, and the Railway edge rule is in place (H01 step 8), or the write-up says the app's own check is the only lock.
